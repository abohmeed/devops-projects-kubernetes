Installing somebody else's operator is the right move for most stateful software, since the people
who maintain it know its failure modes better than anyone else does. But sometimes there is no
existing operator for the thing you need to manage, and building your own means choosing a route
first. This handout scaffolds an operator with kubebuilder, the Go-based toolchain behind most
generated Kubernetes controllers, so you can see a reconcile loop with your own eyes before the next
lecture installs a production operator and the one after that builds a much lighter one with no Go at
all.

## Before you start

You need the EKS cluster from earlier in this course still running:

```bash
eksctl create cluster -f s01/eks/cluster.yaml
```

You also need Go 1.26 and `make`, plus the kubebuilder binary itself. On a Linux x86_64 machine:

```bash
curl -LO https://go.dev/dl/go1.26.8.linux-amd64.tar.gz
sudo tar -C /usr/local -xzf go1.26.8.linux-amd64.tar.gz
echo 'export PATH=$PATH:/usr/local/go/bin' >> ~/.bashrc && source ~/.bashrc
curl -L -o kubebuilder https://github.com/kubernetes-sigs/kubebuilder/releases/download/v4.16.0/kubebuilder_linux_amd64
chmod +x kubebuilder && sudo mv kubebuilder /usr/local/bin/
sudo apt-get install -y make
```

On macOS, swap the first two lines for the `darwin` release and the Homebrew `make` that already
ships with Xcode's command line tools. Confirm both tools resolve before going further:

```bash
export AWS_PROFILE=<your-aws-profile>
go version
kubebuilder version
```

`go version` should print `go1.26.8`, and `kubebuilder version` should print `KubeBuilder: v4.16.0`.
kubebuilder needs exactly this toolchain (a Go compiler, `make`, and its own binary) to do anything at
all, which is itself the first lesson of this lecture: this route has a real setup cost before a
single line of controller code exists.

## Step 1 - Scaffold the project

```bash
mkdir nginx-operator && cd nginx-operator
kubebuilder init --domain devopsprojects.io --repo example.com/nginx-operator
```

`--domain` groups every API this project defines under one namespace-like label, and `--repo` sets
the Go module path the generated code imports itself by. This writes the project skeleton:
`cmd/main.go`, a `Makefile`, and a `config` folder of manifests you will never edit directly.

```bash
kubebuilder create api --group web --version v1 --kind NginxSite --resource --controller
```

This adds the API type and the controller for a new kind called `NginxSite`. Once it finishes, only
two generated files are meant to be edited by hand: `api/v1/nginxsite_types.go` and
`internal/controller/nginxsite_controller.go`. Everything else is scaffolding you build on top of,
not code you rewrite.

## Step 2 - Define the API type

Open `api/v1/nginxsite_types.go`. `NginxSiteSpec` holds the fields a user sets (the desired state),
and `NginxSiteStatus` holds what the controller reports back (the observed state). The `+kubebuilder:`
comments above the fields are markers the tool reads to generate the CustomResourceDefinition; you
never write the CRD's YAML by hand. Replace the scaffold's placeholder `Foo` field with a real one:

```go
// message is the text the site serves.
// +optional
Message string `json:"message,omitempty"`
```

Save the file. This one field is now part of the schema Kubernetes will validate every `NginxSite`
object against.

## Step 3 - Write the reconcile loop

Open `internal/controller/nginxsite_controller.go`. The `Reconcile(ctx, req)` method is the loop
itself, and its signature is deliberately thin: `req` carries only a namespace and a name, nothing
about what actually changed. That is on purpose. It forces every run to read the object fresh,
compare desired state against actual state, and act on whatever difference it finds, which is exactly
why the same loop is safe to run again after any error. Replace the scaffold's placeholder body with:

```go
log := logf.FromContext(ctx)

var site webv1.NginxSite
if err := r.Get(ctx, req.NamespacedName, &site); err != nil {
    return ctrl.Result{}, client.IgnoreNotFound(err)
}
log.Info("reconciling", "name", site.Name, "message", site.Spec.Message)
```

`client.IgnoreNotFound` turns a "the object no longer exists" error into a clean, silent return
instead of a logged failure, which matters because that error is completely expected the moment
someone deletes the resource this controller watches. Lower in the same file,
`For(&webv1.NginxSite{})` inside `SetupWithManager` is the line that tells the controller manager
which kind to watch in the first place; a fuller controller would add `Owns(...)` for any child object
it creates, so a change to that child also triggers a reconcile.

## Step 4 - Generate and install the CustomResourceDefinition

```bash
make manifests
make install
```

`make manifests` regenerates the CRD's YAML from the markers in `nginxsite_types.go`, including the
new `message` field. `make install` applies that CRD to the cluster your kubeconfig points at.
Confirm it registered:

```bash
kubectl get crd nginxsites.web.devopsprojects.io
```

## Step 5 - Run the controller

```bash
make run
```

This starts the controller on your own machine, talking to the cluster through your kubeconfig
exactly like `kubectl` does, rather than running inside a Pod. Leave it running in its own terminal;
it only reads and logs at this point, since nothing has created an `NginxSite` object yet.

## Step 6 - Watch it reconcile

In a second terminal, open `config/samples/web_v1_nginxsite.yaml` and set:

```yaml
message: "Hello from version 1"
```

Apply it and watch both terminals:

```bash
kubectl apply -f config/samples/web_v1_nginxsite.yaml
kubectl get nginxsite
```

The controller's terminal prints a `reconciling` line naming the object and its message. Change the
file to `"Hello from version 2"` and apply it again; a second `reconciling` line appears. Now delete
it:

```bash
kubectl delete -f config/samples/web_v1_nginxsite.yaml
```

Nothing gets logged this time. `Get` returns "not found", `client.IgnoreNotFound` swallows that
error cleanly, and the loop returns without doing anything else, exactly as Step 3 explained.

## The real cost of this route

Everything above worked, but it came at a price worth being honest about. This toolchain needs the
Go compiler itself (about 270 MB) and, once you have scaffolded a project and run a build through it,
**module and build caches that add up to more than 2 GB** on top of that. None of it is billed by
AWS, since it lives entirely on your own machine, but it is a real disk cost that installing a
finished operator (the next lecture's approach) or declaring one in YAML (the lecture after that)
never asks for. The controller you just wrote also still creates nothing on its own: standing up an
actual Deployment, ConfigMap, and Service from this `NginxSite` object is roughly 90 more lines of Go
that were deliberately left out of this walkthrough.

## Cleaning up

Stop the controller with **Ctrl+C** in its terminal, then remove the CRD and confirm it is gone:

```bash
make uninstall
kubectl get crd | grep devopsprojects
```

The second command should print nothing. Reclaim the Go caches from Step 3 if disk space matters to
you:

```bash
go clean -modcache -cache
```

If you are not continuing straight into the next lecture, delete the cluster as well, since nothing
from this lecture needs it kept around on its own:

```bash
eksctl delete cluster -f s01/eks/cluster.yaml --wait
```

## Traps

::: gotcha
**A line reading `Operation cannot be fulfilled … the object has been modified` appears in the
controller's log.** This is an optimistic-concurrency conflict: two updates to the same object raced
each other, and controller-runtime's client retries automatically. It looks alarming because it logs
at error level with a stack trace, but on its own it is harmless and needs no action from you.
:::

::: gotcha
**`kubebuilder init` fails with `project name "…" is invalid: must not contain dots`.** kubebuilder
takes the project's name from the folder you run it in, and a folder name containing a dot is
rejected outright. Make sure you are inside a plainly named folder such as `nginx-operator` before
running `init`.
:::

::: gotcha
**`kubectl apply` on the sample fails with a strict decoding error naming `spec.message`.** This
means the CRD registered in the cluster is older than the type you just edited, which happens if
`make install` was skipped or run before the edit. Re-run `make manifests` and `make install`, then
apply the sample again.
:::
