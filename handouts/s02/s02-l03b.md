Nobody writes a chart for your own application ahead of time, and the next team that has to run it
deserves one versioned package, not a folder of manifests to copy and hand-edit. This handout
scaffolds a chart for the small `whoami` app used in the Kustomize lecture, makes it configurable
through values files, walks through a real templating mistake and the one check that actually
catches it, then installs it into two environments and publishes it so someone else could pull it
without your source folder at all.

## Before you start

You need Helm 4 on your machine (the previous lecture's handout has the full installation steps)
and the EKS cluster from earlier still running. If it was deleted, recreate it:

```bash
eksctl create cluster -f s01/eks/cluster.yaml
```

You will also need a Docker Hub account and a personal access token with **Read & Write** scope, to
publish the chart at the end. Never put that token on a command line or in a file; you will paste it
only at an interactive password prompt.

```bash
export AWS_PROFILE=<your-aws-profile>
mkdir -p s02/helm && cd s02/helm
```

## Step 1 - Scaffold the chart

```bash
helm create hello-chart
cd hello-chart
```

This creates `Chart.yaml`, `values.yaml`, an empty `charts/` folder (for any charts this one might
depend on), a `templates/` folder, and a `.helmignore` file. Skim `values.yaml` and note that
`ingress.enabled`, `httpRoute.enabled`, and `autoscaling.enabled` are all `false` by default; the
starter chart ships with several optional features switched off, ready to turn on later if you need
them, so you do not have to strip anything out to get a working chart.

## Step 2 - Read what was generated

Open `Chart.yaml`. It carries `name: hello-chart`, `version: 0.1.0` (the chart's own version,
bumped whenever the chart itself changes), and `appVersion` (the version of the application it
packages, unrelated to the chart's own version number).

Open `templates/deployment.yaml`. It is a plain Deployment with a few places wrapped in double
curly braces that Helm fills in at install time. The image line reads:

```
"{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
```

The pipe (`|`) passes whatever is on its left into the function on its right, and `default` returns
its argument only when the piped value is empty. With no tag set anywhere, the effective tag falls
back to `appVersion`. The container port is `{{ .Values.service.port }}`, so the Service and the
container always move together whenever that one value changes.

Open `templates/_helpers.tpl`. The `hello-chart.fullname` helper builds the name every object in
this chart gets, from the release name: if the release name already contains the chart name, it is
used as-is; otherwise the two are joined. Install a release literally called `hello-chart`, and
every object it creates is also named `hello-chart`, which is why the commands later in this
handout can address the Service and pods by that exact name.

## Step 3 - Make it your own application

In `Chart.yaml`, set:

```yaml
appVersion: "v1.11.0"
```

In `values.yaml`, change the image repository, and leave the port as it is since `whoami` listens
on port 80:

```yaml
image:
  repository: traefik/whoami
```

Add a new `environment` block at the end of the file:

```yaml
environment:
  - name: WHOAMI_NAME
    value: default
```

In `templates/deployment.yaml`, right under the `imagePullPolicy` line, add:

```yaml
          env:
            {{- toYaml .Values.environment | nindent 12 }}
```

`toYaml` turns the `environment` list back into YAML text, and `nindent 12` inserts a line break and
indents every resulting line by twelve spaces, landing it directly under `env:`. Indentation here is
not cosmetic: it is the only thing telling Helm's template engine, and later the Kubernetes API,
which object a line belongs to. Save the file.

## Step 4 - Two values files, one chart

Keep `values.yaml` as your shared defaults, and add one file per environment for whatever differs.

`values-dev.yaml`:

```yaml
replicaCount: 1
environment:
  - name: WHOAMI_NAME
    value: dev
```

`values-prod.yaml`:

```yaml
replicaCount: 2
environment:
  - name: WHOAMI_NAME
    value: prod
```

A values file passed with `-f` merges on top of `values.yaml`, and a value passed with `--set` on
the command line wins over both. Values files are typically committed to version control, so
secrets never belong in one; pass those on the command line, sourced from environment variables set
outside your shell history.

## Step 5 - Check the chart before installing anything

```bash
helm lint .
```

Expect:

```
==> Linting .
[INFO] Chart.yaml: icon is recommended

1 chart(s) linted, 0 chart(s) failed
```

Render the Deployment without touching the cluster at all:

```bash
helm template hello-chart . -f values-dev.yaml --show-only templates/deployment.yaml
```

You should see `image: "traefik/whoami:v1.11.0"` and the `env` block carrying `dev`.

## Step 6 - The mistake that three checks all miss

Change `nindent 12` to `nindent 8` in `templates/deployment.yaml`, save, and render it again with
the same `helm template` command from Step 5. It still renders successfully, with no warning or
error, but the `env` entry now lands at the same indentation depth as the container itself, which
YAML reads as a second, separate item in the `containers` list rather than a field inside the first
one:

```yaml
      containers:
        - name: hello-chart
          image: "traefik/whoami:v1.11.0"
          imagePullPolicy: IfNotPresent
          env:
        - name: WHOAMI_NAME
          value: dev
          ports:
```

`helm lint .` still reports `0 chart(s) failed` against this broken chart. `helm template` still
exits 0. Even a dry-run install accepts it:

```bash
helm install hello-chart . -n dev --create-namespace -f values-dev.yaml --dry-run=server
```

This also returns `STATUS: pending-install` and `DESCRIPTION: Dry run complete`, with no error at
all. None of these three checks actually validate the objects against the Kubernetes API; `helm
lint` only checks the chart's own conventions, `helm template` only checks that the output is valid
YAML, and `--dry-run=server` only lets templates look values up in the live cluster (for functions
like `lookup`) without ever submitting the rendered manifests for the API server to check.

**The check that actually catches it** pipes the rendered YAML straight into a real server-side
validation, without creating anything:

```bash
helm template hello-chart . -f values-dev.yaml | kubectl apply --dry-run=server -f -
```

This is the real failure the lecture is built around, with the exact error the API server returns:

```
serviceaccount/hello-chart created (server dry run)
service/hello-chart created (server dry run)
pod/hello-chart-test-connection created (server dry run)
Error from server (BadRequest): error when creating "STDIN": Deployment in version "v1" cannot be
handled as a Deployment: strict decoding error: unknown field "spec.template.spec.containers[1].value"
```

The broken indentation turned the `env` list item into a second entry under `containers`, so the
API server sees a second container with no `image`, only a stray `value` field it has never heard
of, and rejects the whole Deployment on the first field it cannot place. Change `nindent 8` back to
`nindent 12`, save, and run the same pipe check again:

```
serviceaccount/hello-chart created (server dry run)
service/hello-chart created (server dry run)
deployment.apps/hello-chart created (server dry run)
pod/hello-chart-test-connection created (server dry run)
```

Every object is now accepted. This one check, `helm template ... | kubectl apply --dry-run=server
-f -`, is worth running before every install of a chart you are still actively editing, precisely
because none of the other three catch this class of mistake.

## Step 7 - Install to dev

```bash
helm upgrade --install hello-chart . -n dev --create-namespace -f values-dev.yaml
kubectl get pods -n dev
```

Expect one `hello-chart-...` pod, `1/1 Running`, within a couple of seconds.

## Step 8 - Reach it

```bash
kubectl port-forward -n dev svc/hello-chart 8080:80
```

In a second terminal:

```bash
curl localhost:8080
```

Expect `Name: dev` in the response, and a `Hostname:` line naming the pod. It is the same
application as the Kustomize lecture, just deployed from a template this time instead of patched
manifests. Stop the port-forward with Ctrl+C once you have confirmed it.

## Step 9 - Package and publish

```bash
helm package .
```

Produces `hello-chart-0.1.0.tgz`, named from the chart's own name and version.

```bash
export DOCKERHUB_USER=<your-docker-hub-username>
helm registry login registry-1.docker.io -u "$DOCKERHUB_USER"
```

At the `Password:` prompt, paste your personal access token (never the account password) and press
Enter; nothing is echoed back to the terminal. Expect `Login Succeeded`.

```bash
helm push hello-chart-0.1.0.tgz oci://registry-1.docker.io/$DOCKERHUB_USER
```

Helm only needs the namespace here; it adds the chart's own name and version, so this lands as
`hello-chart:0.1.0`. Expect a `Pushed:` line and a `Digest:` line.

Read the chart back, straight from Docker Hub, with no local folder involved:

```bash
helm show chart oci://registry-1.docker.io/$DOCKERHUB_USER/hello-chart --version 0.1.0
```

## Step 10 - Install prod straight from the registry

```bash
helm upgrade --install hello-chart oci://registry-1.docker.io/$DOCKERHUB_USER/hello-chart --version 0.1.0 -n prod --create-namespace -f values-prod.yaml
kubectl get pods -n prod
```

Expect two pods this time, both `1/1 Running`. Port-forward and curl it the same way as Step 8; the
response should read `Name: prod`.

## Cleaning up

```bash
helm uninstall hello-chart -n dev
helm uninstall hello-chart -n prod
kubectl get ns
```

`dev` and `prod` are both still listed: `--create-namespace` creates a namespace, but Helm never
deletes one on its own, even after the last release in it is gone. Remove them yourself:

```bash
kubectl delete namespace dev prod
```

Log out of the registry:

```bash
helm registry logout registry-1.docker.io
```

The published chart itself stays on Docker Hub; leaving a small public chart there costs nothing.
If you are stopping here for good, delete the cluster too:

```bash
eksctl delete cluster -f s01/eks/cluster.yaml --wait
```

## Traps

::: gotcha
**`helm lint`, `helm template`, and `helm install --dry-run=server` can all pass a chart that will
still fail, or worse, silently misbehave, once the API server actually sees it.** None of the three
performs full server-side validation. Get in the habit of running
`helm template ... | kubectl apply --dry-run=server -f -` before installing a chart you are still
editing; it is the one check in this lineup that actually asks the API server whether the rendered
objects are valid.
:::

::: gotcha
**An indentation mistake inside a `{{- toYaml ... | nindent N }}` block does not always produce
invalid YAML.** It can produce YAML that parses fine but describes something completely different,
such as a second list item where you meant a nested field. A rendered chart that "looks right" at a
glance is not proof the indentation is correct; count the spaces against the surrounding lines.
:::

::: gotcha
**`kubectl delete namespace dev prod` is a separate, deliberate step.** `helm uninstall` only ever
removes what the chart created; a namespace made with `--create-namespace` is not part of any
release and is never cleaned up automatically.
:::
