Copying the same Kubernetes manifests into three folders, one per environment, works until a fix
applied to one copy gets forgotten in the other two. Branching per environment in Git runs into the
same wall from a different angle: a change that has to land everywhere becomes repeated merges.
Kustomize solves this by keeping the manifests as plain YAML, no templating language and no
placeholders, and adding a small file next to them that names only what changes for that
environment. It ships inside `kubectl` itself, so there is nothing extra to install. This handout
walks through one small application deployed to three namespaces with three different shapes: a
single low-traffic replica in dev, two replicas in qa, and two replicas behind a load balancer in
production.

## Before you start

You need `kubectl` (which bundles Kustomize) and an AWS CLI profile that can manage EKS. Clone the
course repository and confirm the cluster built in the first section is still around; if it was
deleted, recreate it from the same file:

```bash
git clone https://github.com/abohmeed/devops-projects-kubernetes
cd devops-projects-kubernetes
eksctl create cluster -f s01/eks/cluster.yaml
```

Set the profile you use for this course, and move into the Kustomize folder for this lecture:

```bash
export AWS_PROFILE=<your-aws-profile>
cd s02/kustomize
```

## Step 1 - Confirm Kustomize is already there

```bash
kubectl version --client
```

Look for a `Kustomize Version:` line in the output. A modern `kubectl` reports it right alongside
its own client version, which is the whole point: there is no separate binary to fetch.

```bash
kubectl get nodes
```

All three nodes should read `Ready`. Everything below assumes a healthy cluster.

## Step 2 - Read the base

Open `base/deployment.yaml`, `base/service.yaml`, and `base/kustomization.yaml`.

- `deployment.yaml` deploys `traefik/whoami`, a tiny web server whose only job is to answer with
  the name of the pod that handled the request, which makes it easy to see replicas working. It is
  a completely ordinary Deployment: one container, port 80, nothing Kustomize-specific about it.
- `service.yaml` is a plain `ClusterIP` Service, also on port 80, so the pods stay reachable from
  inside the cluster.
- `kustomization.yaml` lists both files under `resources:`. That single field is what turns a
  folder of plain manifests into something Kustomize can build on.

Render it, with nothing patched yet:

```bash
kubectl kustomize base
```

You get back the same objects, just re-printed by Kustomize in its own key order (alphabetical,
and the Service printed before the Deployment). Do not compare it to the source files line by
line; compare what each object actually says.

## Step 3 - The qa overlay, and a patch that fails on purpose

Open `overlays/qa/kustomization.yaml`. It sets `namespace: qa`, pulls in the base through
`resources: [../../base]`, and lists one patch: `deployment-patch.yaml`. (Older Kustomize files
call that field `bases:`; it is deprecated, so every overlay here uses `resources:` for both the
base and the patch list.)

Create `overlays/qa/deployment-patch.yaml` with a deliberate typo in the name, to see what happens
when a patch does not match anything:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: helo
```

Preview the overlay:

```bash
kubectl kustomize overlays/qa
```

This is the real failure the lecture walks through, with the exact error Kustomize returns:

```
error: no resource matches strategic merge patch "Deployment.v1.apps/helo.[noNs]": no matches for Id Deployment.v1.apps/helo.[noNs]; failed to find unique target for patch Deployment.v1.apps/helo.[noNs]
```

Kustomize matches a strategic-merge patch to its target using kind and name together. Get either
one wrong and there is nothing to patch, so the whole build fails loudly. Fix the typo and add a
replica count:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello
spec:
  replicas: 2
```

Preview again; it should render cleanly with `namespace: qa` and `replicas: 2`. Then apply it:

```bash
kubectl create namespace qa
kubectl apply -k overlays/qa
kubectl get pods -n qa
```

Expect two `hello` pods, both `Running`.

## Step 4 - The dev overlay: an inline patch and an image override

Open `overlays/dev/kustomization.yaml`. Instead of a separate patch file, the patch is written
directly inside `kustomization.yaml`, under a `target:` that names the Deployment by kind and name,
and a JSON-Patch style `patch:` block that adds `args: ["--verbose"]` to the container. An
`images:` field also sets `newTag: v1.12.0`, so dev runs a newer build of `whoami` than qa or
production.

```bash
kubectl kustomize overlays/dev
kubectl create namespace dev
kubectl apply -k overlays/dev
```

Reach the app and read its logs:

```bash
kubectl port-forward -n dev svc/hello 8080:80
```

In a second terminal:

```bash
curl localhost:8080
kubectl logs -n dev deploy/hello
```

`curl` returns a `Hostname:` line naming the pod. The log line only shows up because of the
`--verbose` flag: with it, `whoami` prints each request twice; without it (as in qa), it prints
only the startup line. That difference is the proof the patch actually took effect.

::: gotcha
**An inline patch with a `target:` that matches nothing does not fail.** Unlike a strategic-merge
patch file (Step 3), a `target:`-based patch that names a kind or name Kustomize cannot find in the
base renders successfully, exit code 0, with no error and no sign anything was supposed to change.
There is no message telling you the patch never applied. If a change you expected in an overlay's
output is simply missing, check the `target:` block for a typo before assuming the patch itself is
wrong.
:::

Stop the port-forward with Ctrl+C once you are done.

## Step 5 - The prod overlay: native fields and a load balancer

Open `overlays/prod/kustomization.yaml`. Production sets `replicas:` directly, since replica count
is a field Kustomize understands natively and needs no patch file for. What it does patch is the
Service, through `service-patch.yaml`:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: hello
  annotations:
    service.beta.kubernetes.io/aws-load-balancer-type: nlb
spec:
  type: LoadBalancer
```

This cluster has no AWS Load Balancer Controller installed, so the cloud provider's own built-in
integration is what creates the load balancer, and it defaults to a Classic type unless told
otherwise. The annotation `service.beta.kubernetes.io/aws-load-balancer-type: nlb` tells that
built-in integration to provision a Network Load Balancer (NLB) instead. A separately installed AWS
Load Balancer Controller is the more common way to get an NLB in a real production cluster, but the
annotation alone is enough here because it only reads that one field.

```bash
kubectl kustomize overlays/prod
kubectl create namespace prod
kubectl apply -k overlays/prod
```

Check the Service:

```bash
kubectl get svc -n prod hello
```

The `EXTERNAL-IP` column starts as a hostname right away, but the load balancer is not usable the
moment it appears. Expect it to take a few minutes before the hostname resolves over DNS and starts
returning real responses; retry every 15 to 30 seconds rather than assuming something is broken.
Once it answers, curl it a few times:

```bash
curl http://<the hostname from EXTERNAL-IP>/
```

Because there are two pods, repeated requests should return two different `Hostname:` values. The
Service listens on port 80; do not add a port number to the hostname.

## Step 6 - One label, applied to every environment

Add a `labels:` field to `base/kustomization.yaml`, not to any overlay:

```yaml
labels:
  - pairs:
      team: devops
```

Preview qa and production again without touching either overlay file:

```bash
kubectl kustomize overlays/qa
kubectl kustomize overlays/prod
```

Both should now carry `team: devops` under `metadata.labels` on the Service and the Deployment.
The Deployment's `matchLabels` and its pod template labels are left alone: a selector cannot be
changed once a Deployment exists, so `labels:` does not touch it, only the surrounding object
metadata.

## Cleaning up

Remove the workloads in each namespace, then the namespaces themselves:

```bash
kubectl delete -k overlays/prod
kubectl delete -k overlays/dev
kubectl delete -k overlays/qa
kubectl delete namespace dev qa prod
```

Confirm nothing billable is left behind:

```bash
aws elbv2 describe-load-balancers --region us-east-1 --query 'LoadBalancers[].LoadBalancerName'
```

Expect an empty list, `[]`. If it still lists a name, the load balancer is mid-deletion; wait a
short while and check again. While the cluster and any load balancer are running they bill by the
hour whether or not you are actively using them, so if you are stopping for the day, delete the
cluster too:

```bash
eksctl delete cluster -f s01/eks/cluster.yaml --wait
```

## Traps

::: gotcha
**A strategic-merge patch that names the wrong kind or name fails the whole build.** The error
names the object it could not find (`no matches for Id ...`); fix the `name:` or `kind:` in the
patch file to match an object that actually exists in the base.
:::

::: gotcha
**An inline `target:`-based patch that matches nothing renders silently and changes nothing.** See
Step 4. Always check the rendered output actually contains the change you expected, not just that
the command exited successfully.
:::

::: gotcha
**The load balancer's hostname appears in seconds, but does not answer for minutes.** DNS
propagation and health checks both take time. A `curl` that fails or hangs against a brand-new
hostname is expected for the first few minutes; it is not a sign the Service or annotation is
wrong.
:::
