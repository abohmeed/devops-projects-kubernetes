Applying a folder of plain Kubernetes manifests with `kubectl apply` is enough for one application in
one environment. It stops being enough the moment there are several environments to keep in sync,
software somebody else maintains that needs installing and upgrading safely, or an application that
keeps needing attention long after it first goes live. This section is a tour of four different
answers to that growing problem, building on each other rather than replacing one another. This
handout is a map of where the section is going, not a lesson on its own; read it once now, and come
back to it whenever you want to see how a later lecture fits against an earlier one.

## The route through this section

| Stop | What it adds |
|---|---|
| Kustomize | One base set of manifests, with every environment (dev, QA, production) described only by what is different from that base. No templating language, and nothing extra to install. |
| Helm, installing and publishing | Two lectures: first, installing someone else's published chart, upgrading it, and rolling it back; then building a chart of your own and pushing it to a registry so it can be installed the same way. |
| Blue and green with Helm | Running two full copies of an application side by side and switching every user between them with a single command, with the same command able to switch traffic straight back. |
| Operators | What an operator actually is, the tools available for building one, a maintained operator that keeps a MySQL database running and heals itself, and an operator you build yourself for a small Nginx site. |
| Wrap-up | A closing lecture on which of these approaches to reach for, and when, since most of them work together rather than compete. |

## The idea underneath all four

Getting an application deployed the first time is only half of running it in Kubernetes. The other
half is everything that happens afterward: a configuration value changes, a new version needs
rolling out safely, a database needs backing up, or part of the application fails and something has
to notice and react. The first half is usually called day one, and the second is day two. Kustomize
and Helm are strong at day one. Helm can also handle upgrades and rollbacks well, but only at the
moment someone chooses to run it. The operators covered later in this section close that gap, by
watching an application continuously instead of only when a command is typed.

## The cluster this section shares

Every lab and demo in this section runs against the same EKS cluster, the one built earlier in the
course. If that cluster has since been deleted, bring it back from the same file before starting any
lecture in this section:

```bash
eksctl create cluster -f s01/eks/cluster.yaml
```

An EKS cluster and its worker nodes bill by the hour from the moment they exist, whether or not a lab
is actively running against them, so it is worth keeping that command handy rather than leaving the
cluster up between study sessions.
