Writing and patching manifests by hand, the way the previous lecture did, does not scale once you
need someone else's application: a database, a monitoring stack, a web app you did not write and do
not want to maintain a growing pile of YAML for. Helm is the package manager for Kubernetes. A
chart is a package: a set of templated manifests plus a default set of values. A release is one
installed copy of a chart, under its own name; the same chart can run as many separate releases as
you like. Every change made to a release is recorded as a new revision, which is what makes rolling
back possible later. This handout installs Helm itself, finds and installs a small application from
a public chart, then upgrades, rolls back, and removes it.

## Before you start

You need a Linux shell with `curl`, `tar`, and `sudo`, on the same machine as the EKS cluster built
earlier. If the cluster was deleted, recreate it from the course repository:

```bash
eksctl create cluster -f s01/eks/cluster.yaml
```

Set the AWS profile you use for this course:

```bash
export AWS_PROFILE=<your-aws-profile>
```

## Step 1 - Install Helm from the official tarball

Move to a scratch directory and download the release along with its checksum file:

```bash
cd /tmp
curl -fsSLO https://get.helm.sh/helm-v4.3.0-linux-amd64.tar.gz
curl -fsSLO https://get.helm.sh/helm-v4.3.0-linux-amd64.tar.gz.sha256sum
```

Verify the download before trusting it:

```bash
sha256sum -c helm-v4.3.0-linux-amd64.tar.gz.sha256sum
```

Expect exactly:

```
helm-v4.3.0-linux-amd64.tar.gz: OK
```

Extract and install the binary, then clean up:

```bash
tar -xzf helm-v4.3.0-linux-amd64.tar.gz
sudo install -m 0755 linux-amd64/helm /usr/local/bin/helm
rm -rf linux-amd64 helm-v4.3.0-linux-amd64.tar.gz*
```

Confirm the version:

```bash
helm version
```

You are working with Helm 4, its current major version; older tutorials and blog posts written for
Helm 3 sometimes use flags that no longer exist or behave differently.

## Step 2 - Confirm the cluster

```bash
kubectl get nodes
```

All three nodes should read `Ready`. Helm talks to whatever cluster your kubeconfig points at, the
same as `kubectl`, so there is no separate configuration step to connect the two.

## Step 3 - Find a chart on Artifact Hub

Open [Artifact Hub](https://artifacthub.io) and search for `podinfo`. You will see more than one
result; pick the package published under the repository named `podinfo` (the project's own), not a
mirror maintained by someone else. Podinfo is a small, maintained web application whose entire job
is to report its own configuration back to you, which makes it easy to see whether a value you set
actually took effect.

Before installing anything, open its default values and read them. You should see fields like
`replicaCount`, `ui.message`, `ui.color`, and `service.type` (set to `ClusterIP` by default).
Reading a chart's defaults first is how you know what you are allowed to change and what you are
accepting as-is.

Charts are distributed one of two ways: through a classic chart repository, which has to be added
to Helm before you can install from it, or through an OCI registry, the same kind of registry that
stores container images, which needs no adding at all: you give Helm an `oci://` address and a
version directly. This handout uses the OCI form.

## Step 4 - Install it

```bash
helm install podinfo oci://ghcr.io/stefanprodan/charts/podinfo --version 6.15.0
```

Expect Helm to report `Pulled:` with a digest, then a summary block ending in a `NOTES:` section
with instructions for reaching the app. Pinning `--version` is deliberate: leaving it off installs
whatever build happens to be newest on the day you run the command, which is not something you want
in a script you intend to run again later.

```bash
helm list
```

Shows one release at `REVISION 1`, status `deployed`.

```bash
kubectl get deploy,svc
```

Shows exactly what the chart promised: one Deployment and a `ClusterIP` Service named `podinfo`,
listening on ports `9898` (HTTP) and `9999` (gRPC). You will also see `service/kubernetes`, the
cluster's own internal Service; it is not part of what you just installed.

## Step 5 - Reach it

```bash
kubectl port-forward svc/podinfo 9898:9898 &
curl localhost:9898
```

The response is JSON, including a `message`, a `color` of `"#34577c"`, and a `version` of
`"6.15.0"`. This is podinfo's own default configuration, unmodified.

## Step 6 - Why a second install fails

Say you want two replicas and your own message instead of the default one. Running `helm install`
again is the natural first instinct:

```bash
helm install podinfo oci://ghcr.io/stefanprodan/charts/podinfo --version 6.15.0 --set replicaCount=2
```

This is the real failure the lecture is built around. Helm refuses, with a message that says
exactly why:

```
level=ERROR msg="release name check failed" error="cannot reuse a name that is still in use"
Error: INSTALLATION FAILED: release name check failed: cannot reuse a name that is still in use
```

`helm install` only ever creates a brand-new release, and a release name has to be unique inside
its namespace. Changing an existing release is the job of a different command, `helm upgrade`.

## Step 7 - Upgrade with your own values

`helm upgrade --install` does both jobs with one command: it installs a release the first time,
and upgrades that same release on every run after, which is why real pipelines almost always use it
instead of `helm install`, even for a first deploy.

```bash
helm upgrade --install podinfo oci://ghcr.io/stefanprodan/charts/podinfo --version 6.15.0 --set replicaCount=2 --set ui.message="Hello from Helm" --set ui.color="#2e7d32"
```

The dot in `ui.color` addresses the `color` field nested under `ui` in the chart's values structure.
Wait a few seconds for the new pods to become Ready, then:

```bash
kubectl get pods
```

Should show two `podinfo` pods, `Running`.

## Step 8 - See the new values, restart the forward

An upgrade replaces the old pods, so the port-forward from Step 5 is now pointing at a pod that no
longer exists. Kill it and start a fresh one:

```bash
kill %1
```

Press Enter once at the empty prompt so the shell actually reports the job as terminated before you
start a new one; skipping this step is a common cause of `address already in use` errors on the
next line.

```bash
kubectl port-forward svc/podinfo 9898:9898 &
curl localhost:9898
```

The JSON now shows your message and color. An upgrade always starts fresh from the chart's
defaults, plus whatever you pass on that specific command; it does not remember `--set` values from
an earlier revision unless you pass them again. That is why you should pass every value, every
time, in a script or pipeline.

```bash
helm get values podinfo
```

Shows exactly what you supplied for the current revision, `replicaCount: 2` and the two `ui` values.

## Step 9 - History and rollback

```bash
helm history podinfo
```

Lists two revisions: the first `superseded`, the second `deployed`.

```bash
helm rollback podinfo 1
```

Rolling back needs no chart address; Helm already stored everything it applied for that revision.
Cycle the port-forward again the same way as Step 8:

```bash
kill %1
kubectl port-forward svc/podinfo 9898:9898 &
kubectl get pods
curl localhost:9898
```

You should see one pod again, and the JSON reverts to the default color, `"#34577c"`, and to
podinfo's own built-in greeting message. The chart's `ui.message` default is an empty string, and
podinfo treats an empty message as "use my own greeting" rather than showing nothing, so do not
expect a blank `message` field after a rollback to the original install.

```bash
kill %1
helm history podinfo
```

Now shows three revisions, not one. Rolling back does not erase history, it adds to it: the newest
revision reads `Rollback to 1`.

## Cleaning up

```bash
helm uninstall podinfo
helm list
kubectl get all
```

`helm list` comes back empty, and `kubectl get all` shows no podinfo objects left. Podinfo never
creates a persistent volume claim, so there is nothing else to remove by hand for this particular
chart; other charts may leave a claim behind on purpose, which is worth checking with
`kubectl get pvc` after any uninstall.

If you are stopping here, delete the cluster too, since it bills by the hour regardless of whether
anything is running on it:

```bash
eksctl delete cluster -f s01/eks/cluster.yaml --wait
```

## Traps

::: gotcha
**`bash: kill: %1: no such job`.** This happens when Enter was never pressed on the empty prompt
after a previous `kill %1`, so the job was never actually freed. Run `jobs` to see the real job
number, `kill` that number instead, press Enter once, and only then start the next port-forward.
:::

::: gotcha
**`Unable to listen on port 9898: address already in use`.** The previous port-forward is still
running. Same fix as above: find and kill the actual job, confirm it terminated, then retry.
:::

::: gotcha
**A second `helm install` on an existing release name always fails, and `helm upgrade` on a
release name that does not exist yet always fails too.** `install` and `upgrade` are not
interchangeable on their own; `upgrade --install` is the one command that works either way, which
is why it is worth using from the very first deploy.
:::
