This section deployed the same kind of application to Kubernetes several different ways: with
Kustomize, with Helm, and with operators. None of them is simply the newest or the most advanced;
each one answers a different question, and the real skill is recognizing which question is actually
in front of you. This handout is a short reference for making that call, plus a look at what comes
next.

## A quick reference

| Tool | Reach for it when | What it does not do |
|---|---|---|
| **Kustomize** | It is your own application, and environments differ only a little: a replica count, an image tag, whether a Service is exposed externally. | No packaging or versioning story for handing the application to somebody else. |
| **Helm** | You are installing software somebody else maintains, or you want to hand your own application to another team as one versioned, installable chart. | Only acts the moment you run it; nothing watches the application between one `helm upgrade` and the next. |
| **An operator** | The application needs ongoing care after it is deployed: configuration drift, failover, backups and restores. | Only exists if someone has written one, or you write one yourself. |

## Why these tools work together, not against each other

Kustomize stays plain YAML with no templating language at all, and it ships inside `kubectl` itself,
so there is nothing extra to install when the only difference between environments is small. Helm
earns its place once you are thinking in packages: every install becomes a numbered revision, so
rolling one back is a single command, which is exactly the mechanism this section's blue-and-green
lecture used to switch every user between two versions at once and back again just as fast.

An operator matters once an application needs looking after long after the moment it was deployed.
The clearest example in this section was the MySQL operator: it promoted a new primary the instant
its old one was deleted on purpose, and later restored a whole table's worth of data from a backup
sitting in S3. Worth noticing directly: that operator was itself installed with Helm. These tools are
not rivals competing for the same job; Helm got the operator onto the cluster, and the operator then
took over a kind of day-two work Helm was never designed to do on its own.

## When no ready-made operator exists

Sometimes the software that needs an operator is your own, and nobody else has already written one
for it. This section covered both ends of that choice. **kro** fits when the operator is really just
a set of Kubernetes resources that can be fully described in YAML, as with the small Nginx site built
earlier in this section: no Go, no build step, and a real reconcile loop running within minutes.
**kubebuilder** fits once the logic genuinely needs code: calling an external API, driving a
multi-step failover, or doing anything that cannot be expressed as "create or update these resources
to match this schema." One caveat worth remembering either way: kro is still an alpha-stage project,
so treat its API as something that can still change, not as a long-term guarantee.
