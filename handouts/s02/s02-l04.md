A normal `helm upgrade` replaces a Deployment's pods in place, which means undoing a bad rollout
means running another rollout and waiting for it to finish. Blue/green deployment takes a different
approach: keep two full copies of the application running side by side, called blue and green, and
switch every user between them by flipping a single label, instead of restarting or replacing any
pods. This handout builds that chart, switches traffic between two versions of an application, and
switches it back, all with the same one-line command.

## Before you start

You need Helm 4 (the earlier lecture's handout has the installation steps if you skipped it) and
the EKS cluster from this section still running. Recreate it if it is gone:

```bash
eksctl create cluster -f s01/eks/cluster.yaml
```

```bash
export AWS_PROFILE=<your-aws-profile>
mkdir -p s02/blue-green && cd s02/blue-green
```

## The idea, in short

Blue and green are two full copies of the same application. Blue serves live users; green is a new
version, already tested, waiting to take traffic. Once green is confirmed ready, every request is
switched to it at once, and rolling back moves every request straight back to blue just as fast.
The trade-off is cost: both copies run, and both are billed, for as long as the switch might need to
go either way. This is different from a canary rollout, which shifts a small share of traffic at a
time, and different again from A/B testing, which routes users to a variant based on some attribute
of the request; blue/green always sends everyone to exactly one version.

The mechanism behind the switch is simple: two Deployments, each carrying its own `version` label
(`blue` or `green`), sitting behind one Service. A Service sends traffic to whichever Ready pods
match its label selector, so changing the value of one label in that selector moves every request
between the two Deployments instantly, with no pod restarted and no rollout to wait for.

## Step 1 - Scaffold the chart

```bash
helm create blue-green
```

Open `blue-green/templates/_helpers.tpl` and note the generated helper names,
`blue-green.fullname` and `blue-green.selectorLabels`. `helm create` names every helper after the
chart itself, so every template inside this chart has to call its own chart's helpers; a template
copied from a chart with a different name calling that other chart's helpers will fail to render.

## Step 2 - Configure `values.yaml`

Point the image at a small application that reports its own version and message, so you can
actually see which copy answered each request:

```yaml
replicaCount: 2
image:
  repository: ghcr.io/stefanprodan/podinfo
```

Change the Service to a `LoadBalancer` so it is reachable from outside the cluster (port stays 80):

```yaml
service:
  type: LoadBalancer
  port: 80
```

Add the blue/green configuration at the end of the file:

```yaml
activeVersion: blue
blue:
  tag: "6.14.1"
  color: "#1f5fbf"
green:
  tag: "6.15.0"
  color: "#2e8b57"
```

`activeVersion` is the single value that decides which color is live.

## Step 3 - The blue Deployment

Rename `templates/deployment.yaml` to `templates/blue-deployment.yaml`. At the very top of the
file, declare which slot this template is for:

```
{{- $slot := "blue" }}
```

Suffix the Deployment's own name with that slot, so blue and green never collide:

```
metadata:
  name: {{ include "blue-green.fullname" . }}-{{ $slot }}
```

Add `version: {{ $slot }}` to **both** places a label lives: the Deployment's `matchLabels` in its
selector, and the pod template's own labels. Both are required, because a Deployment's selector and
its pod template labels have to agree, or Kubernetes refuses to create it.

Point the image and an environment block at the active slot's values, using `index` to look up a
value by a name held in a variable:

```
          image: "{{ .Values.image.repository }}:{{ (index .Values $slot).tag }}"
          ...
          env:
            - name: PODINFO_UI_COLOR
              value: {{ (index .Values $slot).color | quote }}
            - name: PODINFO_UI_MESSAGE
              value: {{ $slot | quote }}
```

Set the container port to `9898`, the port podinfo actually listens on.

## Step 4 - Copy it to green, changing exactly one word

Copy `blue-deployment.yaml` to `green-deployment.yaml`, then change only the very first line from
`"blue"` to `"green"`. Every other line in the file, including every `{{ include "blue-green...` call,
stays untouched. Do **not** use a find-and-replace across the whole file: doing so would also rename
the calls to `blue-green.fullname` and the other shared helpers, which are the chart's own name and
must not change, and the chart would fail to render, the same mistake as copying a helper from a
chart with a different name.

## Step 5 - The Service selector, with a guard

In `templates/service.yaml`, add the active version to the selector:

```
  selector:
    {{- include "blue-green.selectorLabels" . | nindent 4 }}
    version: {{ .Values.activeVersion }}
```

At the very top of the same file, add a guard that stops the chart from rendering at all if
`activeVersion` is ever anything other than `blue` or `green`:

```
{{- if not (has .Values.activeVersion (list "blue" "green")) }}
{{- fail "activeVersion must be blue or green" }}
{{- end }}
```

Without this guard, a typo such as `gren` would silently match zero pods, and every request to the
Service would fail with no explanation pointing at the actual cause. The Service listens on port 80
and forwards to `targetPort: http`, which both Deployments map to container port 9898.

## Step 6 - Check it before installing

```bash
helm lint ./blue-green
helm template blue-green ./blue-green --show-only templates/service.yaml
```

Confirm the rendered Service shows `type: LoadBalancer` and a selector ending in
`version: blue`, since `activeVersion` defaults to blue.

## Step 7 - Install both copies at once

```bash
helm install blue-green ./blue-green
```

Wait about 15-20 seconds for every pod to become Ready, then:

```bash
kubectl get deploy,pods -l app.kubernetes.io/instance=blue-green -L version
```

Expect four pods total, two per color, all `1/1 Running`. The `VERSION` column on the pod rows
shows `blue` or `green`; the Deployments' own `VERSION` column is empty, since the label lives on
the pods, not the Deployment objects themselves.

## Step 8 - Reach it, and start watching it live

```bash
kubectl get svc blue-green
```

Because this cluster has no separate load balancer controller installed, the built-in cloud
integration provisions a Classic Load Balancer. Give it a few minutes before it actually answers
requests; the hostname appears almost immediately, but DNS and health checks both take time to
settle. Once it does:

```bash
export LB=$(kubectl get svc blue-green -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
while true; do curl -s http://$LB/ | grep -E '"(version|message)"'; sleep 1; done
```

Leave that loop running in its own terminal window; it prints `"version": "6.14.1"` and `"message":
"blue"` roughly once a second. Open a second terminal for every command from here on.

## Step 9 - Confirm green is ready, then flip

Before switching traffic, confirm the green copy is actually healthy:

```bash
kubectl rollout status deployment/blue-green-green
```

Then flip every request to green with one command:

```bash
helm upgrade blue-green ./blue-green --set activeVersion=green
```

Watch the loop from Step 8: within a few seconds it switches to `"version": "6.15.0"` and
`"message": "green"`, with no failed request in between. No pod is restarted or replaced by this
command; only the Service's selector changes, which is the entire point of the pattern.

```bash
kubectl describe svc blue-green
```

Point at the `Selector:` line; it now ends in `version=green`.

## Step 10 - The typo is refused, on purpose

This is the real failure the guard from Step 5 exists to catch:

```bash
helm upgrade blue-green ./blue-green --set activeVersion=gren
```

Expect exactly:

```
Error: UPGRADE FAILED: execution error at (blue-green/templates/service.yaml:2:4): activeVersion must be blue or green
```

The upgrade never applies, the release stays exactly as it was, and the loop keeps answering from
green without interruption. Without the guard added in Step 5, this same typo would have rendered
successfully and quietly broken every request instead.

## Step 11 - Flip back, and read the history

```bash
helm upgrade blue-green ./blue-green --set activeVersion=blue
```

The loop returns to `"version": "6.14.1"` / `"message": "blue"` within a few seconds.

```bash
helm history blue-green
```

Expect three revisions: the install, the flip to green, and the flip back to blue. The rejected
`gren` attempt from Step 10 never appears here at all, since it failed while Helm was still
rendering the templates, before anything was ever recorded as a revision. From here, either
`--set activeVersion=blue` or `helm rollback blue-green` (moving back exactly one revision) gets you
to the same result; running two full copies at once is the ongoing cost of keeping either option
available.

## Cleaning up

Stop the loop from Step 8 with Ctrl+C, then remove the release:

```bash
helm uninstall blue-green
```

```bash
kubectl get svc
```

The Service can take up to about 30 seconds to disappear from this list, since Kubernetes waits for
the underlying load balancer to actually finish being deleted before removing the Service object
itself. Once it is gone, only the cluster's own internal Service should remain. If you are stopping
here, delete the cluster too, since this section's four lectures are the last to use it and nothing
else in this cluster needs to stay running:

```bash
eksctl delete cluster -f s01/eks/cluster.yaml --wait
```

## Traps

::: gotcha
**`function "blue-green.fullname" not defined` (or the same error for `.selectorLabels`).** A
find-and-replace across the copied Deployment file renamed a helper call it should not have
touched. Undo the change and retype only the one line the lecture actually changes (Step 4).
:::

::: gotcha
**`spec.selector` does not match template labels.** The `version:` label was added to only one of
the two required places. Add it to both the Deployment's `matchLabels` and its pod template labels,
save, and reinstall.
:::

::: gotcha
**The watch loop shows nothing at all.** Either the load balancer is not answering yet (see Step 8)
or `$LB` was never exported in the terminal running the loop; environment variables do not carry
over between terminal windows.
:::

::: gotcha
**A mistyped `--set activeVersion=...` value is refused outright, rather than silently doing
nothing.** That refusal is the guard from Step 5 working as intended; without it, the same typo
would render a Service selector matching no pods and fail every request with no clue why.
:::
