Helm installs an Nginx site without any trouble on day one. The trouble starts on day two: the page's
text changes and the pods need restarting, or someone scales the Deployment by hand and nothing
notices it has drifted from what the chart describes. This handout builds a small operator of your
own for exactly that Nginx site, using kro (the Kube Resource Orchestrator), which needs no Go code,
no build step, and no toolchain beyond Helm and `kubectl` themselves.

## Before you start

You need the EKS cluster from earlier in this course still running, and nothing else:

```bash
eksctl create cluster -f s01/eks/cluster.yaml
export AWS_PROFILE=<your-aws-profile>
```

## Step 1 - Install kro

```bash
helm install kro oci://registry.k8s.io/kro/charts/kro --namespace kro-system --create-namespace --version=0.9.4 --wait
kubectl get pods -n kro-system
```

kro is still at an alpha stage of its own development, which is exactly why its API group is
`kro.run/v1alpha1` and why the version is pinned explicitly here rather than left to float. Expect a
single controller pod, `1/1 Running`. Notice there is no Go compiler and no build step anywhere in
this install; Helm and `kubectl` are the entire toolchain kro asks for.

## Step 2 - Define the schema

Create `rgd.yaml` and start with the API kro will generate on your behalf:

```yaml
apiVersion: kro.run/v1alpha1
kind: ResourceGraphDefinition
metadata:
  name: nginxsite
spec:
  schema:
    apiVersion: v1alpha1
    kind: NginxSite
    spec:
      replicas: integer | default=2
      message: string | default="Hello from kro"
    status:
      availableReplicas: ${deployment.status.availableReplicas}
  resources:
```

`kind: NginxSite` under `schema` is the custom resource users of this operator will actually create.
It exposes exactly two fields, `replicas` and `message`, and nothing else; whoever creates a
`NginxSite` object never sees or needs to know about the ConfigMap, Deployment, or Service underneath
it. Every `${...}` expression here is not plain text substitution: kro checks each one against this
schema the moment the file is applied, which is a real advantage over a plain templating tool that
only discovers a bad reference once it tries to render.

## Step 3 - The first resource: the page

Add this under `resources:`:

```yaml
  - id: page
    template:
      apiVersion: v1
      kind: ConfigMap
      metadata:
        name: ${schema.metadata.name}-page
      data:
        index.html: ${schema.spec.message}
```

This ConfigMap holds the page text as a single file, named from whatever the user calls their
`NginxSite` object.

## Step 4 - The second resource: the Deployment

Add this next, directly under the `page` resource:

```yaml
  - id: deployment
    template:
      apiVersion: apps/v1
      kind: Deployment
      metadata:
        name: ${schema.metadata.name}
      spec:
        replicas: ${schema.spec.replicas}
        selector:
          matchLabels:
            app: ${schema.metadata.name}
        template:
          metadata:
            labels:
              app: ${schema.metadata.name}
            annotations:
              site/message: ${schema.spec.message}   # a config change rolls the pods
          spec:
            containers:
            - name: nginx
              image: nginx:1.30.5-alpine
              ports:
              - containerPort: 80
              volumeMounts:
              - name: page
                mountPath: /usr/share/nginx/html
            volumes:
            - name: page
              configMap:
                name: ${page.metadata.name}
```

Two details here matter more than they look. First, `name: ${page.metadata.name}` is a direct
reference to the ConfigMap defined in Step 3; kro reads that reference and learns on its own that the
page has to exist before the Deployment does, with no separate ordering list to maintain. Second, a
ConfigMap mounted as a volume eventually refreshes inside a running pod on its own timing, but the
pod itself is never restarted by that alone. The `site/message` annotation on the pod template exists
specifically to force a rollout on every message change, since changing anything in a pod template
always triggers one.

## Step 5 - The third resource: the Service

Finish the file with:

```yaml
  - id: service
    template:
      apiVersion: v1
      kind: Service
      metadata:
        name: ${schema.metadata.name}
      spec:
        selector:
          app: ${schema.metadata.name}
        ports:
        - port: 80
```

This Service defaults to `ClusterIP`, which is enough for testing from inside the cluster; there is
no load balancer to wait on or pay for here.

## Step 6 - Apply the definition

```bash
kubectl apply -f rgd.yaml
kubectl get rgd -o wide
kubectl get crd nginxsites.kro.run
```

The `-o wide` form matters: a plain `kubectl get rgd` shows the definition is `Active`, but it does
not list the resources inside it at all. Add `-o wide` and a `TOPOLOGICALORDER` column appears,
listing `["page","deployment","service"]`, which is the actual build order kro worked out from the
references in Steps 3 and 4. The CustomResourceDefinition for `NginxSite` exists within seconds of
the apply, generated entirely from the schema you wrote.

## Step 7 - Day one: create an instance

```yaml
# web.yaml
apiVersion: kro.run/v1alpha1
kind: NginxSite
metadata:
  name: web
spec:
  replicas: 2
  message: "Hello from version 1"
```

```bash
kubectl apply -f web.yaml
kubectl get nginxsite web
kubectl get deploy,configmap,svc
```

Expect a Deployment, a ConfigMap, and a Service, named after `web` and `web-page`, all created from
that one small file. Prove the page is actually being served:

```bash
kubectl run curl --rm -i --restart=Never --image=curlimages/curl:8.22.0 -- curl -s http://web
```

Look for `Hello from version 1` in the output.

## Step 8 - A bad value, rejected before kro ever sees it

Edit `web.yaml` and set `replicas` to the word `four` instead of a number, then apply it:

```bash
kubectl apply -f web.yaml
```

This fails, and the error is real and worth reading:

```
The NginxSite "web" is invalid: spec.replicas: Invalid value: "string": spec.replicas in body must be of type integer: "string"
```

This rejection comes from the Kubernetes API server's own validation of the CRD kro generated in Step
6; kro's controller never even sees the request. Fix the value back to `4` and save the file, but do
not apply it yet.

## Step 9 - Day two: change the message

Edit the message to `"Hello from version 2"`, then:

```bash
kubectl apply -f web.yaml
kubectl rollout status deployment/web
kubectl get rs
```

The rollout completes in a few seconds, and `kubectl get rs` shows a brand-new ReplicaSet at `4/4/4`
alongside the previous one scaled to zero. Confirm the new text is actually being served:

```bash
kubectl run curl --rm -i --restart=Never --image=curlimages/curl:8.22.0 -- curl -s http://web
kubectl get nginxsite web -o yaml
```

The status block on the object itself now reports `availableReplicas: 4` and a `Ready` condition of
`"True"`, since the controller writes back exactly what it observes, just as any reconcile loop does.

## Step 10 - Drift: a manual scale gets corrected

```bash
kubectl scale deployment web --replicas=1
kubectl get deployment web
```

A plain Deployment with nothing watching it would stay at one replica indefinitely. Here, the
`NginxSite` object still says four, so kro's controller notices the difference on its next reconcile
and puts the Deployment straight back to `4/4`, almost immediately.

## Step 11 - Drift: a deleted ConfigMap gets corrected

```bash
kubectl delete configmap web-page
kubectl get configmap web-page
```

The ConfigMap comes back within a second or two, with a fresh creation timestamp. This is exactly the
kind of unplanned change a human operator would otherwise have to notice and fix by hand. One real
limit is worth naming here too: kro can reconcile any resource it can describe declaratively, but it
cannot call an external API, run a multi-step failover, or take a backup. Reaching for a coded
operator, such as the kubebuilder one from an earlier lecture, is still the right move once a task
needs logic like that.

## Cleaning up

```bash
kubectl delete nginxsite web
kubectl get deploy,configmap,svc
```

Deleting the `NginxSite` object removes its Deployment, ConfigMap, and Service together, since kro
owns all three as its children.

```bash
kubectl delete rgd nginxsite
helm uninstall kro -n kro-system
```

::: gotcha
**`helm uninstall kro` leaves three CustomResourceDefinitions behind, not zero.** They are
`nginxsites.kro.run` (generated from your own schema), `resourcegraphdefinitions.kro.run`, and
`graphrevisions.internal.kro.run`, an internal kind kro uses to track revisions of a definition.
Removing the Helm release does not remove any of them on its own; they have to be deleted explicitly:
:::

```bash
kubectl delete crd nginxsites.kro.run resourcegraphdefinitions.kro.run graphrevisions.internal.kro.run
kubectl delete namespace kro-system
```

If this is the last lecture of this section you are working through, delete the cluster too, since
nothing later in this handout series needs it kept running:

```bash
eksctl delete cluster -f s01/eks/cluster.yaml --wait
```

Nothing in this handout creates anything outside the cluster itself, so the only ongoing cost while
you work through it is the EKS cluster's own control plane and worker nodes, which bill by the hour
regardless of whether kro is installed on top of them.

## Traps

::: gotcha
**`kubectl apply -f rgd.yaml` fails, or the definition stays `Inactive`.** This almost always means a
typo inside one of the `${...}` expressions, since kro type-checks every one of them against the
schema. Read `kubectl get rgd nginxsite -o yaml` and look at `status.conditions` for the exact
complaint, fix the expression, and apply again.
:::

::: gotcha
**`kubectl apply -f web.yaml` fails with `resource mapping not found` for kind `NginxSite`.** The
CustomResourceDefinition from Step 6 has not finished registering yet. Wait a few seconds and apply
again.
:::
