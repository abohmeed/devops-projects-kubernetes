Running MySQL inside Kubernetes was never the hard part; a StatefulSet already does that on its own.
The hard part is everything that comes after: noticing when the primary database instance dies,
taking backups on a schedule, and knowing how to restore one correctly. This handout installs the
Percona Operator for MySQL, lets it build a three-member replicated cluster from one small
configuration file, breaks that cluster on purpose by killing its primary, and finally backs it up to
S3, drops a table by mistake, and restores it.

## Before you start

You need the EKS cluster from earlier in this course, with the EBS CSI driver and Pod Identity agent
already added to it as add-ons (covered in an earlier section's handout). If either is missing,
recreate the cluster and add both:

```bash
eksctl create cluster -f s01/eks/cluster.yaml
```

```yaml
# addons.yaml
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig

metadata:
  name: <your-cluster-name>
  region: <your-cluster-region>

addons:
  - name: eks-pod-identity-agent
    version: v1.3.10-eksbuild.3
  - name: aws-ebs-csi-driver
    version: v1.66.0-eksbuild.1
    useDefaultPodIdentityAssociations: true
    configurationValues: |-
      defaultStorageClass:
        enabled: true
```

```bash
eksctl create addon -f addons.yaml
kubectl get storageclass
```

Look for `ebs-csi-default-sc (default)` in the output; without a default StorageClass, every MySQL
pod's storage claim in this handout would sit `Pending` forever. This database cluster needs its own
S3 bucket to back up to, and an IAM identity scoped to nothing but that one bucket, since the
credential goes into a Kubernetes Secret and a wider policy would be a needless risk sitting inside
your cluster.

```bash
export AWS_PROFILE=<your-aws-profile>
export AWS_REGION=us-east-1
export BUCKET=<a-bucket-name-you-choose>-$(openssl rand -hex 4)
aws s3api create-bucket --bucket $BUCKET
aws s3api put-public-access-block --bucket $BUCKET --public-access-block-configuration \
  BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
aws s3api put-bucket-encryption --bucket $BUCKET --server-side-encryption-configuration \
  '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"AES256"},"BucketKeyEnabled":true}]}'
```

Write the minimal policy to a file, naming your own bucket in place of the placeholder, then create
the user and attach it:

```json
{"Version":"2012-10-17","Statement":[
 {"Sid":"ListTheBackupBucket","Effect":"Allow","Action":"s3:ListBucket","Resource":"arn:aws:s3:::YOUR-BUCKET-NAME"},
 {"Sid":"ReadWriteBackupObjects","Effect":"Allow","Action":["s3:PutObject","s3:GetObject"],"Resource":"arn:aws:s3:::YOUR-BUCKET-NAME/*"}]}
```

```bash
aws iam create-user --user-name $BUCKET
POLICY_ARN=$(aws iam create-policy --policy-name $BUCKET --policy-document file://policy.json --query Policy.Arn --output text)
aws iam attach-user-policy --user-name $BUCKET --policy-arn $POLICY_ARN
kubectl create namespace ps
```

Create the access key and pipe it directly into a Secret without ever printing it or saving it to a
file of its own:

```bash
read -r AK SK < <(aws iam create-access-key --user-name $BUCKET --query "AccessKey.[AccessKeyId,SecretAccessKey]" --output text)
kubectl -n ps create secret generic s3-backup-creds \
  --from-literal=AWS_ACCESS_KEY_ID="$AK" --from-literal=AWS_SECRET_ACCESS_KEY="$SK"
unset AK SK
```

::: gotcha
**Never run `kubectl get secret -o yaml` or `kubectl describe secret` on this Secret.** Its values are
only base64-encoded, not encrypted, so either command would print the access key in plain sight.
:::

## Step 1 - Confirm the ground work

```bash
kubectl get nodes
kubectl -n ps get secret s3-backup-creds
kubectl get storageclass
```

Three nodes should read `Ready`, the Secret should show two data keys, and `ebs-csi-default-sc`
should carry the `(default)` marker. The operator places one MySQL pod per node, so all three nodes
need to be schedulable before it can build a healthy cluster.

## Step 2 - Install the operator

```bash
helm repo add percona https://percona.github.io/percona-helm-charts/
helm repo update
helm install ps-operator percona/ps-operator --version 1.2.0 -n ps --wait
kubectl -n ps get pods
```

Pinning `--version 1.2.0` matters here specifically, since letting an operator upgrade itself
underneath a running database is one of the easiest ways to turn a routine chart bump into an
unplanned outage. Expect one `ps-operator-…` pod, `1/1 Running`.

## Step 3 - Describe the cluster you want

```yaml
# values-backup.yaml
backup:
  enabled: true
  storages:
    s3-us-east-1:
      type: s3
      verifyTLS: true
      s3:
        bucket: <your-bucket-name>
        prefix: shop
        region: us-east-1
        credentialsSecret: s3-backup-creds
```

Nothing in this file mentions replication, failover, or HAProxy. The chart's own defaults already ask
for three MySQL pods and three HAProxy pods in front of them, and the operator works out everything
else on its own from that one small file.

## Step 4 - Install the cluster and watch it build

```bash
helm install shop percona/ps-db --version 1.2.0 -n ps -f values-backup.yaml
kubectl -n ps get ps -w
```

This takes several minutes on a cold cluster, mostly spent pulling images; let it run until the
`STATE` column reads `ready`, then stop watching with **Ctrl+C**. Then look at everything the
operator actually built from that one file:

```bash
kubectl -n ps get pods,svc,pvc
```

Expect three MySQL pods and three HAProxy pods, all `2/2 Running`, three storage claims `Bound` to
EBS volumes, and **five Services**, not one: `shop-ps-db-haproxy` (the only one client applications
actually connect through), plus `shop-ps-db-mysql`, `shop-ps-db-mysql-primary`,
`shop-ps-db-mysql-proxy`, and `shop-ps-db-mysql-unready`, which the operator uses internally to
coordinate the cluster itself.

## Step 5 - Connect and write some data

```bash
ROOT_PWD=$(kubectl -n ps get secret shop-ps-db-secrets -o jsonpath='{.data.root}' | base64 -d)
kubectl -n ps run mysql-client -it --rm --restart=Never --image=percona/percona-server:8.4.10-10.1 \
  --env="MYSQL_PWD=$ROOT_PWD" --command -- mysql -h shop-ps-db-haproxy -P 3306 -uroot
```

The root password is read straight into a shell variable and passed as an environment variable to a
throwaway client Pod; it is never typed or echoed. Once connected:

```sql
SELECT @@version;
CREATE DATABASE weather;
CREATE TABLE weather.cities (id INT PRIMARY KEY, name VARCHAR(40), temp_c DECIMAL(4,1));
INSERT INTO weather.cities VALUES (1,'Cairo',34.5),(2,'London',14.0),(3,'Tokyo',22.3),(4,'Sydney',18.9),(5,'Toronto',9.2);
SELECT MEMBER_HOST, MEMBER_ROLE, MEMBER_STATE FROM performance_schema.replication_group_members;
SELECT @@hostname;
```

The replication query names one `PRIMARY` and two `SECONDARY` members, all `ONLINE`; note which pod
`@@hostname` names, since that is the one you delete next.

## Step 6 - Kill the primary on purpose

In a second terminal, delete the pod the previous query named as primary:

```bash
kubectl -n ps delete pod shop-ps-db-mysql-0
```

Switch straight back to the SQL client and run the same hostname query again:

```sql
SELECT @@hostname;
```

Expect a real, visible failure first:

```
ERROR 2013 (HY000): Lost connection to MySQL server during query
No connection. Trying to reconnect...
```

The client reconnects on its own within a few seconds and the query answers with a different pod's
name. Two members out of three is still a majority, so the replication group elects a new primary
among the two survivors without anyone telling it to, and HAProxy starts routing new connections
there almost immediately. That short connection drop is not a bug to work around; it is the failover
window itself, and any real application talking to this cluster has to be written to retry through it.

## Step 7 - Write again, and watch the pod heal

```sql
INSERT INTO weather.cities VALUES (6,'Berlin',16.4);
```

```bash
kubectl -n ps get pods -w
```

Watch the deleted pod come back on its own: `Terminating`, then `Pending`, `Init`, and finally
`2/2 Running` again, on the same node and the same underlying disk it had before. Stop watching once
it settles, then confirm the group is whole again:

```sql
SELECT MEMBER_HOST, MEMBER_ROLE, MEMBER_STATE FROM performance_schema.replication_group_members;
```

All three members should read `ONLINE`, with the pod you deleted now listed as `SECONDARY` rather
than `PRIMARY`. No person did any of this by hand.

## Step 8 - Back up to S3

```yaml
# backup.yaml
apiVersion: ps.percona.com/v1
kind: PerconaServerMySQLBackup
metadata:
  name: backup1
  namespace: ps
spec:
  clusterName: shop-ps-db
  storageName: s3-us-east-1
```

Note the table's checksum before backing it up, so you have something exact to compare against
later:

```sql
CHECKSUM TABLE weather.cities;
```

```bash
kubectl apply -f backup.yaml
kubectl -n ps get ps-backup -w
```

Watch the `STATE` column move from `Starting` through `Running` to `Succeeded`, then stop watching.
The backup runs against one of the secondaries by design, so the primary keeps serving live traffic
the entire time it is taken. Confirm the table actually landed in the bucket:

```bash
aws s3 ls s3://$BUCKET/shop/ --recursive | grep cities
```

The table is stored as chunked backup objects, not as a plain SQL file, which is why grepping for the
table name is the fastest way to confirm it is really there.

## Step 9 - The mistake

```sql
INSERT INTO weather.cities VALUES (7,'Madrid',24.1);
DROP TABLE weather.cities;
SHOW TABLES FROM weather;
SELECT COUNT(*) FROM weather.cities;
```

The last query fails, and the failure is real and worth reading carefully:

```
ERROR 1146 (42S02): Table 'weather.cities' doesn't exist
```

The Madrid row was inserted **after** the backup finished, which matters for what comes next.

## Step 10 - Restore

```yaml
# restore.yaml
apiVersion: ps.percona.com/v1
kind: PerconaServerMySQLRestore
metadata:
  name: restore1
  namespace: ps
spec:
  clusterName: shop-ps-db
  backupName: backup1
```

```bash
kubectl apply -f restore.yaml
kubectl -n ps get ps -w
```

Watch the `STATE` column move through `stopping`, `paused`, and `initializing` before it finally
reads `ready` again; this takes several minutes. A restore is not a table-level undo button. It
brings the whole cluster down: the operator restores the backup into one member and the other two
rejoin by cloning from that member, and **the database is unreachable for around two minutes** while
this happens.

## Step 11 - Prove what actually came back

```sql
SELECT * FROM weather.cities ORDER BY id;
CHECKSUM TABLE weather.cities;
```

Expect six rows, Berlin among them (it was written before the backup), but **Madrid is gone**, since
it was written after the backup that was just restored from. The checksum matches the value noted in
Step 8 exactly. That gap is the whole lesson of a restore: **every write made after the backup was
taken is lost**, no matter how the outage started. In real operation, this is exactly why backups run
on a schedule; the more often one is taken, the less there is to lose when a restore is needed.

## Cleaning up

Cleanup here has a required order, because both Kubernetes and the operator leave real cost behind on
purpose if the steps are skipped or run out of sequence.

```bash
exit
```

```bash
kubectl delete -f restore.yaml -f backup.yaml
helm uninstall shop -n ps
kubectl -n ps get ps
```

**Wait for that last command to print `No resources found in ps namespace.`** before continuing; it
normally takes under a minute, since the operator deletes the MySQL pods in a controlled order before
it lets the cluster resource itself go. Only once it is truly gone:

```bash
helm uninstall ps-operator -n ps
```

::: gotcha
**Uninstalling the operator before the cluster resource has fully gone leaves everything stuck.**
The cluster resource carries a finalizer that only the operator can clear. Remove the operator first
and the MySQL and HAProxy pods, and any PVC delete issued against them, will hang indefinitely. If
that happens, reinstall the operator (`helm install ps-operator percona/ps-operator --version 1.2.0
-n ps --wait`), let the stuck resource finish disappearing, and only then uninstall the operator
again.
:::

```bash
kubectl -n ps get pvc
kubectl -n ps delete pvc --all
```

`helm uninstall` never deletes a StatefulSet's storage claims on its own, so this step is required
every time, not just as a precaution. Finally, remove the bucket, the IAM identity, and the last
Kubernetes objects:

```bash
aws s3 rm s3://$BUCKET --recursive
aws s3 rb s3://$BUCKET
aws iam detach-user-policy --user-name $BUCKET --policy-arn $POLICY_ARN
aws iam delete-access-key --user-name $BUCKET --access-key-id <the-access-key-id>
aws iam delete-policy --policy-arn $POLICY_ARN
aws iam delete-user --user-name $BUCKET
kubectl delete namespace ps
kubectl delete crd perconaservermysqls.ps.percona.com perconaservermysqlbackups.ps.percona.com \
  perconaservermysqlrestores.ps.percona.com perconaservermysqlclustersets.ps.percona.com
```

If you are not moving straight on to the next lecture, delete the cluster as well:

```bash
eksctl delete cluster -f s01/eks/cluster.yaml --wait
```

While this cluster, its three MySQL storage volumes, and the S3 bucket all exist, they bill
continuously regardless of whether you are actively querying anything, which is why every one of the
steps above is a required part of finishing this handout, not an optional tidy-up.

## Traps

::: gotcha
**A MySQL storage claim stays `Pending` in Step 4.** The default StorageClass from the add-ons in
"Before you start" is missing or not yet active. Confirm `kubectl get storageclass` shows
`ebs-csi-default-sc (default)` before installing the cluster.
:::

::: gotcha
**The SQL client fails with `ERROR 1045 Access denied`.** `ROOT_PWD` was never set in the terminal
session running the client, most likely because the Secret did not exist yet when it was read.
`exit` the client, set `ROOT_PWD` again, and retype the `kubectl run` line.
:::
