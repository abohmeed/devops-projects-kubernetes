Once an application is deployed, somebody still has to look after it: text on a page changes and a
pod needs restarting, a well-meaning teammate scales a Deployment by hand at an inconvenient hour, or
a database needs a backup taken and, eventually, restored. Helm and Kustomize get an application
running, but neither one keeps watching it afterward; they act only at the moment somebody runs them.
This handout works through what an operator is, using Kubernetes' own built-in behavior as the model,
and ends with the reconcile loop that every operator, however it is built, runs underneath.

## Day one and day two

A human operator, in the everyday sense of the word, is a person who knows how an application should
behave and what to do the moment something about it changes. That work splits into two phases.
**Day one** is getting the application deployed in the first place. **Day two** is everything that
follows: configuration changes, safe upgrades, backups and restores, and recovering when part of the
system fails. Helm and Kustomize are strong at day one, and Helm in particular can upgrade an
existing release and roll it back cleanly, but only when a person types the command that tells it to.
Between one Helm run and the next, nothing is watching the application on its own. A software
operator's entire purpose is to take over day two, and to do it continuously rather than on demand.

## The reconcile loop you already have

Kubernetes runs this pattern for its own built-in objects long before any operator gets involved,
which makes it the clearest place to learn the idea. Take a Pod: a ReplicaSet manages it, and a
Deployment manages that ReplicaSet in turn, and both of them are constantly watching the API server
for changes. Delete a Pod directly, and the ReplicaSet notices right away and creates a replacement,
because the number of Pods actually running no longer matches the number its spec asks for. Change
the container image inside the Deployment instead, and its controller rolls out a fresh ReplicaSet
and scales the previous one down to nothing.

Two terms describe what just happened. **Desired state** is whatever was written into the object's
spec: the thing a person or another controller asked for. **Current state** is whatever is actually
running in the cluster right now. A **controller** is nothing more than a loop that keeps nudging the
current state toward the desired state, over and over:

1. **Watch** the objects it cares about for any change.
2. **Read** the desired state from the object's spec.
3. **Read** the current state of whatever is actually running.
4. **Compare** the two, and act on any difference it finds.
5. **Write back** what it observed, often into the object's own status field.
6. **Repeat**, both whenever something changes and on a regular schedule, so a drift nobody triggered
   still gets corrected.

This is close to how a thermostat works: it does not switch the heater on once and walk away, it
keeps rereading the temperature and reacting every time it drifts from the target. Kubernetes' own
built-in controllers like this one run inside the control plane, in a component called the controller
manager.

## Teaching Kubernetes a brand-new kind of object

Everything above only covers objects Kubernetes already knows about: Pods, ReplicaSets, Deployments.
A **CustomResourceDefinition**, or **CRD**, teaches the API server an entirely new kind of object,
with whatever fields the CRD's author chooses. Define a CRD for something like `NginxSite`, with
fields such as `replicas` and a page `message`, and `kubectl get nginxsite` immediately behaves
exactly like `kubectl get pods`. Writing the CRD itself is the easy part: it is plain YAML, applied
the same way as any other manifest. On its own, though, a custom resource only stores data. Nothing
happens when it changes, because nothing is watching it yet.

## The controller closes the loop

That is where a custom controller comes in: a program that watches every object of the new kind and
reconciles each one, both whenever it changes and on a regular timer. It reads what was asked for in
the custom resource, checks what is actually running, and creates or updates whatever child objects
are needed (a ConfigMap, a Deployment, a Service) until reality matches the request. Edit the
`message` field, and the controller updates the ConfigMap and rolls the Deployment's pods for you,
which is exactly the task a person used to do by hand. Scale that Deployment manually instead, and
the very next reconcile puts it back, since the custom resource still remembers the original count.
That correction of an unplanned change is usually called **drift correction**. The controller also
writes what it currently observes back into the custom resource's own status field, such as how many
replicas are actually available right now.

Put plainly: **an operator is one or more custom resources, plus a controller that encodes what a
human operator already knows how to do.**

## What this buys in practice

In real use, this pattern extends to taking and restoring backups, rolling out upgrades together with
related changes such as a schema update, and recovering automatically when part of an application
fails. The strongest case for reaching for an operator is a database, where the day-two knowledge
(how to fail over safely, how to back up without corrupting a running write) is hard-won and easy to
get wrong by hand. A later lecture in this section installs exactly that kind of operator for MySQL
and lets it heal itself after a failure.

## Why writing one is harder than installing one

If the CRD is the easy half, the controller is where the real difficulty lives. It is code that talks
directly to the Kubernetes API, most commonly written in Go, and writing it well demands a solid
understanding of how Kubernetes actually behaves. Several tools exist specifically to take that
burden away: some generate the Go scaffolding for a controller automatically, and others let the
whole operator be described in YAML instead of code. The next lecture compares those tools directly.
