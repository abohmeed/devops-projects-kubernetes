Most teams never actually compare their options for running Kubernetes. They pick whatever the last
project used, or whatever came up first in a search, and the choice quietly becomes permanent.
Months later, when someone asks who upgrades the control plane and what it costs, nobody has an
answer, because nobody made the decision in the first place. This section builds the same cluster
three different ways specifically so that comparison is not skipped.

::: keyconcept
The **control plane** is the part of a Kubernetes cluster that someone has to run, patch, upgrade,
and pay for: the API server, etcd, the scheduler, and the controller manager. Every difference
between the three methods below traces back to one question: who is that "someone" for the control
plane?
:::

## The three methods

| Method | What it is | Control plane runs on |
|---|---|---|
| kOps | An open-source tool that builds the whole cluster: control plane, worker instances, and networking, with its state stored in Amazon S3 | EC2 instances in your own account |
| Amazon EKS (via eksctl) | AWS's managed Kubernetes service | AWS-operated infrastructure across three Availability Zones, which you never see or log into |
| kubeadm on EC2 | The most manual path: Packer bakes the node image, Terraform builds the network and instances, and kubeadm bootstraps the cluster | EC2 instances you build and manage entirely yourself |

## Who runs it, who upgrades it, who pays

| | kOps | Amazon EKS (via eksctl) | kubeadm on EC2 |
|---|---|---|---|
| Runs the control plane | You, on EC2 instances kOps creates | AWS | You, on every instance you provision |
| Upgrades the control plane | You trigger it; kOps performs a rolling update that replaces control-plane instances one at a time | You trigger it, one minor version at a time; AWS performs the change | You, one minor version at a time; kubeadm cannot skip a version |
| Pays for the control plane | The EC2 instances behind it, no separate fee | A per-cluster hourly fee, on top of the worker nodes | The EC2 instances behind it, no separate fee |

::: gotcha
The EKS per-cluster fee is not flat forever. Once a cluster version falls out of standard support,
the fee for that cluster rises to six times its standard rate. Staying current on versions is
therefore a cost decision, not just a housekeeping one.
:::

kubeadm's role is easy to misjudge: it only bootstraps a cluster. It does not provision the machines
underneath it and does not install a network plugin, so everything else, including image builds
and infrastructure, is work this course wires up separately with Packer and Terraform.

## The mindset behind the comparison

kOps, EKS, and kubeadm are not the only ways to run Kubernetes. Tools like Rancher, OpenShift, and
Kubespray exist too. The point of comparing these three is not to memorize a list of names but to
practice placing any tool on the same line: open source with automation, cloud managed, or fully
manual. Once you can place a new tool on that line, you can evaluate it the same way this section
evaluates these three. Which of the three methods is the right default is covered later in this
section, once all three have actually been built.

## Before the next lecture

- An AWS account, with a CLI profile configured for **AWS CLI version 2** that has administrator
  permissions.
- Work in the **us-east-1** Region.
- All three methods in this section target the same Kubernetes minor version, so every resulting
  cluster looks identical from `kubectl`.
