kubeadm installs nothing but Kubernetes itself. Every node still needs the same container
runtime, the same kernel settings, and the same kubelet version before `kubeadm` can even run. Set
that up by hand across several nodes and they drift apart: a package moves on, a setting gets
missed on one machine, and a cluster whose nodes quietly disagree fails in ways that are hard to
trace. The fix is to configure a node once, freeze it as an image, and build every node from that
image. This lesson builds that image, a golden AMI, with a tool called Packer.

The companion files for this lesson live in `s01/kubeadm/kubernetes-ami/` in
`abohmeed/devops-projects-kubernetes`:

```
kubernetes-ami/
  node.pkr.hcl
  scripts/
    k8s-node.sh
```

## What Packer actually does

Packer is a HashiCorp tool, the same company behind Terraform. It launches a temporary instance,
runs the provisioners you give it, snapshots the result into an Amazon Machine Image (AMI), and
deletes the instance again. An AMI is an image with the software already installed on it: the
template every new instance boots from. Packer itself is a single Go binary with no runtime of its
own, so installing it is just downloading it and putting it on your `PATH`.

```bash
curl -fsSLO https://releases.hashicorp.com/packer/1.16.1/packer_1.16.1_linux_amd64.zip
unzip packer_1.16.1_linux_amd64.zip && sudo install packer /usr/local/bin/ && packer version
```

This pins Packer at **1.16.1**. If your workstation is macOS on Apple Silicon, swap the file for
`packer_1.16.1_darwin_arm64.zip`; do not install Packer with a package manager instead, since that
will not pin this exact version.

## Finding the base image

Before Packer can build anything it needs to know which base image to start from:

```bash
export AWS_PROFILE=devops-projects

aws ec2 describe-images --region us-east-1 --owners 099720109477 \
  --filters "Name=name,Values=ubuntu/images/hvm-ssd-gp3/ubuntu-noble-24.04-amd64-server-*" \
  --query 'sort_by(Images,&CreationDate)[-1].[Name,CreationDate]' --output table
```

Two details matter here, and both come back later in the template:

- **`--owners 099720109477`** is Canonical's own AWS account ID. It is public, and it is the only
  reason this filter can be trusted: without it, nothing stops another account from publishing an
  image with a name that merely looks official.
- **`hvm-ssd-gp3/ubuntu-noble-24.04-amd64-server-*`** is the path Ubuntu 24.04 (noble) images
  publish under. The older `hvm-ssd` path (without `-gp3`) is how 20.04 (focal) images were named;
  using it here would quietly hand you the wrong Ubuntu release.

The command reads only the name and the creation date, never the image ID. That is deliberate: the
exact same filter goes into the Packer template below, so Packer resolves the current image for
itself on every build, rather than a human copying an ID that goes stale the next time Canonical
publishes a patch.

## The template: `node.pkr.hcl`

```hcl
packer {
  required_plugins {
    amazon = {
      source  = "github.com/hashicorp/amazon"
      version = "= 1.8.2"
    }
  }
}

source "amazon-ebs" "ubuntu" {
  region          = "us-east-1"
  instance_type   = "t3.micro"
  ami_name        = "k8s-node-1.36.4"
  ami_description = "Ubuntu 24.04 + containerd 2.3.6 + kubelet/kubeadm/kubectl 1.36.4"

  source_ami_filter {
    filters = {
      name                = "ubuntu/images/hvm-ssd-gp3/ubuntu-noble-24.04-amd64-server-*"
      root-device-type    = "ebs"
      virtualization-type = "hvm"
    }
    owners      = ["099720109477"]
    most_recent = true
  }

  ssh_username                              = "ubuntu"
  temporary_security_group_source_public_ip = true

  force_deregister      = true
  force_delete_snapshot = true

  tags = {
    Name       = "k8s-node-1.36.4"
    kubernetes = "1.36.4"
    containerd = "2.3.6"
    base_image = "{{ .SourceAMIName }}"
  }
}

build {
  name    = "k8s-node"
  sources = ["source.amazon-ebs.ubuntu"]

  provisioner "shell" {
    environment_vars = [
      "KUBERNETES_MINOR=v1.36",
      "KUBERNETES_VERSION=1.36.4-1.1",
      "CONTAINERD_VERSION=2.3.6-1~ubuntu.24.04~noble",
    ]
    execute_command = "chmod +x {{ .Path }}; sudo {{ .Vars }} bash {{ .Path }}"
    script          = "scripts/k8s-node.sh"
  }
}
```

Credentials come from `AWS_PROFILE`, exported before you run the build. There is no `profile`
setting and no account ID anywhere in this file.

A few lines carry more weight than their length suggests:

- **`required_plugins`.** Plugins are no longer bundled with Packer. This block is what
  `packer init` reads to install the `amazon` plugin, pinned here at `1.8.2`. Delete this block and
  `packer init` has nothing to fetch, so the build fails later with `Unknown source type
  amazon-ebs`, not at `init` itself.
- **`source_ami_filter`** is the same filter you ran by hand above, `most_recent = true` included,
  so a rebuild months from now still finds whatever Canonical is currently shipping.
- **`temporary_security_group_source_public_ip = true`** limits the temporary SSH rule Packer
  creates for the build to your own IP address, rather than leaving port 22 open to the internet
  for the length of the build.
- **`force_deregister`** and **`force_delete_snapshot`** mean a second build with the same
  `ami_name` replaces the old AMI and its snapshot instead of failing because the name is taken.
  Without them, your account accumulates one stale AMI per rebuild.

::: gotcha
Do not "correct" `version = "= 1.8.2"` to something looser like `~> 1.8`. The pin is exact on
purpose: it is what makes this build reproducible months from now, when a newer plugin release
might behave differently.
:::

## Why a shell script, not Ansible

Ansible is a reasonable tool for configuring a fleet of long-lived servers, since it can be re-run
against machines that already exist and only change what has drifted. This image is the opposite
case: it is built once, from nothing, and never changed in place afterward. If it ever needs more
configuration, the fix is to add another line to the shell provisioner, rebuild, and replace the
AMI, not to re-run something against a live host. A plain shell script covers everything an
immutable image needs, with one less moving part to install and keep current.

## The provisioning script: `scripts/k8s-node.sh`

The full file is in the companion repo at `s01/kubeadm/kubernetes-ami/scripts/k8s-node.sh`. It runs
as root on the temporary build instance, in six numbered blocks.

**Block 1, kernel modules.**

```bash
cat <<'EOF' > /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF
modprobe overlay
modprobe br_netfilter
```

`overlay` and `br_netfilter` are what containerd and pod networking rely on to work at all.

**Block 2, packet forwarding.**

```bash
cat <<'EOF' > /etc/sysctl.d/k8s.conf
net.ipv4.ip_forward                 = 1
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
EOF
sysctl --system
```

`net.ipv4.ip_forward = 1` is the setting kubeadm's own documentation lists as required. The two
bridge sysctls are for the bridge network the pods will use; unlike `ip_forward`, they are not a
documented kubeadm requirement, but they are standard practice with a bridge-based CNI.

**Block 3, swap off.**

```bash
swapoff -a
sed -i '/\sswap\s/ s/^/#/' /etc/fstab
```

kubeadm's default kubelet configuration expects swap to be off, both now and after every reboot
(the node support for swap that exists elsewhere in Kubernetes does not change what kubeadm's
default configuration expects here).

**Block 4, containerd from Docker's own apt repository.**

```bash
apt-get install -y "containerd.io=${CONTAINERD_VERSION}"
apt-mark hold containerd.io
```

Two things rule out the obvious alternatives. Docker Engine is not the container runtime kubelet
talks to; kubelet speaks the Container Runtime Interface (CRI), and Docker's dockershim bridge for
it was removed in Kubernetes 1.24. And Ubuntu's own `containerd` package is version 1.7.12, too old
for kubelet 1.36. Docker's own apt repository ships `containerd.io` 2.3.6, on the 2.3 LTS line
(supported to 2028-04-30), which is what this pins and holds so a routine `apt upgrade` cannot move
it.

**Block 5, regenerating containerd's configuration.**

```bash
containerd config default > /etc/containerd/config.toml
sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml
grep -q 'SystemdCgroup = true' /etc/containerd/config.toml
```

Docker's `containerd.io` package ships a default configuration with the CRI plugin disabled, so the
config is regenerated from scratch rather than edited. The `sed` line turns on the systemd cgroup
driver, which is the setting that matters on a systemd-managed host (kubelet itself learns its
cgroup driver from the CRI runtime, so setting it only on the kubelet side does nothing). The
`grep -q` line right after is an end-state check: if the setting did not actually land in the file,
the script exits non-zero and the whole build fails right there, instead of shipping a broken
image that fails silently much later.

**Block 6, kubelet, kubeadm, and kubectl.**

```bash
curl -fsSL "https://pkgs.k8s.io/core:/stable:/${KUBERNETES_MINOR}/deb/Release.key" \
  | gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg
echo "deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/${KUBERNETES_MINOR}/deb/ /" \
  > /etc/apt/sources.list.d/kubernetes.list
apt-get install -y "kubelet=${KUBERNETES_VERSION}" "kubeadm=${KUBERNETES_VERSION}" "kubectl=${KUBERNETES_VERSION}"
apt-mark hold kubelet kubeadm kubectl
```

The old `apt.kubernetes.io` repository is gone; `pkgs.k8s.io` replaced it, and it publishes one
repository per Kubernetes minor version. The `${KUBERNETES_MINOR}` variable (`v1.36`) baked into
the repository URL is what stops a routine update from silently moving you to 1.37; `apt-mark hold`
stops it moving even within 1.36 outside of a deliberate rebuild.

The script ends with:

```bash
kubeadm config images pull --kubernetes-version v1.36.4
```

This pulls the control-plane container images ahead of time. It speeds up `kubeadm init` in the
next lesson, since the images are already local, and it doubles as proof, right here during the
build, that the CRI plugin actually works, since the pull would fail against a containerd
configuration that still has CRI disabled.

## Building it

```bash
packer init . && packer fmt . && packer validate .
packer build .
```

`packer init` installs the pinned amazon plugin, `packer fmt` normalizes the file's formatting, and
`packer validate` checks it before anything is launched. `packer build` then does the real work:
watch for the temporary key pair and temporary security group it creates at the start, and notice
that it deletes both again once the AMI is ready. Expect the build itself to take several minutes
on a `t3.micro`, most of it the provisioning script running.

## Verifying the AMI

```bash
aws ec2 describe-images --region us-east-1 --owners self --filters "Name=name,Values=k8s-node-1.36.4" \
  --query 'Images[].[ImageId,Name,State]' --output table

aws ec2 describe-images --region us-east-1 --owners self --filters "Name=name,Values=k8s-node-1.36.4" \
  --query 'Images[].Tags' --output table
```

The first command finds the AMI by name, exactly the way the next lesson's Terraform will. Packer
prints the new AMI's ID when the build finishes, and it appears again in this output; you never
need to write it down anywhere, since every later step looks the AMI up by name with `owners =
["self"]`. The second command shows the tags the template set: `kubernetes=1.36.4`,
`containerd=2.3.6`, and `base_image` naming the exact source image the build resolved to.

## Traps worth knowing about

| Looks reasonable | Why it is wrong here |
|---|---|
| `apt install containerd` from Ubuntu's own archive | Version 1.7.12, too old for kubelet 1.36 |
| "Docker is the container runtime" | dockershim was removed in Kubernetes 1.24; kubelet talks CRI to containerd directly |
| Setting the cgroup driver only in a kubelet flag | kubelet learns the driver from the CRI runtime; the containerd-side setting is the one that counts |
| Calling `packer build` without a `packer` block | `packer init` has nothing to install, and the build fails later on the missing plugin, not immediately |
| Hand-copying an AMI ID between lessons | IDs change on every rebuild; the by-name lookup with `owners = ["self"]` does not |

## Cleaning up

This AMI, and its roughly 8 GiB snapshot, cost a small amount to keep around each month, and they
are deliberately left in place at the end of this lesson: the next two lessons build the
infrastructure and the cluster from this exact image. Leave it as it is if you are moving on.

If you are stopping here and do not plan to continue the chain, you can remove it yourself:

```bash
AMI=$(aws ec2 describe-images --region us-east-1 --owners self \
  --filters "Name=name,Values=k8s-node-1.36.4" --query 'Images[0].ImageId' --output text)
aws ec2 deregister-image --region us-east-1 --image-id "$AMI" --delete-associated-snapshots
```

`--delete-associated-snapshots` removes the backing snapshot in the same call, so nothing keeps
billing after the image itself is gone.
