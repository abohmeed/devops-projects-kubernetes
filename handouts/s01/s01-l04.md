A managed Kubernetes service takes the control plane off your hands: no etcd to back up, no
control-plane node to patch, no failed control-plane instance to replace at two in the morning.
In exchange, you pay an hourly fee and you accept that you never see, and never need to see, the
API server or etcd instances that back your cluster. This handout builds one such cluster on
Amazon EKS, using an infrastructure-as-code tool, then removes it completely.

## Why eksctl

You can create an EKS cluster from the AWS console, from CloudFormation, from Terraform, or
straight from the AWS CLI. This handout uses **eksctl**, an open source Go binary maintained
together with AWS at [`eksctl-io/eksctl`](https://github.com/eksctl-io/eksctl). Under the hood,
eksctl drives CloudFormation for you: it writes the templates, submits the stacks, and waits for
them, so you describe the cluster you want in a small YAML file instead of writing
infrastructure code by hand.

## Installing the pinned release

Pin an exact eksctl release rather than "whatever is latest," so the same config file behaves the
same way every time you run it.

```bash
ARCH=amd64   # use arm64 if your machine is Arm-based
PLATFORM=$(uname -s)_$ARCH
curl -sLO "https://github.com/eksctl-io/eksctl/releases/download/v0.230.0/eksctl_$PLATFORM.tar.gz"
tar -xzf eksctl_$PLATFORM.tar.gz -C /tmp && rm eksctl_$PLATFORM.tar.gz
sudo install -m 0755 /tmp/eksctl /usr/local/bin && rm /tmp/eksctl
eksctl version
```

`eksctl version` should print `0.230.0`. You will also want to know which identity you are
using before you create anything, since that identity becomes the cluster's administrator later:

```bash
aws sts get-caller-identity
```

For an assumed role, the `Arn` this prints is a **session** ARN
(`arn:aws:sts::<account-id>:assumed-role/<your-role>/<session-id>`). Keep that distinction in
mind: it is not the same string that shows up later in the cluster's access entries.

## The ClusterConfig, field by field

Save this as `cluster.yaml`:

```yaml
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig

metadata:
  name: basic-cluster
  region: us-east-1
  version: "1.36"

accessConfig:
  authenticationMode: API
  bootstrapClusterCreatorAdminPermissions: true

managedNodeGroups:
  - name: ng-1
    amiFamily: AmazonLinux2023
    instanceType: t3.large
    desiredCapacity: 3
    minSize: 3
    maxSize: 3
```

**`version: "1.36"`.** Written as a quoted string on purpose: unquoted, YAML reads `1.36` as the
number 1.36, which is not valid here. The version is written explicitly and not left to default,
because eksctl's own default is an older release. At the time of writing, Kubernetes 1.36 stays
in standard EKS support until 2027-08-02.

**`accessConfig.authenticationMode: API`.** Leaving `accessConfig` out entirely falls back to
`API_AND_CONFIG_MAP`, which keeps the older ConfigMap-based access mechanism alive alongside the
newer one. Setting it to `API` makes access entries the only path in, which is the direction this
handout (and the rest of this course) takes.

**`bootstrapClusterCreatorAdminPermissions: true`.** This is already eksctl's default value. It
is written down anyway so it is visible in the file: it is what grants whoever runs
`eksctl create cluster` an administrator access entry on the new cluster.

**`managedNodeGroups`, `amiFamily: AmazonLinux2023`.** A managed node group hands the underlying
Auto Scaling group and the node lifecycle to EKS, instead of you patching and replacing worker
nodes yourself. AmazonLinux2023 is used because the older AmazonLinux2 node image does not support
Kubernetes versions above 1.33.

## Creating the cluster

```bash
eksctl create cluster -f cluster.yaml
```

This creates two CloudFormation stacks, one for the cluster and one for the node group, along
with a new VPC (including a NAT gateway), and takes roughly fifteen to twenty minutes. When it
finishes, the log ends with a line similar to:

```
EKS cluster "basic-cluster" in "us-east-1" region is ready
```

## Reading the cluster back

```bash
kubectl get nodes
```

Expect three nodes, all `Ready`, running a `v1.36.x` kubelet version. There is no control-plane
node in that list at all: AWS runs it, and you never connect to it directly. `eksctl create`
already wrote your kubeconfig, so `kubectl` can reach the cluster's API endpoint immediately, over
HTTPS on port 443.

## Who can get in: access entries

```bash
aws eks describe-cluster --name basic-cluster --region us-east-1 --query cluster.accessConfig
```

```json
{
    "authenticationMode": "API"
}
```

With `authenticationMode` set to `API`, access entries alone decide who can reach this cluster.
There is no `aws-auth` ConfigMap to inspect or edit.

```bash
aws eks list-access-entries --cluster-name basic-cluster --region us-east-1
```

```json
{
    "accessEntries": [
        "arn:aws:iam::<account-id>:role/aws-service-role/eks.amazonaws.com/AWSServiceRoleForAmazonEKS",
        "arn:aws:iam::<account-id>:role/<your-admin-role>",
        "arn:aws:iam::<account-id>:role/eksctl-basic-cluster-nodegroup-ng-1-NodeInstanceRole-<suffix>"
    ]
}
```

Three entries, and each one exists for a different reason:

| Access entry | What it is for |
|---|---|
| `AWSServiceRoleForAmazonEKS` | A service-linked role that lets the EKS service itself manage resources on your behalf. You did not create it and do not manage it. |
| Your admin role (the identity that ran `eksctl create cluster`) | Added automatically by `bootstrapClusterCreatorAdminPermissions: true`. This is what makes you a cluster administrator without ever touching a ConfigMap. |
| The node group's `NodeInstanceRole` | Lets the EC2 instances in the managed node group join the cluster as worker nodes. |

To confirm what the middle entry can actually do, copy its role ARN from the output above and
pass it as `--principal-arn`:

```bash
aws eks list-associated-access-policies --cluster-name basic-cluster --region us-east-1 \
  --principal-arn <your-admin-role-arn>
```

```json
{
    "associatedAccessPolicies": [
        {
            "policyArn": "arn:aws:eks::aws:cluster-access-policy/AmazonEKSClusterAdminPolicy",
            "accessScope": {
                "type": "cluster",
                "namespaces": []
            }
        }
    ],
    "clusterName": "basic-cluster",
    "principalArn": "arn:aws:iam::<account-id>:role/<your-admin-role>"
}
```

`AmazonEKSClusterAdminPolicy` confirms it: whoever created the cluster is already a full
administrator, with no ConfigMap edit required. Notice that the entry uses the **role** ARN, not
the session ARN that `aws sts get-caller-identity` printed earlier: for an assumed role, the
access entry is always keyed on the role itself, not on any one session of it.

## Traps

::: gotcha
**eksctl defaults to Kubernetes 1.34 if you omit `version`.** Leaving `version` out of
`cluster.yaml` does not give you the newest supported release; it gives you eksctl's own
built-in default, which is older than what you likely intend and older than the kubectl you may
already have installed. Always write the version down explicitly.
:::

::: gotcha
**Never edit the `aws-auth` ConfigMap on a cluster running `authenticationMode: API`.** Once
`accessConfig.authenticationMode` is set to `API`, the ConfigMap mechanism is switched off:
editing `aws-auth` has no effect on who can reach the cluster. Access is controlled entirely
through `eksctl create iamidentitymapping` / access entries and the `aws eks` access-entry
commands shown above.
:::

::: gotcha
**AmazonLinux2 cannot run Kubernetes above 1.33.** If you pin a newer Kubernetes version and
leave `amiFamily` on the older `AmazonLinux2`, the create fails outright. Use
`AmazonLinux2023` for any version 1.34 and above.
:::

::: gotcha
**The version string must be quoted.** `version: 1.36` without quotes is parsed by YAML as the
number 1.36, not the string `"1.36"`, and eksctl will reject or misread it. Always quote it.
:::

## What this costs while it is running

The EKS control plane is billed **per cluster, per hour**, whether or not you have any pods
running on it. The default VPC that eksctl creates also includes a **NAT gateway**, which bills
hourly on top of the control plane fee. Neither charge depends on the workload: an idle cluster
with three worker nodes and zero pods keeps billing exactly the same as a busy one.

## Cleaning up

Delete the cluster with the same tool that created it, not by removing pieces through the
console. Deleting individual resources by hand can leave CloudFormation stacks (and their
charges) behind.

```bash
eksctl delete cluster -f cluster.yaml --wait
```

This tears down the node group stack, then the cluster stack, then the VPC and NAT gateway that
came with it. Confirm nothing is left:

```bash
eksctl get cluster --region us-east-1
```

```
No clusters found
```

If that comes back empty, there is nothing left in this account to bill you for this cluster.
