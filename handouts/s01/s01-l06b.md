The previous lesson built a control plane, two workers, and a load balancer with Terraform. None of
that is a cluster yet: `kubectl get nodes` has nothing to show, because no cluster exists. And
running `kubeadm init` by itself is not enough either. The node comes up `NotReady`, CoreDNS sits
`Pending`, and even once networking starts working the node still refuses ordinary pods. Two
separate pieces are missing, a network plugin and a cloud controller, and each one leaves its own
visible sign as it lands. This lesson brings in both, in order, and reads each sign as it clears.

The companion files for this lesson are authored on the workstation and copied up: `cluster/init.yaml`
and `cluster/join.yaml` in `s01/kubeadm/` in `abohmeed/devops-projects-kubernetes`.

## Writing `init.yaml`

```yaml
apiVersion: kubeadm.k8s.io/v1beta4
kind: InitConfiguration
nodeRegistration:
  kubeletExtraArgs:
    - name: cloud-provider
      value: external
---
apiVersion: kubeadm.k8s.io/v1beta4
kind: ClusterConfiguration
kubernetesVersion: v1.36.4
clusterName: basic-cluster
controlPlaneEndpoint: "PASTE-API-ENDPOINT:6443"   # terraform output -raw api_endpoint
networking:
  podSubnet: 192.168.0.0/16
  serviceSubnet: 10.96.0.0/12
controllerManager:
  extraArgs:
    - name: cloud-provider
      value: external
```

A few things about this file are worth more than a glance:

- **`kubeadm.k8s.io/v1beta4`** is the current kubeadm config API. `extraArgs` is written here as a
  list of `name`/`value` pairs; older kubeadm config versions used a plain map, and `v1beta2` has
  been unsupported since Kubernetes 1.27.
- **`cloud-provider: external`** appears twice: once on the kubelet's extra arguments
  (`nodeRegistration.kubeletExtraArgs`), and once on the controller-manager's
  (`ClusterConfiguration.controllerManager.extraArgs`). It is **deliberately absent from the API
  server**. Add it there and `kubeadm init` fails outright, since the Kubernetes 1.36 API server has
  no such flag at all; the in-tree AWS cloud provider it once referred to was removed in 1.27.
- **`controlPlaneEndpoint`** is pasted in from the previous lesson's Terraform output
  (`terraform output -raw api_endpoint`), with `:6443` appended by hand. Never retype a DNS name by
  reading it off a screen.
- **`podSubnet: 192.168.0.0/16`** does not overlap the VPC's own `10.240.0.0/16`, which is exactly
  why the VPC CIDR was chosen the way it was in the previous lesson.
- There is no `nodeRegistration.name` field here. The previous lesson's launch template user data
  already set the instance's hostname to its own EC2 private DNS name, and kubeadm registers the
  node under whatever `hostname` reports, so nothing extra is needed here.

## Getting onto the control plane and running `kubeadm init`

```bash
B=$(terraform output -raw bastion_public_ip); CP=$(terraform output -raw control_plane_private_ip)
scp -J ubuntu@$B init.yaml ubuntu@$CP:
ssh -J ubuntu@$B ubuntu@$CP
```

`-J` tunnels the connection through the bastion, since the control plane has no public IP of its
own. Once connected, confirm the node's name matches what kubeadm is about to register it under:

```bash
TOKEN=$(curl -sX PUT http://169.254.169.254/latest/api/token -H "X-aws-ec2-metadata-token-ttl-seconds: 300")
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/local-hostname; echo
hostname
```

Both commands should print the same value, something like `ip-10-240-1-79.ec2.internal`. Then:

```bash
sudo kubeadm init --config init.yaml
```

Because the control-plane container images were already pulled into the AMI back when it was built,
this step runs in seconds rather than minutes.

## The first sign: NotReady

Back on the workstation, copy the admin kubeconfig down and point `kubectl` at it:

```bash
mkdir -p ~/.kube
ssh -J ubuntu@$B ubuntu@$CP sudo cat /etc/kubernetes/admin.conf > ~/.kube/basic-cluster.conf
chmod 600 ~/.kube/basic-cluster.conf
export KUBECONFIG=~/.kube/basic-cluster.conf
kubectl get nodes
kubectl get pods -n kube-system
```

`kubectl get nodes` shows exactly one node, and it is `NotReady`. `kubectl get pods -n kube-system`
shows CoreDNS stuck `Pending`. This is the fingerprint of a missing network plugin: a kubelet
reports its network as not ready until something actually writes a CNI configuration for it, and
CoreDNS cannot be scheduled at all without a pod network to land its pod on.

## Installing Cilium

```bash
helm install cilium oci://quay.io/cilium/charts/cilium --version 1.20.2 -n kube-system \
  --set ipam.mode=kubernetes
```

`ipam.mode=kubernetes` is not optional here: it tells Cilium to hand out pod addresses from the
per-node ranges Kubernetes itself carves out of `podSubnet`, rather than from Cilium's own default
address pool, which would overlap this VPC's own CIDR and break routing in a much harder-to-diagnose
way. Cross-node pod traffic then travels as VXLAN over UDP port 8472, the exact port the previous
lesson's security group already opened between nodes.

```bash
kubectl get nodes
```

The node is now `Ready`.

## The second sign: the uninitialized taint

```bash
kubectl describe node | grep -A2 Taints
```

```
Taints:             node-role.kubernetes.io/control-plane:NoSchedule
                    node.cloudprovider.kubernetes.io/uninitialized=true:NoSchedule
```

The `control-plane` taint is normal and expected; it stays. The second one is the sign this lesson
is actually about: a kubelet started with `cloud-provider: external` marks its own node
uninitialized, and Kubernetes refuses to schedule ordinary pods there, CoreDNS included, until a
cloud controller comes along and fills in the node's cloud-provider details. Networking working is
not the same thing as the node being usable.

## Installing the AWS cloud controller manager

```bash
helm repo add aws-cloud-controller-manager https://kubernetes.github.io/cloud-provider-aws
helm install aws-cloud-controller-manager aws-cloud-controller-manager/aws-cloud-controller-manager \
  --version 0.0.12 -n kube-system \
  --set image.tag=v1.36.1 \
  --set hostNetworking=true \
  --set "args={--v=2,--cloud-provider=aws,--configure-cloud-routes=false}"
```

Each of the three settings fixes a specific problem:

- **`image.tag=v1.36.1`.** The chart defaults to an older `v1.35.0` image, which does not match a
  1.36 cluster.
- **`hostNetworking=true`.** Without it, the controller's pod runs on the ordinary pod network, and
  from there it cannot reach the EC2 instance metadata service to ask AWS who it is: the IMDSv2 token
  reply does not survive the extra hop Cilium's overlay adds. A control-plane component like this
  belongs on the node's own network, not a pod network.
- **`--configure-cloud-routes=false`.** The chart's default leaves cloud route configuration on, and
  with no cluster CIDR argument given, the route controller refuses to start at all. It does not
  need to configure anything here anyway: Cilium's own overlay carries pod traffic, not AWS route
  tables.

```bash
kubectl describe node | grep -A2 Taints
```

The `uninitialized` line is gone; only the normal `control-plane` taint remains.

```bash
kubectl get node -o jsonpath='{.items[0].spec.providerID}'; echo
```

This prints a string naming the region, the Availability Zone, and the instance
(`aws:///us-east-1a/i-...`). The cloud controller matched the node's name to its EC2 DNS entry, set
this `providerID`, filled in its zone and instance type, and lifted the taint.

```bash
kubectl get pods -n kube-system
```

CoreDNS is now `Running`.

::: gotcha
Leave out either of the two extra `--set` flags above and the controller pod crash-loops, for two
different reasons. Without `hostNetworking=true`, the logs show something like `could not init cloud
provider "aws": operation error ec2imds: GetRegion, request canceled, context deadline exceeded`, since
the pod on the ordinary network cannot complete the IMDSv2 handshake. Without
`--configure-cloud-routes=false`, the logs show `error running controllers: invalid CIDR[0]: <nil>`,
since the route controller has nothing to configure routes with. Neither failure mentions the flag
that fixes it, so if you see either message, check both settings are actually present in the
install command.
:::

## Joining the workers

A worker is joined with a **config file**, not the bare `kubeadm join` command kubeadm prints,
because kubelet flags like `cloud-provider: external` are set per node at join time. A worker joined
with the plain printed command would come up as an ordinary node the cloud controller never adopts:
no `providerID`, no zone label, left out of any load balancer built later.

```bash
ssh -J ubuntu@$B ubuntu@$CP sudo kubeadm token create --print-join-command
```

This prints one line: `kubeadm join <endpoint>:6443 --token <token> --discovery-token-ca-cert-hash
sha256:<hash>`. Copy the three values it contains into `join.yaml`:

```yaml
apiVersion: kubeadm.k8s.io/v1beta4
kind: JoinConfiguration
discovery:
  bootstrapToken:
    apiServerEndpoint: "PASTE-API-ENDPOINT:6443"      # from: sudo kubeadm token create --print-join-command
    token: "PASTE-TOKEN"                              # the --token value
    caCertHashes: ["sha256:PASTE-HASH"]               # the --discovery-token-ca-cert-hash value
nodeRegistration:
  kubeletExtraArgs:
    - name: cloud-provider
      value: external
```

Note the `sha256:` prefix stays as part of the hash value; dropping it fails join with a certificate
validation error. The bootstrap token itself is valid for 24 hours; after that,
`kubeadm token create --print-join-command` prints a fresh one.

```bash
WORKERS=$(aws ec2 describe-instances --region us-east-1 \
  --filters "Name=tag:aws:autoscaling:groupName,Values=basic-cluster-workers" "Name=instance-state-name,Values=running" \
  --query 'Reservations[].Instances[].PrivateIpAddress' --output text)

for W in $WORKERS; do
  scp -J ubuntu@$B join.yaml ubuntu@$W:
  ssh -J ubuntu@$B ubuntu@$W sudo kubeadm join --config join.yaml
done
```

## Verifying the finished cluster

```bash
kubectl get nodes -o wide
```

All three nodes should show `Ready`, all on `v1.36.4`.

## The two fingerprints, side by side

| Symptom | Missing piece | Cleared by |
|---|---|---|
| Node `NotReady`; CoreDNS `Pending` | a network plugin (CNI) | installing Cilium |
| Taint `node.cloudprovider.kubernetes.io/uninitialized` | a cloud controller | installing the AWS cloud controller manager |

Both conditions look similar from the outside (pods will not schedule), but they are unrelated
problems with unrelated fixes; reading `kubectl describe node`'s actual condition and taint output,
rather than guessing from symptoms, is what tells you which one you are looking at.

## Cleaning up the whole chain

This lesson is the end of the chain that started with building the AMI. Nothing further consumes
any of this infrastructure, so a full teardown here removes everything all three lessons built,
including the AMI itself:

```bash
terraform destroy -auto-approve
aws s3 rb "s3://${BUCKET}" --force
```

If you ever created a `LoadBalancer` Service inside this cluster, delete it **first**, before
`terraform destroy`: the load balancer and security group behind a `LoadBalancer` Service are
created by the cloud controller, not by Terraform, so they sit outside Terraform's state and can
block the VPC from being deleted at all. This lesson never created one, so there is nothing to
delete here, but it matters the moment you experiment further on your own.

Finally, the golden AMI and its snapshot from the first lesson in this chain:

```bash
AMI=$(aws ec2 describe-images --region us-east-1 --owners self \
  --filters "Name=name,Values=k8s-node-1.36.4" --query 'Images[0].ImageId' --output text)
aws ec2 deregister-image --region us-east-1 --image-id "$AMI" --delete-associated-snapshots \
  --query 'DeleteSnapshotResults[].ReturnCode' --output text
```

`--delete-associated-snapshots` removes the backing EBS snapshot in the same call, which matters
because a snapshot keeps billing on its own even after the AMI that referenced it is gone. Confirm
it is actually gone:

```bash
aws ec2 describe-images --region us-east-1 --owners self --filters "Name=name,Values=k8s-node-1.36.4" \
  --query 'Images[].Name' --output text
```

An empty result means the whole chain, from the first lesson's AMI through this lesson's cluster, has
been fully torn down.
