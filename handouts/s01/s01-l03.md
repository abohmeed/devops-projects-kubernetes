kOps sits between building your own control plane by hand and handing it entirely to a managed
service. You still own the control-plane nodes (their size, their count, SSH access, the exact
Kubernetes version), but kOps builds the VPC, subnets, route tables, IAM roles, Auto Scaling
groups and load balancer for you. This is the full sequence to go from an empty AWS account to a
running, validated cluster, and back to nothing again.

Everything below runs from a Linux terminal on `amd64` (Intel/AMD 64-bit). If your machine is a
different OS or architecture, download the matching kops and kubectl binaries from the links in
the Reference section instead of the ones below; nothing else in this guide changes.

## 1. Install the tools

kOps is a single binary with no runtime, so it is a straight download. Pin the version instead of
grabbing "latest": the cluster you build later is pinned to Kubernetes 1.36.4, and a newer kOps or
kubectl can disagree with an older cluster in small but confusing ways.

```bash
curl -Lo kops https://github.com/kubernetes/kops/releases/download/v1.36.2/kops-linux-amd64
chmod +x kops && sudo mv kops /usr/local/bin/kops
kops version
```

Expect `Client version: 1.36.2 (git-v1.36.2)`.

```bash
curl -LO https://dl.k8s.io/release/v1.36.4/bin/linux/amd64/kubectl
chmod +x kubectl && sudo mv kubectl /usr/local/bin/kubectl
kubectl version --client
```

Expect two lines: `Client Version: v1.36.4` and a `Kustomize Version` line. There is no `--short`
flag on modern kubectl; it was removed, so do not add it.

::: gotcha
Match kubectl's version to the **cluster's** Kubernetes version, not to whatever is newest. At the
time this lecture was written, the newest kubectl was already a full minor version ahead of the
cluster.
:::

## 2. Give kOps its own identity

kOps calls EC2, IAM, S3 and other services on your behalf. Give it a dedicated IAM group and user
with exactly the access it needs, instead of reusing your own admin credentials.

```bash
aws iam create-group --group-name kops
```

Then paste all seven lines below as one block and press Enter once; they run one after another.

```bash
aws iam attach-group-policy --group-name kops --policy-arn arn:aws:iam::aws:policy/AmazonEC2FullAccess
aws iam attach-group-policy --group-name kops --policy-arn arn:aws:iam::aws:policy/AmazonRoute53FullAccess
aws iam attach-group-policy --group-name kops --policy-arn arn:aws:iam::aws:policy/AmazonS3FullAccess
aws iam attach-group-policy --group-name kops --policy-arn arn:aws:iam::aws:policy/IAMFullAccess
aws iam attach-group-policy --group-name kops --policy-arn arn:aws:iam::aws:policy/AmazonVPCFullAccess
aws iam attach-group-policy --group-name kops --policy-arn arn:aws:iam::aws:policy/AmazonSQSFullAccess
aws iam attach-group-policy --group-name kops --policy-arn arn:aws:iam::aws:policy/AmazonEventBridgeFullAccess
```

The first five are the classic set: compute, DNS, the state bucket, IAM itself (so kOps can create
roles for the nodes) and the VPC. The last two, SQS and EventBridge, are newer additions: kOps uses
them to handle instance lifecycle events such as a node terminating, so a cluster stays consistent
when an instance goes away unexpectedly.

```bash
aws iam list-attached-group-policies --group-name kops
```

::: gotcha
IAM does not list attached policies in the order you attached them. Do not assume the last two
entries printed are AmazonSQSFullAccess and AmazonEventBridgeFullAccess; read the names, not the
position.
:::

Now the user, and the credential it authenticates with:

```bash
aws iam create-user --user-name kops
aws iam add-user-to-group --user-name kops --group-name kops
aws iam create-access-key --user-name kops > ~/.aws/kops-access-key.json
```

**Keep the secret off your screen and out of your shell history.** `create-access-key` prints the
access key ID and the secret access key as JSON. The `>` redirect on the end of that command sends
that JSON straight into a file instead of your terminal, so nothing sensitive is ever displayed or
scrolled back through. Never run `create-access-key` without a redirect; if you ever do, the key
has already been exposed, so delete it immediately with `aws iam delete-access-key` and create a
new one.

```bash
aws configure --profile kops
```

Answer the four prompts: for the access key ID and secret access key, open
`~/.aws/kops-access-key.json` in a text editor (never `cat` it to your terminal) and paste each
value in when asked; the CLI does not echo the secret back to the screen. For region, type
`us-east-1`. For output format, type `json`. Once the profile is saved, delete the file so a
plaintext copy of a live credential does not sit around on disk:

```bash
rm ~/.aws/kops-access-key.json
```

Switch your shell to the new profile and confirm it:

```bash
export AWS_PROFILE=kops
aws sts get-caller-identity
```

Expect the `Arn` field to end in `user/kops`, which is your proof you are now acting as the kops
user rather than your own account. Do not treat the 12-digit account number in this output as a
secret; it is not one, but there is also no reason to write it down anywhere.

## 3. Create the state store

Every `kops` command reads the cluster's configuration from an S3 bucket and writes back to it.
This bucket is called the state store, and kOps cannot do anything without one.

```bash
export ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
export BUCKET=dop-kops-state-${ACCOUNT_ID}
```

S3 bucket names are globally unique across every AWS customer, so building the name from your own
account ID guarantees nobody else already owns it.

::: gotcha
`us-east-1` is S3's default Region, and it is the **only** Region that rejects a
`LocationConstraint`. A command copied from a tutorial written for another Region looks like this
and fails:

```bash
aws s3api create-bucket --bucket ${BUCKET} --region us-east-1 --create-bucket-configuration LocationConstraint=us-east-1
```

```text
aws: [ERROR]: An error occurred (InvalidLocationConstraint) when calling the CreateBucket operation: The specified location-constraint is not valid
```

Drop the `--create-bucket-configuration` argument entirely when the Region is `us-east-1`:

```bash
aws s3api create-bucket --bucket ${BUCKET} --region us-east-1
```

This one succeeds and returns a `Location` and a `BucketArn`. If you are creating this bucket in
any other Region, you keep the `--create-bucket-configuration LocationConstraint=<that Region>`
argument; `us-east-1` is the single exception.
:::

Turn on versioning so a bad edit to the cluster's spec later can be rolled back instead of lost for
good:

```bash
aws s3api put-bucket-versioning --bucket ${BUCKET} --versioning-configuration Status=Enabled
aws s3api get-bucket-versioning --bucket ${BUCKET}
```

Expect `"Status": "Enabled"`.

```bash
export KOPS_STATE_STORE=s3://${BUCKET}
export NAME=dop-kops.example.com
```

::: gotcha
`KOPS_STATE_STORE` needs the `s3://` prefix. Leave it off and kOps will not raise an error right
away; it simply will not be able to find its own state later, which is a much more confusing
failure to debug. `NAME` can be any name you like; it does not need to be a domain you actually
own, because of the flag in the next step.
:::

## 4. Define the cluster

Create a dedicated SSH key for this cluster rather than reusing your everyday one:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/kops -N ""
```

Now the cluster spec itself:

```bash
kops create cluster \
  --name ${NAME} \
  --cloud aws \
  --zones us-east-1a,us-east-1b,us-east-1c \
  --control-plane-zones us-east-1a,us-east-1b,us-east-1c \
  --control-plane-count 3 \
  --control-plane-size t3.large \
  --node-count 3 \
  --node-size t3.large \
  --kubernetes-version 1.36.4 \
  --dns none \
  --ssh-public-key ~/.ssh/kops.pub
```

What each part is doing:

| Flag | Why it matters |
|---|---|
| `--control-plane-zones` with three zones, `--control-plane-count 3` | One control-plane node per Availability Zone. If one zone fails, the other two still hold a majority (2 of 3) for etcd's quorum, so the cluster keeps working |
| `--kubernetes-version 1.36.4` | Set explicitly. Without it, kOps picks its own default, which may not match the kubectl you just installed |
| `--dns none` | The cluster needs no domain name and no Route 53 hosted zone at all |
| `--ssh-public-key` | Installs your own key onto every node instead of a shared or default one |

::: gotcha
The flags are `--control-plane-size`, `--control-plane-zones` and `--control-plane-count`. Older
guides use `--master-size` and `--master-zones`; those flags no longer exist and current kOps
rejects them outright.
:::

::: gotcha
`--dns none` is the modern choice. kOps can still register a real Route 53 zone if you already own
a domain, and an older "gossip" mode (cluster names ending `.k8s.local`) also exists, but gossip is
deprecated and current kOps rejects it for new clusters. Unless you specifically own a domain and
want it wired up, use `--dns none`.
:::

This command only **writes the spec** to your state store; it does not create anything in AWS yet.
You can inspect what you defined:

```bash
kops get cluster
kops get ig --name ${NAME}
```

`ig` stands for instance group. Expect six of them: three `ControlPlane` groups (one per zone) and
three `Node` groups (one per zone), each sized `t3.large`.

## 5. Build it and wait for it to become healthy

```bash
kops update cluster --name ${NAME} --yes --admin
```

`--yes` is what turns the spec into real AWS resources; leave it off and the command only shows you
a preview of what it would do. `--admin` also writes an admin kubeconfig entry for this cluster, so
`kubectl` is already pointed at it once the command returns. This step takes a few minutes; most of
that time is one line sitting still while it waits for the API load balancer to finish being
created, which is normal.

```bash
kops validate cluster --name ${NAME} --wait 15m
```

`validate` checks the cluster's actual health and keeps retrying until it passes or the wait
expires, instead of you guessing when it is ready. Expect two phases: for the first couple of
minutes it cannot reach the API at all (connection timeouts, since the load balancer is still
coming up), and then it reports specific nodes that have not joined yet or are not ready. Both are
expected while the instances are still booting; that is exactly why `--wait` exists instead of
checking once and giving up. It ends with `Your cluster <name> is ready`.

## 6. Read the proof

```bash
kubectl get nodes -o wide -L topology.kubernetes.io/zone
```

Expect six rows, all `Ready`, all reporting `v1.36.4`. Three show the role `control-plane` and
three show `node` (these are your workers). The extra column on the right, added by
`-L topology.kubernetes.io/zone`, shows which Availability Zone each node runs in, so you can
confirm they really are spread across all three.

Optional: SSH into a control-plane node using the `EXTERNAL-IP` from the output above and the
`ubuntu` user, which a managed Kubernetes service would never let you do directly:

```bash
ssh -i ~/.ssh/kops ubuntu@<control-plane-node-external-ip>
```

Type `exit` to disconnect when you are done looking around.

## Cleaning up

Six `t3.large` instances, their load balancer and their EBS volumes bill by the hour for as long
as they exist. Delete the cluster as soon as you are done with it:

```bash
kops delete cluster --name ${NAME} --yes
```

This removes everything kOps created for this cluster: the instances, the Auto Scaling groups, the
load balancer, the VPC, the subnets and the IAM roles it made for the nodes. It takes a minute or
two and prints its progress as it retries resources that still have dependencies; that is normal,
not a failure.

It deliberately leaves three things alone, because they cost almost nothing to keep and let you
recreate the exact same cluster later without repeating section 2 and 3 above:

- the state bucket, `${BUCKET}`
- the `kops` IAM group and its seven attached policies
- the `kops` IAM user

If you are done with kOps entirely and will not be recreating this cluster, remove those too:

```bash
aws iam delete-access-key --user-name kops --access-key-id <the-access-key-id-from-step-2>
aws iam remove-user-from-group --user-name kops --group-name kops
aws iam delete-user --user-name kops
aws iam detach-group-policy --group-name kops --policy-arn arn:aws:iam::aws:policy/AmazonEC2FullAccess
aws iam detach-group-policy --group-name kops --policy-arn arn:aws:iam::aws:policy/AmazonRoute53FullAccess
aws iam detach-group-policy --group-name kops --policy-arn arn:aws:iam::aws:policy/AmazonS3FullAccess
aws iam detach-group-policy --group-name kops --policy-arn arn:aws:iam::aws:policy/IAMFullAccess
aws iam detach-group-policy --group-name kops --policy-arn arn:aws:iam::aws:policy/AmazonVPCFullAccess
aws iam detach-group-policy --group-name kops --policy-arn arn:aws:iam::aws:policy/AmazonSQSFullAccess
aws iam detach-group-policy --group-name kops --policy-arn arn:aws:iam::aws:policy/AmazonEventBridgeFullAccess
aws iam delete-group --group-name kops
aws s3 rm s3://${BUCKET} --recursive
aws s3api delete-bucket --bucket ${BUCKET}
```

A bucket with versioning enabled keeps old versions of every object, so a plain `aws s3 rm
--recursive` may not empty it completely; if `delete-bucket` fails, remove the remaining object
versions and delete markers first, then retry.

A long-lived access key you are not using is one more thing that can leak, so do not leave the
`kops` user's key sitting around once you no longer need it.

## If something does not work

| Symptom | Likely cause | What to do |
|---|---|---|
| `InvalidLocationConstraint` on the first `create-bucket` | You included `--create-bucket-configuration` while creating in `us-east-1` | Drop that argument and rerun; see the gotcha in section 3 |
| `EntityAlreadyExists` on `create-group` or `create-user` | You already ran section 2 in this account | Skip the create step, or delete the existing group/user first if you want to start over |
| `BucketAlreadyOwnedByYou` | You already created this exact bucket | Skip the create step and move on to enabling versioning |
| `State Store: Required value` from a `kops` command | `KOPS_STATE_STORE` is not exported in the current shell, or is missing the `s3://` prefix | Re-export both `KOPS_STATE_STORE` and `NAME` (section 3); a new terminal session does not remember them |
| `validate` keeps failing until the 15-minute wait times out | The cluster did not converge | Run `kops validate cluster --name ${NAME}` again on its own and `kubectl get pods -A` to see what is stuck, before trying to fix or recreate anything |
| `Unable to connect to the server` from kubectl | The API load balancer is not reachable yet, or your kubeconfig context changed | Re-run `kops export kubecfg --name ${NAME} --admin`, then retry `kubectl get nodes` |
