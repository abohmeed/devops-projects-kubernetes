Section one built the same Kubernetes cluster three ways: with kOps, with Amazon EKS through eksctl,
and with kubeadm on EC2 using Packer and Terraform. A real team has to commit to one of them and live
with its upgrades, its bill, and its on-call pages for years. This handout collects that comparison
in one place, so the decision can be made deliberately rather than by habit.

## The question everything else follows from

Who ends up owning the control plane?

- **Amazon EKS**: AWS runs the API server and etcd. You never see those machines directly. Running
  `kubectl get nodes` against an EKS cluster only ever lists the worker nodes, never the control
  plane.
- **kOps**: the control-plane nodes are EC2 instances in your own account. kOps creates and rolls
  them for you, but they are yours, so if they misbehave, you are the one who finds out.
- **kubeadm on EC2**: you own everything, from the image you built to the network and etcd itself.

## Side-by-side comparison

| | Amazon EKS (via eksctl) | kOps | kubeadm on EC2 |
|---|---|---|---|
| Control plane owned by | AWS. Not visible as nodes you manage | You. EC2 instances that kOps creates and rolls | You. Every component, built by hand |
| Upgrades | One API call or eksctl command upgrades the control plane; managed node groups roll themselves afterward | `kops upgrade cluster`, then `kops update cluster`, then `kops rolling-update cluster` | `kubeadm upgrade plan` and `kubeadm upgrade apply`, node by node, one minor version at a time; the node image is rebuilt with Packer when a newer base is needed |
| Cost of the control plane | A per-cluster hourly fee on top of the worker nodes | No separate fee; you pay for the control-plane EC2 instances themselves | No separate fee; you pay for the control-plane EC2 instances, plus your own time keeping them healthy |
| Time to a working cluster | Shortest: one configuration file and one command | One command, once DNS and the state store are ready | Longest: build the image, provision the infrastructure, initialize the control plane, install the network plugin and cloud controller, then join the workers |
| Flexibility | Lowest: limited to AWS-supported Kubernetes versions and add-ons | High: you choose the network plugin, the OS image, and the control-plane size while kOps handles the mechanics | Total: any version, any flag, any etcd layout |
| What tends to page someone at 3 a.m. | Almost never the control plane; AWS owns that | A bad control-plane node is yours to fix | A bad node or a failed etcd member is yours to fix |

::: keyconcept
The EKS fee is not only a cost, it buys back the hours a team would otherwise spend patching a
control plane by hand. Whether that trade is worth it depends on how much operational time your team
has to spend elsewhere, not on which number is smaller on an invoice.
:::

## What the EKS control plane actually costs

| Support tier | Price |
|---|---|
| Standard support | $0.10 per cluster per hour (about $70 a month) |
| Extended support | $0.60 per cluster per hour |

kOps and kubeadm charge no separate control-plane fee. What you pay instead is the EC2 instances
behind the control plane, plus the operational time of keeping them healthy.

## The IPv6 correction

An earlier version of this comparison claimed EKS did not support IPv6. That has not been true since
January 2022, when AWS added IPv6 cluster support to Amazon EKS. One constraint still matters for
this decision, though: the IP family is chosen when the cluster is created and cannot be changed
afterward. kOps also offers IPv6, but it remains labeled as beta there. In practice, this means IPv6
on its own is no longer a reason to reach for kubeadm.

::: gotcha
Because the IP family is locked in at cluster creation, "we will just switch to IPv6 later if we
need it" is not an option on EKS. If dual-stack or IPv6-only networking is a real requirement,
decide on it before the cluster exists, not after workloads are already running on it.
:::

## When each one is the right call

| Choose | When |
|---|---|
| **Amazon EKS** (the default for most production teams) | You want no control plane to patch, a predictable fee, and first-class AWS integration |
| **kOps** | You want to own the control plane, its sizing, its network plugin, and its OS image, but you want one tool creating, upgrading, and rolling it for you |
| **kubeadm on EC2** | Neither managed option meets a real requirement: a Kubernetes version or feature flag EKS and kOps do not support yet, a custom etcd layout, or a deliberate choice to learn how the pieces fit together |

The advice underneath all of this has not changed: do not spend a long time on this decision. Pick
the simplest method that actually meets your requirements.

## Which cluster the rest of this course uses

For the next two sections, any of the three clusters from this section works equally well. Later in
the course, though, the continuous-delivery and disaster-recovery sections both build their own
clusters with Amazon EKS and eksctl, so it is worth keeping eksctl installed and ready regardless of
which method you choose here. If you want a single cluster to carry you through the rest of the
course, make it EKS.
