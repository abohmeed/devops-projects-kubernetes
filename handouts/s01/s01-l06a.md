The previous lesson's AMI has containerd, kubelet, kubeadm, and kubectl already baked in. An AMI is
not a cluster, though: launch three copies of it into the default VPC with the default security
group and nothing works. The workers cannot reach the API server on port 6443, the kubelets cannot
be reached on port 10250, and the cloud controller the next lesson installs cannot find the
instances at all, because nothing tagged them and nothing gave them permission to call the AWS API.
This lesson builds the network, the firewall rules, the permissions, and the machines themselves,
exactly as much as kubeadm needs and no wider.

The companion files live in `s01/kubeadm/terraform/` in `abohmeed/devops-projects-kubernetes`:
`versions.tf`, `terraform.tfvars`, `network.tf`, `security.tf`, `iam.tf`, `compute.tf`,
`outputs.tf`, `variables.tf`, `set-hostname.sh`, and a committed `.terraform.lock.hcl`.

## The layout

One VPC, one public subnet, one private subnet, in a single Availability Zone:

- **Public subnet:** a bastion host, a NAT gateway, and the API load balancer.
- **Private subnet:** the control plane and the workers, neither with a public IP.

A second and third Availability Zone would each add their own private subnet and their own
control-plane instance behind the same load balancer, for high availability. That is not built
here; this lesson is the single-control-plane case.

## Installing Terraform

```bash
curl -fsSLO https://releases.hashicorp.com/terraform/1.16.4/terraform_1.16.4_linux_amd64.zip
unzip terraform_1.16.4_linux_amd64.zip && sudo install terraform /usr/local/bin/
terraform version
```

Same method as the previous lesson's Packer install: download the release zip, install the binary
onto the path. This pins Terraform at **1.16.4**.

## `versions.tf`, pinning what everyone builds with

```hcl
terraform {
  required_version = "~> 1.16.0"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0" # tested 6.66.0; .terraform.lock.hcl is committed
    }
  }
  backend "s3" {
    key          = "kubeadm/terraform.tfstate"
    region       = "us-east-1"
    use_lockfile = true
  }
}
```

There is no `bucket` line here on purpose: it is passed in at `terraform init` time (see below), so
this file has no per-student value baked into it. The provider is pinned to the `~> 6.0` line, and
the repository commits `.terraform.lock.hcl` alongside it. Without a version pin and a committed
lock file, `terraform init` resolves whatever provider is newest at the time, and a provider major
version can rename or remove arguments out from under you: version 6 of the AWS provider, for
example, removed the old `vpc = true` argument on `aws_eip` in favor of `domain = "vpc"`.

## `terraform.tfvars`, the one file you edit

```hcl
region              = "us-east-1"
cluster_id          = "basic-cluster"    # it becomes the cluster tag
vpc_cidr            = "10.240.0.0/16"    # does not overlap the pod subnet 192.168.0.0/16
admin_cidr          = "PASTE-YOUR-IP/32" # curl -s https://checkip.amazonaws.com
ssh_public_key_path = "~/.ssh/id_ed25519.pub"
control_plane_type  = "t3.medium" # kubeadm preflight needs 2 vCPUs
worker_type         = "t3.medium"
worker_count        = 2
```

`vpc_cidr` is chosen so it cannot collide with the pod network the next lesson hands to Cilium
(`192.168.0.0/16`); if your VPC CIDR ever overlapped the pod CIDR, pod-to-pod routing would break in
ways that have nothing to do with anything in this file. For `admin_cidr`, run:

```bash
curl -s https://checkip.amazonaws.com
```

and paste the address it prints in place of `PASTE-YOUR-IP`, keeping the `/32`. The variable has a
validation rule that rejects anything that is not a `/32`, so a mistake here fails at `terraform
plan`, not silently at runtime.

## `network.tf`

Key points, rather than the full file:

- `enable_dns_hostnames = true` and `enable_dns_support = true` on the VPC. Every instance's private
  DNS name (something like `ip-10-240-1-23.ec2.internal`) is what the node's own name has to match
  in the next lesson, so DNS has to actually be turned on for that to exist.
- Both subnets carry `"kubernetes.io/cluster/${var.cluster_id}" = "owned"`. This is the tag the AWS
  cloud controller manager (installed in the next lesson) uses to decide what belongs to this
  cluster at all.
- The public subnet also carries `"kubernetes.io/role/elb" = "1"`, and the private subnet
  `"kubernetes.io/role/internal-elb" = "1"`, telling the cloud controller which subnet gets external
  load balancers and which gets internal ones.
- The NAT gateway sits in the public subnet so the private instances can pull container images
  without having a public IP of their own.

## `security.tf`, the port map of a Kubernetes cluster

Every rule here is written as its own resource with a `description`, so nothing is a mystery CIDR
block. There are four security groups:

| Security group | Port / protocol | Source | Why |
|---|---|---|---|
| `bastion` | TCP 22 (SSH) | your admin address only | the only door in from the internet; never `0.0.0.0/0` |
| `nodes` (control plane + workers; the one group tagged `owned`) | TCP 22 (SSH) | `bastion` group | `ssh -J` tunnels through the bastion |
| `nodes` | TCP 10250 (kubelet API) | `nodes` group | the API server reaching kubelets for logs, exec, and metrics |
| `nodes` | UDP 8472 (VXLAN) | `nodes` group | Cilium's pod-to-pod overlay between nodes |
| `nodes` | TCP 4240 (health) | `nodes` group | Cilium's node-to-node health checks |
| `nodes` | ICMP echo | `nodes` group | Cilium's node-to-node health probes |
| `control_plane` (extra group, untagged) | TCP 6443 (API server) | the whole VPC | nodes and the load balancer reach the API server |
| `control_plane` | TCP 2379-2380 (etcd) | `control_plane` group | etcd client and peer traffic, ready for a second or third control-plane node |
| `api_lb` (on the load balancer) | TCP 6443 | your admin address, the VPC CIDR, and the NAT gateway's own address | see below |

Two things are easy to get wrong here. First, missing UDP 8472 or TCP 4240 between nodes does not
stop kubeadm from succeeding: the cluster comes up, nodes go Ready, and only later do you discover
that pods on different nodes silently cannot reach each other, or that Cilium reports its peers as
unreachable. The failure is invisible until you actually test cross-node pod traffic. Second, for
the ICMP rule specifically, `from_port` and `to_port` do not mean ports at all for the ICMP
protocol: they mean the ICMP type and code, `8` (echo request) and `0` respectively.

The third `api_lb` source, the NAT gateway's own address, is easy to miss and easy to leave out by
mistake: the load balancer is internet-facing, so its DNS name resolves to a public address even
when a private instance inside the VPC looks it up. A private node reaching that address goes out
through the NAT gateway and arrives at the load balancer carrying the NAT gateway's own address, not
its own private IP. Without this third rule, `kubeadm init` and every `kubeadm join` through the
load balancer time out, even though the exact same request from the workstation succeeds.

## `iam.tf`

These permissions belong to the EC2 instance and to the AWS cloud controller manager that runs on
it, wrapped in an instance profile. They are never a pod's permissions, and never "Kubernetes"
permissions in general; a pod running on these nodes has no access to any of this unless something
else grants it explicitly.

- The **control-plane role** can describe Auto Scaling groups and EC2 resources, create and manage
  load balancers and target groups for a Kubernetes `Service`, and create the one service-linked
  role AWS load balancers need.
- The **node role** is narrower: it can describe instances and regions, and read from a container
  registry.

The exact action lists are copied from the AWS cloud-provider-aws project's own prerequisites
document; see `iam.tf` in the companion repo for the full policies rather than retyping them here.

## `compute.tf`

```hcl
data "aws_ami" "node" {
  owners      = ["self"]
  most_recent = true
  filter {
    name   = "name"
    values = ["k8s-node-1.36.4"]
  }
}
```

The AMI from the previous lesson is found **by name**, owned by `self`, never by a hard-coded ID.
Rebuild the AMI later and this lookup still resolves to whatever the current build produced.

The control plane and the workers each get a launch template of the same shape, differing only in
instance type and IAM profile: both are IMDSv2-only (`http_tokens = "required"`), and both run a
small `set-hostname.sh` script as user data that sets the instance's hostname to its own EC2 private
DNS name. That single fact, node name equals EC2 private DNS name, is what lets the cloud controller
in the next lesson match a Kubernetes node object back to a real EC2 instance; without it, the node
would come up and the taint the cloud controller is supposed to clear would simply never lift.

The control plane is a single `aws_instance`, not an Auto Scaling group, so it keeps one fixed
identity for the load balancer to point at; a second and third control-plane node would be added the
same way, individually. The workers are an `aws_autoscaling_group` sized from `worker_count`.

```hcl
resource "aws_instance" "control_plane" {
  # ...
  lifecycle {
    ignore_changes = [user_data]
  }
}
```

That `lifecycle` block matters more than it looks: the instance's user data comes from the launch
template, and Terraform normally reads it back and reconciles it. Without `ignore_changes`, a second
`terraform apply` later would see a difference and try to clear the instance's user data, which
means stopping and restarting the control plane just to do it.

`aws_lb.api` is a network load balancer on port 6443, forwarding to the control plane, with:

```hcl
preserve_client_ip = false
```

on its target group. Turn this on and the control plane, calling its own API through the load
balancer, would see the caller's real address arrive instead of the load balancer's own private
address. The control-plane security group only admits the VPC CIDR on port 6443, and a caller's real
address might not even be inside the VPC (a workstation reaching in from outside, for example), so
that path can hang. With client-IP preservation off, the control plane always sees the load
balancer's own private address, which the security group already admits.

## `outputs.tf`

```hcl
output "bastion_public_ip" { ... }
output "control_plane_private_ip" { ... }
output "api_endpoint" { ... }       # the load balancer's DNS name
output "cluster_id" { ... }
```

The next lesson pastes `api_endpoint` straight into a kubeadm config file, so it is worth confirming
this output looks like a DNS name (`basic-cluster-api-....elb.us-east-1.amazonaws.com`), not an IP.

## Applying it

```bash
BUCKET="kubeadm-tfstate-$(openssl rand -hex 4)"
aws s3 mb "s3://${BUCKET}" --region us-east-1
terraform init -backend-config="bucket=${BUCKET}"
git add .terraform.lock.hcl && git commit -m "Pin provider versions"   # only if it is not committed yet
terraform plan
terraform apply -auto-approve
terraform output
```

`terraform plan` should report resources being added only, nothing changed or destroyed. Keep the
`BUCKET` value around (write it down, or keep this shell open) since a later `terraform init` needs
it again if you come back to this later.

## Verifying the result

```bash
aws ec2 describe-instances --filters Name=tag-key,Values=kubernetes.io/cluster/basic-cluster \
  Name=instance-state-name,Values=running \
  --query "Reservations[].Instances[].Tags[?Key=='Name'].Value" --output text
```

This should print exactly three names: the control plane and the two workers. The bastion is
deliberately absent from that list, since it was never tagged with the cluster tag; it belongs to
the infrastructure, not to the cluster the cloud controller will later manage.

## What Terraform did *not* do

At the end of `terraform apply`, no cluster exists yet. Terraform built machines, a network, and
permissions; nothing has run `kubeadm` on any of them. And the workers were booted, not joined: if
the Auto Scaling group ever replaces one of them, the replacement will not join the cluster on its
own, since that automation is not part of this configuration. The next lesson is where all of that
happens.

## Cleaning up

The stack, once applied, includes a NAT gateway and a network load balancer, and both bill by the
hour even sitting idle. If you are not moving on to the next lesson right away:

```bash
terraform destroy -auto-approve
```

The AMI from the previous lesson is a separate resource and is unaffected by this: it stays in your
account either way, ready for a later `terraform apply` to find again by name.
