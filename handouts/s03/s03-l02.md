The previous lesson's resources ran the Weather App with plain Docker: one network, four separate
`docker run` commands, and a fixed order to remember, database first, everything else after. Get
that order wrong, or forget one variable, and a container exits or hangs. This handout describes
the same application in a single file and brings it up and down with one command each time, using
Docker Compose. Everything below assumes the `.env` file from the previous lesson's resources
already exists in the same application folder, filled in with your own values and your WeatherAPI
key.

## Before you start

Docker Compose ships as a plugin bundled with a current Docker Engine install, not as a separate
program you install yourself. Confirm it is present:

```bash
docker compose version
```

Expect a line such as `Docker Compose version v5.5.1`. Notice the command has a space in it,
`docker compose`, not a hyphen: this is a plugin subcommand of the `docker` CLI, distinct from an
older, now-unsupported standalone tool of a similar name. Docker Compose only ever manages
containers on the single machine it runs on; once an application needs to run across a cluster of
machines, that becomes a job for an orchestrator such as Kubernetes, covered later in this course.

## Reading `compose.yaml`

The application ships with a `compose.yaml` file already written; open it in an editor rather than
typing it from scratch. A few blocks are worth reading closely before you run anything.

**The file identifies itself, with no version key:**

```yaml
name: weatherapp
```

Older Compose files carried a `version:` field at the top. It is no longer read by current Compose
releases, so this file omits it entirely.

**Each service either builds an image or names one:**

```yaml
services:
  auth:
    build: ./auth
  db:
    image: mysql:8.4.11
```

`auth`, `ui`, and `weather` are each built from their own folder, using the same Dockerfiles the
previous lesson's resources used by hand. `db` instead names a ready-made image directly; nothing
under `db/` gets built.

**Required values come from `.env`, and Compose refuses to start without them:**

```yaml
environment:
  DB_HOST: db
  DB_USER: ${DB_USER:?set DB_USER in .env}
```

The `${DB_USER:?set DB_USER in .env}` syntax means "read this from the environment (which Compose
loads from `.env` automatically), and if it is missing, stop with this message instead of starting
anything." `DB_HOST: db` needs no such guard: it is a fixed value, the service name `db` itself,
which resolves exactly the way a container name did in the previous lesson's resources.

**A healthcheck decides when a service is actually ready, not just running:**

```yaml
healthcheck:
  test: ["CMD", "wget", "-q", "-O", "/dev/null", "http://127.0.0.1:8080/"]
  interval: 5s
  timeout: 3s
  retries: 10
  start_period: 10s
```

auth's healthcheck calls its own `/` endpoint, which only answers `200` once it can reach MySQL.
A container can be "running" from Docker's point of view while the process inside it is still
failing every request; a healthcheck is what tells Compose the difference.

**Services wait on each other by health, not merely by existence:**

```yaml
depends_on:
  db:
    condition: service_healthy
```

`condition: service_healthy` means auth is not even started until `db`'s own healthcheck passes,
not just once `db`'s container has been created. `ui` carries the same pattern against both `auth`
and `weather`.

**The database's own healthcheck is deliberately a TCP query, not a socket check:**

```yaml
test: ["CMD-SHELL", "mysql -h 127.0.0.1 -u\"$$MYSQL_USER\" -p\"$$MYSQL_PASSWORD\" -e 'SELECT 1' auth > /dev/null"]
```

During MySQL's very first startup, it briefly answers only on its local socket, before the
application's own user and database exist. A check against the socket could report healthy too
early. Querying over TCP, as this one does, only succeeds once MySQL has finished that first-time
setup and is genuinely ready for the application to connect. The doubled `$$` is deliberate too: a
single `$` would be interpreted by Compose itself on your machine; `$$` tells Compose to leave it
alone so it reaches the container and is expanded there instead.

**Only one service is reachable from outside the app:**

```yaml
ui:
  ports:
    - "3000:3000"
```

`auth`, `weather`, and `db` have no `ports` entry at all. They are reachable only from other
containers on the same Compose-managed network; only `ui` is published to your own machine.

**An optional secret is allowed to be empty:**

```yaml
weather:
  environment:
    WEATHER_API_KEY: ${WEATHER_API_KEY:-}
```

The `:-` form, unlike the `:?` form above, supplies an empty default instead of stopping Compose.
The application is written to run without a key; only the weather lookup itself is affected.

**Data outlives the containers, in a named volume:**

```yaml
volumes:
  - db-data:/var/lib/mysql
```

with, near the bottom of the file:

```yaml
volumes:
  db-data:
```

`db-data` is a **named volume**, managed by Docker rather than tied to any one container. Removing
and recreating the `db` container does not touch this volume unless you explicitly ask Compose to
remove it too.

## Bringing the whole app up

```bash
docker compose up --build -d --wait
```

This single command builds the three images that need building, creates the network and the
volume, starts every service in the order its `depends_on` health conditions require, and returns
to your prompt only once every service reports healthy. Expect a summary resembling:

```
 ✔ Image weatherapp-auth          Built
 ✔ Image weatherapp-ui            Built
 ✔ Image weatherapp-weather       Built
 ✔ Network weatherapp_app-net     Created
 ✔ Volume weatherapp_db-data      Created
 ✔ Container weatherapp-db-1      Healthy
 ✔ Container weatherapp-weather-1 Healthy
 ✔ Container weatherapp-auth-1    Healthy
 ✔ Container weatherapp-ui-1      Healthy
```

`db` and `weather` start together, since neither depends on the other; `auth` waits for `db` to
become healthy; `ui` waits for both `auth` and `weather`. That is the same start order the previous
lesson's resources enforced by hand, now handled automatically.

## Checking it

```bash
docker compose ps
```

Expect all four services listed as `(healthy)`, with only `ui` showing a published port
(`0.0.0.0:3000->3000/tcp`); the others show only their internal container port.

```bash
docker compose logs auth
```

Expect auth's startup banner followed by `Listening and serving HTTP on :8080`, with **no**
"waiting for the database" line and no restart, since Compose only started auth once the database
was already healthy.

## Using the app

```bash
curl -d 'username=ahmed&password=mypass' localhost:3000/signup
curl -c /tmp/wa-cookies -d 'username=ahmed&password=mypass' localhost:3000/login
curl -b /tmp/wa-cookies localhost:3000/weather/London
```

The first two calls each answer with a redirect (sign-up to the login page, login to the home
page); the cookie jar from the second call carries the session into the third, which returns
London's current weather as JSON, exactly as it did with plain Docker, only now with no container
name or address typed anywhere.

## Proving the data survives a restart

```bash
docker compose down
docker volume ls
```

`down` removes the containers and the network, but not the volume:

```
DRIVER    VOLUME NAME
local     weatherapp_db-data
```

Bring the app back up and log in again right away, without signing up a second time:

```bash
docker compose up -d --wait
curl -c /tmp/wa-cookies -d 'username=ahmed&password=mypass' localhost:3000/login
```

A `302` redirect straight to `/` (not back to `/login`) confirms the account created earlier is
still there: the named volume kept the database's data across the `down` and `up`.

## Cleaning up completely

```bash
docker compose down -v
docker volume ls
rm -f /tmp/wa-cookies
```

The `-v` flag also removes the named volume this time, deleting every account that was ever
created. `docker volume ls` afterward prints only the header line, confirming nothing is left.

::: gotcha
**`down` and `down -v` are not interchangeable.** Plain `down` is safe to run whenever you want to
stop the app but keep its data. `down -v` is destructive: it deletes every user account along with
the volume. Reach for `down -v` only when you actually want a clean slate.
:::

## Traps

::: gotcha
**A missing `.env` value stops everything, before anything is created.** If `DB_PASSWORD` or
another required value from `.env` is missing, `docker compose up` refuses to start, naming the
exact variable, and creates no containers, no network, and no volume at all. This is different
from plain Docker, where a missing variable might not surface until a container has already
started and then exits.
:::

::: gotcha
**The database healthcheck query looks unusual on purpose.** If you copy the `db` healthcheck line
into a shell to test it by hand, remember it was written to run inside the container, where a
single `$` (not `$$`) refers to the container's own environment variables.
:::

::: gotcha
**Compose does not reuse the previous lesson's image tags.** Even though `auth:0.0.1`,
`weather:0.0.1`, and `ui:0.0.1` may still exist on your machine from the previous lesson's
resources, this `compose.yaml` builds its own images (`weatherapp-auth`, `weatherapp-ui`,
`weatherapp-weather`). The build finishes quickly because Docker's build cache is reused, not
because the old image tags are picked up directly.
:::
