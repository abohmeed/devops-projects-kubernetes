The previous lesson's resources pushed the three Weather App images to Docker Hub. This handout
assumes an EKS cluster already exists, built from the same cluster file used in the lecture that
first created one; if that cluster was deleted afterward, recreate it from that same file before
starting here. MySQL is the one part of this app that has to remember something: its users table
must survive a pod restart, which on Kubernetes means a PersistentVolumeClaim. A brand-new EKS
cluster has nothing that can turn that claim into an actual disk, so without a fix the database
would wait forever. This handout adds real storage to the cluster, deploys the app with three Helm
charts, tests it through a load balancer, and removes everything again afterward.

## Before you start

You need `kubectl`, `eksctl`, and Helm 4 on your machine, an AWS CLI profile with permission to
manage EKS, and the three images already pushed from the previous lesson's resources. Set the
region and profile you are using for this course before running anything:

```bash
export AWS_PROFILE=<your-aws-profile>
```

## Step 1 - Confirm there is no default storage class yet

```bash
kubectl get storageclass
```

On a freshly created cluster, expect only one entry:

```
NAME   PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION   AGE
gp2    kubernetes.io/aws-ebs   Delete          WaitForFirstConsumer   false                  8m55s
```

Notice `gp2` has no `(default)` marker after its name. Kubernetes does not create disks by itself;
it asks a provisioner to do that, and on AWS the provisioner is the EBS CSI driver, which `eksctl`
does not install for a cluster by default. Even the `gp2` class shown above cannot actually serve a
new claim without that driver running, since Kubernetes retired its own built-in EBS support. A
PersistentVolumeClaim created against this cluster right now would sit in `Pending` state
indefinitely, which is exactly what would happen to MySQL's claim later in this handout if you
skipped straight to Step 4.

## Step 2 - Write an add-ons file, without touching the cluster file

Leave the file that originally created your cluster exactly as it is. Instead, create a new file
next to it, `addons.yaml`, naming the same cluster and region:

```yaml
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig

metadata:
  name: <your-cluster-name>
  region: <your-cluster-region>

addons:
  - name: eks-pod-identity-agent
    version: v1.3.10-eksbuild.3
  - name: aws-ebs-csi-driver
    version: v1.66.0-eksbuild.1
    useDefaultPodIdentityAssociations: true
    configurationValues: |-
      defaultStorageClass:
        enabled: true
```

- `metadata.name` and `metadata.region` have to match your existing cluster exactly, since this
  file is applied to that cluster, not used to create a new one.
- `eks-pod-identity-agent` is what lets the EBS CSI driver call the EC2 API (to create and attach
  volumes) using an IAM role handed to it directly, with no long-lived access keys stored anywhere
  on the cluster.
- `aws-ebs-csi-driver` is the provisioner itself, the piece that turns a PersistentVolumeClaim into
  a real EBS volume. `useDefaultPodIdentityAssociations: true` assigns it the IAM role it needs
  automatically, so you do not have to create and wire up that role by hand.
- `configurationValues.defaultStorageClass.enabled: true` tells the driver to create and mark a
  StorageClass as the cluster's default the moment it starts up, which is what makes a claim that
  names no class at all (like the one this app's Helm chart creates) resolve automatically.

## Step 3 - Apply the add-ons to the running cluster

```bash
eksctl create addon -f addons.yaml
```

This takes roughly a minute and a half. Expect output naming both add-ons as they activate, ending
in a line about `aws-ebs-csi-driver` starting to create. No account ID or role name needs to appear
anywhere in your own notes about this command; if you want to inspect the IAM role it created,
do that through the AWS Console rather than a command whose output you might paste somewhere else.

## Step 4 - Confirm the default storage class now exists

```bash
kubectl get storageclass
```

Expect a second entry, marked default:

```
NAME                           PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION   AGE
ebs-csi-default-sc (default)   ebs.csi.aws.com         Delete          WaitForFirstConsumer   true                   0s
gp2                            kubernetes.io/aws-ebs   Delete          WaitForFirstConsumer   false                  12m
```

`gp2` is still listed but is no longer the default. Any claim that does not explicitly ask for a
class, such as the one this app's MySQL chart creates, now provisions on `ebs-csi-default-sc`
instead, which creates a gp3 volume unless a class says otherwise. If only `gp2` shows up here, the
add-on has not finished activating yet; wait a few seconds and run the command again.

## Step 5 - Read what you are about to deploy

Before installing anything, it is worth opening the three chart folders and looking at four things:

- The auth chart's `Chart.yaml` declares a dependency on `mysql`, a small chart that ships inside
  its own `charts/` folder rather than being downloaded from anywhere. It runs the official
  `mysql:8.4.11` image directly; no third-party MySQL chart is used anywhere in this course.
- Each chart's `values.yaml` runs two replicas by default, and the auth, weather, and UI services
  listen on ports 8080, 5000, and 80 respectively, with only the UI's service set to
  `type: LoadBalancer`, which is what actually gets exposed outside the cluster.
- The auth deployment's environment reads `DB_HOST` as `<release name>-mysql`, and the application
  connects as its own `weatherapp` database user, with a password read from a Secret the MySQL
  sub-chart manages, never as the database's root account.
- None of the three secrets these charts need (`jwtSecret`, the MySQL root password, or the app
  user's password) are written anywhere in a `values.yaml` file. Every one of them is supplied on
  the command line at install time with `--set`, which keeps a secret value out of any file that
  might end up committed to version control.

## Step 6 - Generate this install's secrets

```bash
cd ~/<path-to-the-weatherapp-folder>
export DOCKERHUB_USER=<your-docker-hub-username>
export JWT_SECRET=$(openssl rand -hex 32)
export DB_ROOT_PASSWORD=$(openssl rand -hex 16)
export DB_PASSWORD=$(openssl rand -hex 16)
```

`DOCKERHUB_USER` has to be exported again here even if you set it in the previous lesson's
resources, since this is a new terminal session that remembers nothing from before.
`openssl rand -hex` prints a random value made only of hexadecimal characters (`0` to `9` and `a` to
`f`), and none of these commands can ever produce a comma. That matters specifically because
`--set` reads a comma as a separator between multiple values, so a secret containing one would
silently corrupt the command that installs the chart. A base64-encoded random value, by contrast,
commonly does contain a `+`, `/`, or occasionally other characters that cause their own problems on
a command line; hex output has none of that risk.

::: gotcha
**MySQL only reads `rootPassword` and `password` the very first time it starts, against an empty
data directory.** If you later run the same `helm upgrade` again with newly generated secrets, the
Kubernetes Secret object changes, but the password already stored inside MySQL's own data does not.
The application then fails to authenticate, and the fix is not another `helm upgrade`: it means
either reusing the original values or deleting the underlying volume and starting over. Keep the
three values generated in this step unchanged for as long as you intend to keep this particular
install running.
:::

Now read the Weather API key without letting it appear on screen or land in your shell history:

```bash
read -rs WEATHER_API_KEY && export WEATHER_API_KEY
```

The terminal shows no prompt and no characters while you type or paste; that silence is expected.
Paste your key and press enter.

## Step 7 - Install the auth chart

```bash
helm upgrade --install weatherapp-auth ./weatherapp-auth \
  --set image.repository=$DOCKERHUB_USER/weatherapp-auth \
  --set jwtSecret="$JWT_SECRET" \
  --set mysql.auth.rootPassword="$DB_ROOT_PASSWORD" --set mysql.auth.password="$DB_PASSWORD"
```

`upgrade --install` is worth using from the very first install onward, not just on later changes:
it installs the chart the first time it is run against a release name that does not exist yet, and
upgrades that same release every time after, so you never need two different commands depending on
whether something is already there. The `mysql.` prefix on two of the `--set` flags is how a value
reaches the nested MySQL chart rather than the auth chart itself; anything under that prefix is
handed down to the sub-chart by Helm automatically.

Check on it right away:

```bash
kubectl get pods
```

Expect something like:

```
NAME                              READY   STATUS              RESTARTS   AGE
weatherapp-auth-554b9584b-7x9s2   0/1     Running             0          10s
weatherapp-auth-554b9584b-rdcd9   0/1     Running             0          10s
weatherapp-auth-mysql-0           0/1     ContainerCreating   0          10s
```

Both auth pods show `Running` but `0/1`, meaning the container itself started but has not yet
passed its own health check, because it is waiting for MySQL to finish initializing. This is a
deliberate startup probe holding the pod there on purpose, not a crash. Give it under a minute and
check again; every pod should settle at `1/1 Running` with zero restarts once MySQL is ready.

## Step 8 - Install the weather and UI charts

```bash
helm upgrade --install weatherapp-weather ./weatherapp-weather \
  --set image.repository=$DOCKERHUB_USER/weatherapp-weather \
  --set apikey="$WEATHER_API_KEY"
helm upgrade --install weatherapp-ui ./weatherapp-ui \
  --set image.repository=$DOCKERHUB_USER/weatherapp-ui \
  --set jwtSecret="$JWT_SECRET"
```

The `jwtSecret` value passed to the UI chart must be the exact same value passed to the auth chart
above. Auth signs each login token with this value, and the UI verifies that signature on every
request; if the two charts are ever given different values, every login will look invalid to the
UI even though auth issued it correctly.

Confirm all three releases:

```bash
helm list
```

Expect three rows, all `deployed`, all reporting app version `2.1.0`, which comes from the images
built and pushed in the previous lesson's resources without you needing to pass a tag explicitly.

## Step 9 - Confirm the database has real storage

```bash
kubectl get pvc
```

Expect the claim bound to a real volume:

```
NAME                           STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS         VOLUMEATTRIBUTESCLASS   AGE
data-weatherapp-auth-mysql-0   Bound    pvc-fc4d6ff3-11f0-4d36-9288-768e14ef6b8c   8Gi        RWO            ebs-csi-default-sc   <unset>                 8m12s
```

```bash
kubectl get pv
```

```
NAME                                       CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS   CLAIM                                  STORAGECLASS         VOLUMEATTRIBUTESCLASS   REASON   AGE
pvc-fc4d6ff3-11f0-4d36-9288-768e14ef6b8c   8Gi        RWO            Delete           Bound    default/data-weatherapp-auth-mysql-0   ebs-csi-default-sc   <unset>                          8m12s
```

Look at the `CLAIM` column here, not the volume's own `NAME`. The volume itself is named after an
internal identifier the driver assigned, but the `CLAIM` column reads
`default/data-weatherapp-auth-mysql-0`, the claim template name (`data`) joined to the specific pod
name (`weatherapp-auth-mysql-0`), which is how a StatefulSet like this one names every claim it
creates.

## Step 10 - Reach the app through its load balancer

```bash
kubectl get svc weatherapp-ui
```

```
NAME            TYPE           CLUSTER-IP       EXTERNAL-IP                                                               PORT(S)        AGE
weatherapp-ui   LoadBalancer   10.100.153.245   a7c572c0de40f43eda91d14d2f2c4e36-1280507143.us-east-1.elb.amazonaws.com   80:30924/TCP   7m51s
```

Because this course does not install the AWS Load Balancer Controller, EKS's own built-in
controller provisions a **Classic Load Balancer** for any Service of type `LoadBalancer`, listening
on plain HTTP port 80 and forwarding to the UI pods behind it. The hostname under `EXTERNAL-IP`
usually takes a minute or two to start resolving over DNS after it first appears.

Open `http://<the hostname from EXTERNAL-IP>` in a browser once it resolves. Sign up for an
account, log back in with the same credentials, and search for a city such as Cairo. A working
install returns that city's current weather, which means every piece, the UI, auth, weather, MySQL,
and the external weather provider, is talking to the others correctly.

## Cleaning up

Removing this deployment takes several steps, in a specific order, because Helm and Kubernetes
each leave part of the storage behind on purpose. Skipping the order, or stopping partway, leaves
something still billing.

```bash
helm uninstall weatherapp-ui weatherapp-weather weatherapp-auth
```

```bash
kubectl get pvc
```

The claim is still listed, still `Bound`. Helm does not delete a PersistentVolumeClaim that a
StatefulSet created, even when the StatefulSet itself is gone, since Helm has no way to know
whether you wanted to keep that data.

```bash
kubectl delete pvc data-weatherapp-auth-mysql-0
```

Wait roughly thirty seconds, then confirm the volume itself is gone:

```bash
kubectl get pv
```

Expect `No resources found`. If a volume still shows up in a `Released` state, the disk is still
in the process of detaching; wait a little longer and check again. Only once this comes back empty
is the underlying EBS volume actually deleted and no longer billing.

Finally, delete the cluster itself, using the exact same file that originally created it:

```bash
eksctl delete cluster -f <your-cluster-file>.yaml --wait
```

This removes the node group, the cluster control plane, and the IAM roles the add-ons created,
including the one behind the EBS CSI driver. It normally takes several minutes to finish. Do not
skip `--wait` and close the terminal early: without it you have no confirmation the delete actually
completed rather than merely being requested.

While this cluster and its load balancer are up, several things bill by the hour regardless of
whether you are actively using the app: the EKS control plane itself, every worker node instance,
the load balancer, and the network address the cluster's outbound networking uses. None of that
stops until the cluster is actually deleted, which is why this section exists as a required last
step, not an optional one.

## Traps

::: gotcha
**A PVC stuck in `Pending` with an event about no storage class.** This means the chart was
installed before the add-ons from Step 2 finished creating the default StorageClass. It usually
resolves on its own within well under a minute once the class appears, since the same claim binds
automatically the moment a default class exists; if it does not, confirm Step 4 actually shows
`ebs-csi-default-sc (default)` before doing anything else.
:::

::: gotcha
**`ErrImagePull` or `ImagePullBackOff` on any pod.** Either `DOCKERHUB_USER` was not exported in
this terminal session, or the image referenced was never actually pushed in the previous lesson's
resources. Confirm the value with `echo $DOCKERHUB_USER`, and confirm the image exists publicly on
Docker Hub before retrying the install.
:::

::: gotcha
**Login redirects straight back to the sign-in page.** This is either a wrong password, or the auth
and UI charts were installed with two different `jwtSecret` values. If the terminal session that
held `$JWT_SECRET` was closed or restarted between installs, uninstall all three releases, delete
the PVC, wait for `kubectl get pv` to come back empty, and start again from Step 6 with freshly
generated secrets.
:::

::: gotcha
**A city search returns an error about the weather provider rejecting the key.** This means the
value passed as `apikey` is missing, mistyped, or not yet active on the provider's side. It is a
different failure from a missing key outright: a rejected key means the provider actually received
a request and turned it down, so check the key itself rather than the chart's configuration.
:::
