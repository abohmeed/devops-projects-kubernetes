The previous lesson's resources mapped the Weather App: three services, a database, and the
settings each one reads from the environment. A diagram does not run anything, though. This
handout walks through turning each service into an image and starting the whole app with plain
`docker build` and `docker run`, one container at a time, checking each one with `curl` before
starting the next. Every command below is meant to be copied and run as written.

## Before you start

You need a working Docker Engine and the `git`, `curl`, and `openssl` command-line tools. Nothing
in this lesson touches a cloud account; everything runs on your own machine.

## Step 1 - Clone the app and look at what is there

```bash
git clone https://github.com/abohmeed/devops-projects-kubernetes.git
cd devops-projects-kubernetes/weatherapp
ls -A
```

A plain `ls` would hide `.env.example`, since its name starts with a dot; `-A` shows it. Expect to
see three service folders (`auth`, `UI`, `weather`), three Helm chart folders you will not need
until a later section, `compose.yaml`, `README.md`, `VERSIONS.md`, and `.env.example`.

## Step 2 - Create your own `.env` file

Every secret this app needs comes from a file named `.env`, which is never committed to the
repository. Start from the example:

```bash
cp .env.example .env
```

Open the new `.env` file in a text editor. It has five values to fill in:

```
DB_ROOT_PASSWORD=change-me-root
DB_USER=weatherapp
DB_PASSWORD=change-me-app
JWT_SECRET=change-me-to-a-long-random-string
WEATHER_API_KEY=
```

- Replace `DB_ROOT_PASSWORD` and `DB_PASSWORD` with any throwaway values of your own; this copy of
  the database only exists on your machine, so nothing here needs to be memorable or reused
  anywhere else.
- Leave `DB_USER` as `weatherapp`. The application already expects that exact name.
- Generate `JWT_SECRET` instead of typing one by hand:

```bash
openssl rand -hex 32
```

Copy the 64-character value this prints and paste it in place of
`change-me-to-a-long-random-string`.

- Leave `WEATHER_API_KEY` empty for now. Step 5 below comes back to it.

Save the file once all four values (everything except the key) are filled in.

## Step 3 - Confirm Git will never see this file

```bash
git check-ignore -v .env
```

A working `.gitignore` prints the file and line that matches, for example:

```
weatherapp/.gitignore:1:.env	.env
```

If this command prints nothing, `.env` is not ignored, and you should stop and check the
`.gitignore` file before continuing. Never remove a value from `.env.example` to "test" whether
Git picks it up; check the ignore rule this way instead.

## Step 4 - Load `.env` into your shell

```bash
set -a; source .env; set +a
```

This command prints nothing on success. It reads every `KEY=value` line in `.env` and exports each
one as a shell variable for the rest of this terminal session, so the `docker run` commands below
can reference them by name without ever typing a secret value directly on the command line.

::: gotcha
Every value in `.env` must avoid spaces, `$`, and backtick characters, since `source` reads the
file literally. A password with a `$` in it, for example, would be treated as a shell variable
reference instead of a literal character.
:::

## Step 5 - Create a network and start MySQL

```bash
docker network create app-net
```

A user-defined network like this one gives every container on it a DNS name equal to its
`--name`. That is what lets the auth container reach the database simply by calling it `db`,
instead of hunting down an IP address that changes every time a container restarts.

```bash
docker run -d --name db --network app-net \
  -e MYSQL_ROOT_PASSWORD="$DB_ROOT_PASSWORD" -e MYSQL_DATABASE=auth \
  -e MYSQL_USER="$DB_USER" -e MYSQL_PASSWORD="$DB_PASSWORD" \
  mysql:8.4.11
```

This prints one long container ID. Notice there is no `-p` flag: MySQL is reachable only from
other containers on `app-net`, on port 3306, and is never exposed to your own machine directly.
There is also no `-v` flag, so this container's data lives in an anonymous volume Docker creates
automatically; once this specific container is removed, nothing in this command points back to
that data again. The next lesson's resources fix that with a named volume.

MySQL takes a few seconds to finish its first-time setup before it starts accepting connections.
The Dockerfile tour in the next step gives it time to catch up.

## Step 6 - Build and run auth

Open `auth/Dockerfile` and look at its shape: it is a **multi-stage build**. The first stage uses a
Go base image to compile the source; the final stage copies only the compiled binary into a small
Alpine image and runs it as a non-root user (UID 10001), not as root. Only Go needs a compile
stage here; the Python and JavaScript services below install their dependencies instead.

```bash
docker build -t auth:0.0.1 ./auth
```

```bash
docker run -d --name auth --network app-net -p 8080:8080 \
  -e DB_HOST=db -e DB_USER -e DB_PASSWORD -e JWT_SECRET \
  auth:0.0.1
```

Notice the difference between `-e DB_HOST=db`, which sets a fixed value, and `-e DB_USER` alone,
which forwards whatever value is already in your shell (from Step 4) without ever typing it again
on this command line. That is a deliberate habit worth keeping: it keeps secret values out of your
shell history and out of anything that inspects a container's running command.

Check the log:

```bash
docker logs auth
```

auth is written to wait for the database instead of crashing if it starts too soon. If MySQL was
still finishing its own setup, you will see a few lines like
`waiting for the database: dial tcp ...: connect: connection refused`, retried every three
seconds, followed by a startup banner ending in `Listening and serving HTTP on :8080`. If MySQL
was already ready, the log starts directly at that banner with no waiting lines. Either is normal.

Now confirm auth is answering:

```bash
curl localhost:8080/
```

Expect `{"success":"The auth is running"}`.

Sign up a user, then try the same sign-up again:

```bash
curl -s -w '\n%{http_code}\n' -X POST -H 'Content-Type: application/json' \
  -d '{"user_name":"ahmed","user_password":"mypass"}' localhost:8080/users
```

The first call answers `{"success":"User added successfully"}` and `200`. Run the exact same
command a second time and it answers `{"error":"User already exists"}` and `422`.

Log in with the right password, then with the wrong one:

```bash
curl -s -w '\n%{http_code}\n' -X POST -H 'Content-Type: application/json' \
  -d '{"user_name":"ahmed","user_password":"mypass"}' localhost:8080/users/ahmed
```

Expect a `200` with a JSON body containing a `JWT` field, a long signed token. Run it again with
`"user_password":"wrong"` instead, and expect `{"error":"Bad credentials"}` and `403`. This is
exactly the check the UI relies on later, only called directly.

## Step 7 - Build and run weather, first without a key

```bash
docker build -t weather:0.0.1 ./weather
docker run -d --name weather --network app-net -p 5000:5000 weather:0.0.1
curl -s -w '%{http_code}\n' localhost:5000/London
```

Expect:

```
{"error":"The weather service has no API key (WEATHER_API_KEY is not set)"}
503
```

The container itself is healthy; only this one call fails, because no key has been supplied yet.

### Getting a free WeatherAPI.com key

1. Go to [weatherapi.com](https://www.weatherapi.com/) and sign up for a free account.
2. Verify your email address if you are asked to.
3. Log in and open your account dashboard.
4. Copy the API key shown there.
5. Paste it into your `.env` file as the value of `WEATHER_API_KEY`, and save the file.

Never commit `.env` to version control, and never paste the key into a command line where it
could end up in your shell history. If a key is ever exposed, generate a new one from the same
dashboard and update `.env`.

### Running weather with the key

```bash
set -a; source .env; set +a
docker rm -f weather
docker run -d --name weather --network app-net -p 5000:5000 -e WEATHER_API_KEY weather:0.0.1
curl -s localhost:5000/London
curl -s -w '%{http_code}\n' localhost:5000/Nowhereville
```

With a valid key, the London call returns a JSON object with the city, country, current
temperature, and condition. A city the provider does not recognize, such as `Nowhereville`,
answers `404` with the provider's own "no matching location" message instead.

::: gotcha
If the key was mistyped, truncated, or has not activated yet, weather answers
`{"error":"The weather provider rejected the API key"}` with status `502`. That is a different
failure from the `503` above: `503` means no key was supplied at all, `502` means a key was
supplied and the provider turned it down.
:::

## Step 8 - Build and run UI

Open `UI/Dockerfile`: it uses a current Node.js LTS base image, installs dependencies with
`npm ci` from the lock file (rather than a looser `npm install`, so exactly the tested versions are
installed every time), and runs as the image's built-in low-privilege `node` user, not root.

```bash
docker build -t ui:0.0.1 ./UI
docker run -d --name ui --network app-net -p 3000:3000 \
  -e AUTH_HOST=auth -e AUTH_PORT=8080 -e WEATHER_HOST=weather -e WEATHER_PORT=5000 -e JWT_SECRET \
  ui:0.0.1
```

Notice that `AUTH_HOST` and `WEATHER_HOST` are the container names `auth` and `weather`, not IP
addresses. That is only possible because all three containers share the `app-net` network created
in Step 5.

Use the app the same way a browser would, through `curl` with a cookie jar:

```bash
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' localhost:3000/
```

Expect `302` redirecting to `/login`, since no login cookie has been sent yet.

```bash
curl -s -c /tmp/wa-cookies -o /dev/null -w '%{http_code} %{redirect_url}\n' \
  -d 'username=ahmed&password=mypass' localhost:3000/login
```

Expect `302` redirecting to `/`. The `-c` flag saves the cookie UI just set into `/tmp/wa-cookies`.

```bash
curl -s -b /tmp/wa-cookies localhost:3000/weather/London
```

This reuses the saved cookie and returns the same weather JSON as before, only this time the
request traveled through UI, to auth (to confirm the session was never checked directly, since UI
verifies the token itself), to weather, to WeatherAPI.com, and back.

## Step 9 - Clean up

```bash
docker ps
```

Expect four running containers: `db`, `auth`, `weather`, and `ui`.

```bash
docker rm -f ui weather auth db
docker network rm app-net
rm -f /tmp/wa-cookies
```

This removes every container and the network. The three image tags (`auth:0.0.1`, `weather:0.0.1`,
`ui:0.0.1`) are left in place on purpose: the next lesson's resources reuse the same build cache,
so leaving the images behind costs nothing and saves time later.

## Traps

::: gotcha
**`DB_HOST=localhost` is the classic mistake.** Inside a container, `localhost` means that
container itself, not the host machine or any other container. Without a shared network and a
container name to call, auth would have no way to find the database at all. The user-defined
network in Step 5 is what fixes this.
:::

::: gotcha
**A missing environment variable does not always fail loudly the same way.** auth and UI are both
written to exit immediately if a required variable is missing, with a message naming which one.
If a container you just started is not listed in `docker ps` a moment later, check its log for a
message like "is not set" before assuming something else went wrong.
:::

::: gotcha
**Typing a secret directly after `-e NAME=`, instead of `-e NAME` alone, puts that value in your
shell history and in the output of tools that list running processes.** Every command in this
handout that forwards a secret does it with the bare `-e NAME` form, reading the value from the
shell environment set up in Step 4.
:::
