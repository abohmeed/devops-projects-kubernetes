The previous lesson's resources ran the whole Weather App on one machine with Docker Compose,
which built all three images and kept them in that machine's local image store. A Kubernetes
cluster does not share that store. Its nodes run their own container runtime, and when it is asked
to start a pod it pulls the image from a registry over the network, never from a laptop or a build
VM sitting somewhere else. This handout builds the three Weather App images again, this time
tagged and pushed to Docker Hub, so a cluster can pull them on its own in a later lesson.

## Before you start

You need a free Docker Hub account and a working Docker Engine. Work from the same application
folder used in the earlier Docker and Compose lessons (the one containing `auth`, `UI`, `weather`,
and the three Helm chart folders).

## Creating a Docker Hub access token

Never type your Docker Hub account password into a terminal. Use a personal access token instead,
since a token can be scoped and revoked without changing your account password.

1. Sign in at [hub.docker.com](https://hub.docker.com) and open **Account Settings**.
2. Go to **Security** and choose **New Access Token**.
3. Give it a name you will recognize later, such as `weatherapp-push`, and set its permission to
   **Read & Write** (a **Read-only** token can pull images but cannot push them).
4. Generate the token and copy it immediately. Docker Hub shows the full value exactly once; if you
   navigate away before copying it, you have to create a new one.

Keep this value somewhere safe for the next step. Treat it exactly like a password: never commit
it to a repository and never paste it into a command line where it would be saved in your shell
history.

## Step 1 - Export your Docker Hub username

```bash
export DOCKERHUB_USER=<your-docker-hub-username>
```

Every command below reads this variable, so replace `<your-docker-hub-username>` with your actual
Docker Hub account name once, here, and every later command already has the right value.

## Step 2 - Log in with the token

```bash
docker login -u "$DOCKERHUB_USER"
```

This prompts for a password. Paste the access token you copied above (not your account password)
and press enter. The terminal shows nothing while you paste or type here; that is expected, not a
sign that anything is broken. A successful login prints `Login Succeeded`. Docker may also print a
warning that the credential is being stored in plain text in a local config file; that is normal
for a personal machine and does not affect anything in this lesson.

::: gotcha
**A `Password:` prompt is not the place to use `-p` on the command line.** Never run
`docker login -p <token>`. Typing a secret as a command-line argument writes it into your shell
history and into anything on the machine that can list running process arguments. Always let the
prompt ask for it.
:::

## Step 3 - Understand the tag you are about to use

Every image needs a full name shaped like `namespace/repository:tag`. Here, `namespace` is your
Docker Hub username, and `repository` is one of `weatherapp-auth`, `weatherapp-ui`, or
`weatherapp-weather`, the exact names each Helm chart already looks for by default.

The tag matters just as much as the name. Each chart declares an `appVersion` of `2.1.0`, and when
a chart is installed without explicitly overriding the image tag, Helm falls back to that
`appVersion` value automatically. Push an image under any other tag and the chart will still ask
for `2.1.0` when you deploy it later, and the cluster will fail to find it. Tagging your images
`2.1.0` now is what makes the deployment lesson work without you having to think about the tag
again.

## Step 4 - Build the three images

```bash
docker build -t "$DOCKERHUB_USER/weatherapp-auth:2.1.0" auth
docker build -t "$DOCKERHUB_USER/weatherapp-ui:2.1.0" UI
docker build -t "$DOCKERHUB_USER/weatherapp-weather:2.1.0" weather
```

Notice the middle folder name is spelled `UI`, in upper case; the other two are lower case. The
`auth` build is a multi-stage build that compiles the service's own source code as part of the
build, covered in an earlier lesson's resources if you want a refresher on what each Dockerfile
stage does.

::: gotcha
**Building on an Apple Silicon Mac or another arm64 machine?** Add `--platform linux/amd64` to
every one of the three build commands above, for example
`docker build --platform linux/amd64 -t "$DOCKERHUB_USER/weatherapp-auth:2.1.0" auth`. Amazon EKS
worker nodes in this course run on x86_64 (amd64) instances. An image built natively on an arm64
machine without this flag produces an arm64 image, and a pod that tries to run it on an amd64 node
fails immediately with `exec format error`, a message that gives no hint that the real problem is
the processor architecture. If you are building on an Intel or AMD machine, or inside a Linux VM
that is itself x86_64, this flag changes nothing and can be safely left off.
:::

Confirm all three images exist locally:

```bash
docker image ls "$DOCKERHUB_USER/*"
```

Expect three lines, one per repository, each showing the `2.1.0` tag and an image ID:

```
IMAGE                                 ID             DISK USAGE   CONTENT SIZE   EXTRA
<user>/weatherapp-auth:2.1.0          7bf8706f988c       44.8MB         12.4MB
<user>/weatherapp-ui:2.1.0            c06697b3c8ae        255MB         63.7MB
<user>/weatherapp-weather:2.1.0       a727d7e06940        193MB         46.7MB
```

If this filter prints nothing, `DOCKERHUB_USER` was probably not exported in the terminal session
you are currently using; re-run Step 1 and try again.

## Step 5 - Push all three images

```bash
docker push "$DOCKERHUB_USER/weatherapp-auth:2.1.0"
docker push "$DOCKERHUB_USER/weatherapp-ui:2.1.0"
docker push "$DOCKERHUB_USER/weatherapp-weather:2.1.0"
```

Each push ends with a line similar to `2.1.0: digest: sha256:... size: 855`. Watch the layer list
while each one uploads. `weatherapp-auth` and `weatherapp-ui` are both built on an Alpine base
image, so the layer they share only has to upload once; the second push of it should report the
layer as already present rather than uploading it again. `weatherapp-weather` is built on a
different, Debian-based image, so none of its layers are shared with the other two, and all of
them upload freshly. The `weatherapp-auth` push itself is the smallest of the three: its final
stage is nothing more than a base Alpine image plus one compiled binary.

A brand-new repository created this way is **public by default** on a free Docker Hub account,
which means any Kubernetes node can pull it anonymously, with no credentials at all. A private
repository would still work, but the cluster would then need an `imagePullSecret` configured so its
nodes could authenticate to Docker Hub before pulling. This course does not use a private
repository or an `imagePullSecret` anywhere, so keep these three repositories public.

## Step 6 - Prove the image exists in the registry

```bash
docker buildx imagetools inspect "$DOCKERHUB_USER/weatherapp-auth:2.1.0"
```

This command talks to Docker Hub directly over HTTPS and reads back the manifest for the tag you
just pushed, which is proof the image now lives somewhere your own machine did not put it. Expect
output naming the image, its digest, and one or more manifests, one of which includes a line
`Platform: linux/amd64`, matching the architecture of the nodes this image will eventually run on.
A second manifest entry describing an `unknown/unknown` platform is a build provenance record that
recent Docker versions attach automatically; it is not another copy of the image and can be
ignored.

## Cleaning up

Leave all three images pushed to Docker Hub. A later lesson's resources pull these exact tags to
deploy the app on a cluster, so removing them now would only mean rebuilding and repushing later.

If you want to reclaim local disk space, the three images built on your own machine are safe to
remove, since Docker Hub already holds the copies that matter:

```bash
docker rmi "$DOCKERHUB_USER/weatherapp-auth:2.1.0" \
  "$DOCKERHUB_USER/weatherapp-ui:2.1.0" \
  "$DOCKERHUB_USER/weatherapp-weather:2.1.0"
```

If you are working on a shared or borrowed machine, also remove the saved login credential:

```bash
docker logout
```

## Traps

::: gotcha
**`unauthorized: incorrect username or password` at login.** This means either your account
password was pasted instead of a token, or the token has expired or been revoked. Generate a fresh
Read & Write token from Docker Hub's Security settings and repeat the login step.
:::

::: gotcha
**`denied: requested access to the resource is denied` on push.** This usually means one of three
things: you are not actually logged in, the token you used only has Read access, or
`DOCKERHUB_USER` does not match the account the token belongs to. Check
`echo $DOCKERHUB_USER` against the account name shown in Docker Hub, and log in again with a
Read & Write token if needed.
:::

::: gotcha
**`toomanyrequests` while building.** Docker Hub limits how many times an anonymous, unauthenticated
puller can download images from a single network address over a rolling window. If you hit this
while pulling one of the public base images the Dockerfiles start from, wait a while and try again,
or log in first, since an authenticated pull gets a higher limit than an anonymous one.
:::
