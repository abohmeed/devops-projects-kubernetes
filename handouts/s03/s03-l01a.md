Later lessons in this section build, run, and package this application. Before any of that makes
sense, you need a map: what each piece does, what it talks to, and what it needs to run. This
handout is that map. Nothing here changes; you are reading the application, not modifying it, and
no background in Go, Python, or JavaScript is assumed.

## The app from a visitor's point of view

The Weather App lets a signed-in user type the name of a city and see its current weather. Before
that lookup works, a visitor has to create an account and log in. Requiring an account is a
deliberate choice, not an accident: it keeps the weather lookup from being called anonymously by
anyone who finds the URL, which limits how much traffic reaches the paid-per-call weather provider
behind the scenes.

- **Sign up** with a unique user name and a password.
- **Log in** with that same pair.
- **Look up a city** and see its current condition and temperature.
- **Log out** when finished.

The weather values themselves are not produced by this application. They are fetched, on every
lookup, from an outside provider, MET Norway (the Norwegian Meteorological Institute), which shares
its forecasts for free. The app is a thin, authenticated front end over that provider's data.

## Three services and one database

| Service | Language / runtime | Port | Talks to | Job |
|---|---|---|---|---|
| **auth** | Go | 8080 | MySQL | creates accounts, checks passwords, issues a login token |
| **UI** | JavaScript on Node.js | 3000 | auth, weather | serves every page; the only service a browser ever reaches directly |
| **weather** | Python (Flask, served through gunicorn) | 5000 | MET Norway | finds the city in its built-in list, then fetches its current conditions |
| MySQL | (official image) | 3306 | (used only by auth) | stores the list of user accounts |

Splitting one small application into three services like this, each with its own image, its own
language runtime, and one job, is called a **microservices** architecture. The point of splitting
it is not the code itself: it is that each of these three pieces can be built, tested, and shipped
on its own schedule, by its own team if there were more than one, without touching the other two.
Automating exactly that build-test-ship cycle is what most of the rest of this course is about.

::: keyconcept
Notice that the browser never talks to auth or to weather. UI is the only service exposed to the
outside world; auth and weather are reachable only from UI. This is a common shape for a small
service group: one public front door, and internal services behind it that never need to defend
themselves against arbitrary internet traffic.
:::

## Sign-up flow

| # | Hop | Detail |
|---|---|---|
| 1 | Browser to UI | `POST /signup` with the sign-up form |
| 2 | UI to auth | `POST /users`, JSON body `{"user_name", "user_password"}` |
| 3 | auth to MySQL | stores a **bcrypt hash** of the password, never the password itself |
| 4 | auth to UI | `200` if the account was created, or `422` with `"User already exists"` if it was not |
| 5 | UI to browser | sent on to the login page either way |

Hashing the password with bcrypt before it ever reaches the database means that even if the users
table were stolen outright, the raw passwords would not be exposed. auth never stores, logs, or
returns the plaintext password at any point after it receives it.

## Log-in flow and the JSON Web Token

| # | Hop | Detail |
|---|---|---|
| 1 | Browser to UI | `POST /login` with the login form |
| 2 | UI to auth | `POST /users/<name>`, JSON body `{"user_name", "user_password"}` |
| 3 | auth | checks the submitted password against the stored bcrypt hash |
| 4 | auth to UI (wrong password) | `403` with `"Bad credentials"` |
| 5 | auth to UI (correct password) | `200` with a signed **JSON Web Token (JWT)** |
| 6 | UI to browser | the token is stored in a cookie named `token`, marked `httpOnly` |

A JWT is a signed, self-contained credential. This one carries the user name and an expiration
time set thirty minutes ahead, and it is signed with a value called `JWT_SECRET` using the HS256
algorithm. Because the signature can be checked with nothing more than that shared secret, UI
verifies every later request on its own, without calling auth again. That is the whole reason
auth and UI have to hold the exact same `JWT_SECRET` value: UI is the one doing the checking, not
the one who signed it. Marking the cookie `httpOnly` means no page script running in the browser
can read the token, only the browser itself, which sends it back automatically on later requests.

::: gotcha
If auth and UI ever end up with two different values for `JWT_SECRET`, login still appears to
succeed at auth, which issues a token just fine. UI, holding a different secret, cannot verify
that token's signature and quietly sends the user back to the login page. There is no error
message that names the mismatch; it just looks like login "doesn't work." One secret, in both
places, always.
:::

Notice something about this flow: auth never sees a weather request. It only ever handles sign-up
and login. From this point on, UI relies entirely on the token to decide whether a request is
allowed.

## Weather lookup flow

| # | Hop | Detail |
|---|---|---|
| 1 | Browser to UI | `GET /weather/<city>`, only accepted with a valid token cookie |
| 2 | UI to weather | `GET /<city>` |
| 3 | weather to MET Norway | the city's coordinates from the built-in list; HTTPS on port 443, with a contact address in the User-Agent |
| 4 | MET Norway to weather | JSON with the forecast for that spot; weather keeps it until its expiry time |
| 5 | weather to UI to browser | the page renders city, country, condition, and temperature |

Without a valid token, step 1 never reaches weather at all: UI redirects the browser straight
back to the login page.

Because this whole flow depends on an outside service that the app does not control, weather is
written to fail with a clear, specific error rather than hanging or crashing:

| Situation | Status code |
|---|---|
| No contact address configured at all | `503` |
| MET Norway refuses the request | `502` |
| City not in the built-in list | `404` |
| Provider unreachable | `504` |

Every one of those is a JSON body the page can display, so a missing contact address degrades one
feature of the app rather than breaking it.

## Ports and environment variables

Inside the application, every service talks to every other service in plain HTTP; only the call
out to MET Norway leaves the app and uses HTTPS.

| Service | Internal port | Protocol |
|---|---|---|
| UI | 3000 | HTTP |
| auth | 8080 | HTTP |
| weather | 5000 | HTTP |
| MySQL | 3306 | (MySQL wire protocol) |

None of these hosts, ports, or credentials are written into the application's source code. Every
one of them is read from an environment variable at start-up, which is what lets the exact same
image run in different places (your machine, a container orchestrator, a different cluster
entirely) with different values.

| Service | Environment variable | Secret? |
|---|---|---|
| auth | `DB_HOST` | no |
| auth | `DB_USER` | no |
| auth | `DB_PASSWORD` | **yes** |
| auth | `JWT_SECRET` | **yes** |
| UI | `AUTH_HOST` | no |
| UI | `AUTH_PORT` | no |
| UI | `WEATHER_HOST` | no |
| UI | `WEATHER_PORT` | no |
| UI | `JWT_SECRET` | **yes** |
| weather | `WEATHER_CONTACT` | no |

::: keyconcept
Configuration through environment variables, rather than through values baked into the code, is
what makes the same built image deployable in more than one way. It is also what keeps secrets out
of the source: none of the values marked "yes" above belong in the application's Git repository,
under any circumstances.
:::

`WEATHER_CONTACT` is not a key and not a secret: it is your email address or a link to your project,
which MET Norway's terms ask every app to send so they can reach its owner. There is nothing to sign
up for. The app is written to tolerate its absence: leave it unset and every part of the app still
runs, only the weather lookup answers with an error instead of a result. Setting it on the running
app is covered in the next lesson's resources, not here.

MET Norway's data and the GeoNames city list are both licensed CC BY 4.0, which allows commercial
use as long as the source is credited. The page credits both under every result.

## Traps

::: gotcha
**A missing `WEATHER_CONTACT` is not a crash.** The app is deliberately written so that an absent
contact address only fails the one feature that needs it. If you see the whole app refuse to start,
the cause is something else: a missing database credential or a missing `JWT_SECRET` will stop
auth or UI outright, since those are required for every request.
:::

::: gotcha
**auth returns a token; UI creates the cookie.** It is easy to describe this backward. auth's job
ends at handing back a signed JWT in a JSON response. Turning that token into a browser cookie,
and reading it back on every later request, is entirely UI's responsibility.
:::

::: gotcha
**A stolen password table is not the same as stolen passwords.** Because auth stores a bcrypt hash
rather than the password itself, recovering the original password from the stored value is
computationally impractical. That property only holds because the app hashes before writing to
the database; if that step were ever skipped, this protection would not exist.
:::
