The previous handout finished the staging pipeline: any change pushed to `main` was built, tested and
already running in staging without anyone touching a keyboard. But staging is not production. In
production you want three things staging never asked for: a person to decide when a version actually
goes live, a way to know exactly which version is running at any moment, and — if a release turns out
bad — a way back that takes about a minute rather than a rebuild. This handout turns a git tag into a
release, puts a manual step in front of production, and uses that same tag to bring back an earlier
version. It ends by removing everything this section built.

## Before you start

You need `.gitlab-ci.yml` from the previous handout, with `staging` running and its pipeline green.

```bash
cd ~/weatherapp
git switch -c release-stages
```

## Step 1 - What a version is

A version such as `1.0.0` is nothing more than an annotated git tag on a commit that has already passed
staging. The tag pattern `*` was already protected earlier in this section, so only a Maintainer can
create a tag in this project — which means a tag pipeline is the one place that gets the protected
variables and the AWS role, since it only runs for a ref the trust policy trusts.

## Step 2 - Three edits to `.gitlab-ci.yml`

In `workflow: rules:`, add a third rule:

```yaml
    - if: $CI_COMMIT_TAG
```

From now on GitLab starts a pipeline for a merge request, for a push to `main`, and now for a tag as
well. In `stages:`, add `promote` and `deploy` after `deliver`.

At the end of the file:

```yaml
promote:
  extends: .docker
  stage: promote
  script:
    - echo "$DOCKERHUB_TOKEN" | docker login --username "$DOCKERHUB_USER" --password-stdin
    - docker buildx imagetools create --tag "$DOCKERHUB_USER/weatherapp-auth:$CI_COMMIT_TAG" "$DOCKERHUB_USER/weatherapp-auth:$CI_COMMIT_SHORT_SHA"
    - docker buildx imagetools create --tag "$DOCKERHUB_USER/weatherapp-ui:$CI_COMMIT_TAG" "$DOCKERHUB_USER/weatherapp-ui:$CI_COMMIT_SHORT_SHA"
    - docker buildx imagetools create --tag "$DOCKERHUB_USER/weatherapp-weather:$CI_COMMIT_TAG" "$DOCKERHUB_USER/weatherapp-weather:$CI_COMMIT_SHORT_SHA"
  rules:
    - if: $CI_COMMIT_TAG

deploy:
  extends: .deploy
  stage: deploy
  environment:
    name: production
  resource_group: production
  variables:
    NAMESPACE: production
    IMAGE_TAG: $CI_COMMIT_TAG
  rules:
    - if: $CI_COMMIT_TAG
      when: manual
```

`promote` extends `.docker`, the same base the `build` job uses, but only runs in a tag pipeline. It
signs in to Docker Hub, then runs `docker buildx imagetools create` three times, once per image. In a
tag pipeline `$CI_COMMIT_SHORT_SHA` is the short SHA of the exact commit that was tagged, and that
commit's images already exist in the registry, since `push` already pushed them and `deliver` already
ran them in staging. `imagetools create` **doesn't pull anything and doesn't rebuild anything** — it
writes a new tag straight into the registry, pointing at that same image. What reaches production is
the identical image that already passed staging, not a fresh build of the same source.

`deploy` extends `.deploy`, the same template that installs the three Helm charts in staging. Only two
variables change: `NAMESPACE` becomes `production`, `IMAGE_TAG` becomes `$CI_COMMIT_TAG`. The job has
no steps of its own — the sign-in and the three chart upgrades all come from the template; only where
they point has changed. The rule is `when: manual`, so it waits for a person. That manual click is what
turns this into **continuous delivery**: every version sits ready, and a person decides when it goes
out.

## Step 3 - Merge it

```bash
git add .gitlab-ci.yml
git commit -m "Promote tagged versions and deploy them to production"
git push -u origin release-stages
```

Open the merge-request link, **Create merge request** → **Set to auto-merge**. Once it merges, `main`
delivers to staging exactly as before — nothing changes on screen, since it's still the same
application.

## Step 4 - Cut and release version 1.0.0

```bash
git switch main
git pull
git tag -a 1.0.0 -m "Version 1.0.0"
git push origin 1.0.0
```

```
To gitlab.com:<your-group>/weatherapp.git
 * [new tag]         1.0.0 -> 1.0.0
```

In **Build** → **Pipelines**, a pipeline for `1.0.0` appears. `promote` runs on its own and finishes;
`deploy` sits with a play (▶) button, and the pipeline's status badge reads **Blocked**. **Blocked
doesn't mean something failed** — it means the gate is doing exactly its job: nothing reaches
production until a person presses play. Click ▶ on `deploy`.

## Step 5 - Confirm production

```bash
kubectl get pods --namespace production
```

The same seven pods known from staging, now in their own namespace with their own MySQL volume.

```bash
kubectl get svc weatherapp-ui --namespace production
```

A second `…elb.amazonaws.com` hostname, entirely separate from staging's. Once it resolves, open it —
the app is there, login button green.

## Step 6 - Cut and release version 1.0.1

```bash
git switch -c login-button
```

In `UI/public/login.html` line 42, change `btn-success` to `btn-warning`, then:

```bash
git add UI/public/login.html
git commit -m "Change the login button color"
git push -u origin login-button
```

Open a merge request, **Set to auto-merge**; staging picks it up once it merges. Then:

```bash
git switch main
git pull
git tag -a 1.0.1 -m "Version 1.0.1"
git push origin 1.0.1
```

In the `1.0.1` pipeline, press play on `deploy`. Reload the production tab: the button is orange.

## Step 7 - Roll back

Say `1.0.1` turns out to be a bad release and you want `1.0.0` back, right now — no new tag, no git
involved at all. In GitLab: **Operate** → **Environments** → `production`. Two deployments are listed,
`1.0.1` on top and `1.0.0` underneath. Next to the `1.0.0` deployment, click **Rollback environment**
and confirm. GitLab re-runs **only that old deploy job**: the same tag, the same images, a fresh
sign-in, nothing rebuilt.

```bash
kubectl get deployment weatherapp-ui --namespace production -o jsonpath='{.spec.template.spec.containers[0].image}'
```

→ `<your-dockerhub-username>/weatherapp-ui:1.0.0` — the rollback didn't rebuild anything and didn't
touch git history. The old image was still sitting in the registry; Helm simply upgraded back to it.

## Cleaning up

This is the last lecture of the section — remove everything it created, in this order, or something
gets left behind still billing.

```bash
helm uninstall weatherapp-ui weatherapp-weather weatherapp-auth --namespace production
helm uninstall weatherapp-ui weatherapp-weather weatherapp-auth --namespace staging
```

Uninstalling a release does **not** delete its MySQL PersistentVolumeClaim. **Deleting the MySQL PVC
needs its namespace named explicitly** — delete it in each namespace separately, or the underlying disk
keeps costing you:

```bash
kubectl delete pvc data-weatherapp-auth-mysql-0 --namespace production
kubectl delete pvc data-weatherapp-auth-mysql-0 --namespace staging
```

Then the IAM side:

```bash
export ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
aws iam delete-role-policy --role-name gitlab-weatherapp-deployer --policy-name eks-describe-cluster
aws iam delete-role --role-name gitlab-weatherapp-deployer
aws iam delete-open-id-connect-provider --open-id-connect-provider-arn "arn:aws:iam::${ACCOUNT_ID}:oidc-provider/gitlab.com"
```

Finally, the cluster:

```bash
cd ~/devops-projects/s01-l04
eksctl delete cluster -f cluster.yaml --wait
```

This takes several minutes: the control plane, both load balancers, both volumes, the node group and
the EKS access entry all go with it. The GitLab project and its pipeline history stay behind, since
they cost nothing to keep. If you generated a Docker Hub token just for this section, revoke it now
from Docker Hub's Security settings.

::: gotcha
**Watch your GitLab compute minutes while working through this section.** Building the full pipeline
end to end — every merge request, every push to `main`, every tag release — used 22 of the Free tier's
400 monthly minutes. Plenty of headroom, but a habit of re-running pipelines "just to check" adds up
faster than it looks.
:::

## Traps

::: gotcha
**The tag pipeline's `promote` job fails with `… not found`.** You tagged a commit whose `main`
pipeline hadn't finished pushing images yet. Delete the tag (`git push origin :1.0.0`,
`git tag -d 1.0.0`), wait for `main`'s pipeline to go green, then re-tag.
:::

::: gotcha
**`deploy` fails with `AccessDenied … AssumeRoleWithWebIdentity`.** The tag pattern isn't protected.
Check **Settings** → **Repository** → **Protected tags** for `*`, then re-push the tag.
:::

::: gotcha
**Once a GitLab project has run CI, never delete it.** GitLab.com burns a deleted project's path for
CI: recreating a project at a path that has already issued ID tokens fails its first job with
`id_token_burned_project_path`. If you want a clean slate, rewind branches and delete tags in place —
never delete and recreate the project itself.
:::
