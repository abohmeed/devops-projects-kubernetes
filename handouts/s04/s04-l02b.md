The previous handout built a ServiceAccount token a pipeline can use to reach any Kubernetes cluster.
On EKS specifically, there is a better option: the cluster already trusts AWS IAM directly, so a GitLab
job can sign in to AWS using a short-lived token GitLab issues for that one run, with no stored key
anywhere in GitLab, AWS, or the cluster. This handout builds that chain: GitLab ID token → IAM OIDC
provider → IAM role → EKS access entry → Kubernetes group → the same RoleBindings from before.

## Before you start

You need the cluster and `rbac.yaml` from the previous handout, already applied.

```bash
cd ~/devops-projects/s04
kubectl get namespaces
```

Confirm `staging`, `production` and `cicd` all show `Active`. No account ID is ever typed directly in
this handout: it is captured into a shell variable and every file that needs it uses `${ACCOUNT_ID}`,
filled in by `envsubst` at the moment a command runs, never written to disk with the real value.

## Step 1 - Register GitLab as an identity provider

```bash
export AWS_PROFILE=<your-aws-profile>
export AWS_REGION=us-east-1
export ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
aws iam create-open-id-connect-provider --url https://gitlab.com --client-id-list https://gitlab.com
```

```json
{
    "OpenIDConnectProviderArn": "arn:aws:iam::<your-account-id>:oidc-provider/gitlab.com"
}
```

The client ID doubles as the audience: the value each GitLab job embeds in its token to declare the
token is meant specifically for AWS. There is no certificate thumbprint to supply; AWS verifies
GitLab's certificate on its own.

## Step 2 - Write the trust policy

Create `trust-policy.json`:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::${ACCOUNT_ID}:oidc-provider/gitlab.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "gitlab.com:aud": "https://gitlab.com",
          "gitlab.com:ref_protected": "true"
        },
        "StringLike": {
          "gitlab.com:sub": "project_path:${GITLAB_PROJECT_PATH}:ref_type:*:ref:*"
        }
      }
    }
  ]
}
```

Three conditions gate who can assume this role: `aud` must equal the audience registered above; `sub`
must start with the project's path (a feature branch inside the project cannot assume the role, since
`ref_protected` below excludes it); and `ref_protected` must literally be the string `"true"`, so only
protected branches and tags (never an arbitrary feature branch) get a token AWS will accept.
`${ACCOUNT_ID}` and `${GITLAB_PROJECT_PATH}` stay as placeholders in the file; `envsubst` fills them
from your shell the moment the policy is sent, so your account number never sits in the file itself.

## Step 3 - Create the role and its one permission

The course uses the GitLab group `devops-projects-kubernetes`. Use **your own** GitLab group or
username in its place:

```bash
export GITLAB_PROJECT_PATH=<your-group>/weatherapp
aws iam create-role --role-name gitlab-weatherapp-deployer --assume-role-policy-document "$(envsubst < trust-policy.json)" --query Role.RoleName --output text
```

→ `gitlab-weatherapp-deployer`

Create `deployer-policy.json`:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "eks:DescribeCluster",
      "Resource": "arn:aws:eks:us-east-1:${ACCOUNT_ID}:cluster/basic-cluster"
    }
  ]
}
```

```bash
aws iam put-role-policy --role-name gitlab-weatherapp-deployer --policy-name eks-describe-cluster --policy-document "$(envsubst < deployer-policy.json)"
```

`eks:DescribeCluster` is the **only** AWS permission this role ever needs: it's what
`aws eks update-kubeconfig` calls to learn the cluster's API endpoint. Once the pipeline is inside the
cluster, Kubernetes RBAC decides what it may do; IAM's job stops at the cluster door.

## Step 4 - The EKS access entry

Since the cluster runs with `authenticationMode: API`, EKS reads access entries rather than the older
`aws-auth` config map:

```bash
aws eks create-access-entry --cluster-name basic-cluster --principal-arn "arn:aws:iam::${ACCOUNT_ID}:role/gitlab-weatherapp-deployer" --username 'gitlab-ci:{{SessionName}}' --kubernetes-groups cicd --query 'accessEntry.[username,kubernetesGroups]'
```

```json
[
    "gitlab-ci:{{SessionName}}",
    [
        "cicd"
    ]
]
```

Two choices worth noticing: `--kubernetes-groups cicd` puts every session of this role into a single
Kubernetes group, so the same RoleBindings from the ServiceAccount handout can serve this identity too.
`--username 'gitlab-ci:{{SessionName}}'` names each session after the actual GitLab job that ran it:
error messages and audit logs then point to which job did what, instead of a long AWS role ARN.

::: gotcha
**`InvalidParameterException: The specified principalArn is invalid: invalid principal.`** IAM is
eventually consistent, so a role created only seconds ago may not yet be visible everywhere. Wait
about 20 seconds and re-run the same command.
:::

## Step 5 - Add the Group subject to RBAC

Open `rbac.yaml` and add a second subject under `subjects:` of **both** RoleBindings, after the
existing ServiceAccount entry:

```yaml
  - kind: Group
    apiGroup: rbac.authorization.k8s.io
    name: cicd
```

```bash
kubectl apply -f rbac.yaml
```

```
namespace/staging unchanged
namespace/production unchanged
namespace/cicd unchanged
serviceaccount/gitlab-ci unchanged
rolebinding.rbac.authorization.k8s.io/cicd configured
rolebinding.rbac.authorization.k8s.io/cicd configured
```

The ServiceAccount from the previous handout and this new EKS role now share exactly the same
permissions, through the same two RoleBindings.

## Step 6 - Ask Kubernetes what the group can do

You can't sign in as this role from your own terminal (only a real GitLab job can request its token),
but as cluster admin you can ask Kubernetes what a member of `cicd` is permitted to do:

```bash
kubectl auth can-i create deployments --namespace production --as gitlab-ci:test --as-group cicd
```

→ `yes`

```bash
kubectl auth can-i list pods --namespace kube-system --as gitlab-ci:test --as-group cicd
```

→ `no`

## Cleaning up

Keep the OIDC provider, the role, the access entry and `rbac.yaml`: the rest of this section's
handouts build on all of them, ending with the production release lecture, which deletes everything at
once. If you are stopping here for good, remove what this handout built:

```bash
aws eks delete-access-entry --cluster-name basic-cluster --principal-arn "arn:aws:iam::${ACCOUNT_ID}:role/gitlab-weatherapp-deployer"
aws iam delete-role-policy --role-name gitlab-weatherapp-deployer --policy-name eks-describe-cluster
aws iam delete-role --role-name gitlab-weatherapp-deployer
aws iam delete-open-id-connect-provider --open-id-connect-provider-arn "arn:aws:iam::${ACCOUNT_ID}:oidc-provider/gitlab.com"
```

Only delete the OIDC provider if no other role in your account trusts `gitlab.com`.

## Traps

::: gotcha
**`EntityAlreadyExists: Provider with url https://gitlab.com already exists.`** Your account already
registered `gitlab.com` as a provider, from an earlier attempt, or another project entirely. Skip
Step 1 and reuse the existing provider; do not delete it unless you are certain nothing else trusts it.
:::

::: gotcha
**It's worth remembering that a GitLab project's path can, in principle, be reused after the project
behind it is deleted.** GitLab.com itself now also refuses ID tokens to a recreated project at a path
that had already issued tokens (the job fails with `id_token_burned_project_path`). Even so, once your
project genuinely exists, the next handout in this section narrows this trust policy further with the
project's permanent numeric ID. Belt and braces is still worth having.
:::
