Handing a CI pipeline your own admin kubeconfig means anyone who can edit the pipeline file can do
anything to your cluster. This handout builds a separate identity for the pipeline instead: a
ServiceAccount that lives in its own namespace, bound by RBAC to exactly two target namespaces, and a
kubeconfig built from a short-lived token rather than a certificate. This approach works on any
Kubernetes cluster, EKS or otherwise. The next handout adds an EKS-specific shortcut on top of it.

## Before you start

You need the EKS cluster from earlier in this course, brought back with the same two files used to
build it originally:

```bash
cd ~/devops-projects/s01-l04
export AWS_PROFILE=<your-aws-profile>
eksctl create cluster -f cluster.yaml
eksctl create addon -f addons.yaml
```

The cluster create takes about 15 minutes and the add-ons another minute and a half; both commands
return without printing your account ID. Confirm the cluster is ready:

```bash
kubectl get nodes
```

Expect three nodes, `Ready`, running a `v1.36.x-eks-…` kubelet version.

## Step 1 - Why a separate identity

When you run `kubectl` and Helm by hand on your own machine, you are cluster admin. A CI pipeline runs
on someone else's servers, on every commit, and a leaked or misconfigured pipeline file should never
be able to reach further than the two namespaces it actually deploys to. The fix is a Kubernetes-native
identity: a ServiceAccount that RBAC can scope down before the pipeline ever asks for a token.

## Step 2 - Write `rbac.yaml`

```bash
mkdir -p ~/devops-projects/s04 && cd ~/devops-projects/s04
```

Create `rbac.yaml`:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: staging
---
apiVersion: v1
kind: Namespace
metadata:
  name: production
---
apiVersion: v1
kind: Namespace
metadata:
  name: cicd
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: gitlab-ci
  namespace: cicd
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: cicd
  namespace: staging
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: edit
subjects:
  - kind: ServiceAccount
    name: gitlab-ci
    namespace: cicd
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: cicd
  namespace: production
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: edit
subjects:
  - kind: ServiceAccount
    name: gitlab-ci
    namespace: cicd
```

Three namespaces: `staging` and `production` are where the pipeline will deploy; `cicd` only holds the
pipeline's own identity. The built-in `edit` ClusterRole can manage Deployments, StatefulSets,
Services, Secrets, PVCs and ServiceAccounts inside a namespace (everything Helm needs for a chart
install), but it cannot create namespaces or touch RBAC itself. Each RoleBinding grants `edit` in one
target namespace to the `gitlab-ci` ServiceAccount that lives in `cicd`.

## Step 3 - Apply it

```bash
kubectl apply -f rbac.yaml
```

```
namespace/staging created
namespace/production created
namespace/cicd created
serviceaccount/gitlab-ci created
rolebinding.rbac.authorization.k8s.io/cicd created
rolebinding.rbac.authorization.k8s.io/cicd created
```

```bash
kubectl get namespaces
```

`cicd`, `production` and `staging` should all read `Active`, alongside the cluster's built-in
namespaces.

## Step 4 - Mint the token

```bash
TOKEN=$(kubectl create token gitlab-ci --namespace cicd --duration 720h)
```

`--duration 720h` asks for a token good for thirty days. On EKS, that request is capped:

```
Warning: requested expiration of 2592000 seconds shortened to 86400 seconds
```

**EKS caps service-account tokens at 24 hours, no matter what duration you ask for.** On a kops or
kubeadm cluster the same command really does return a token valid for the full thirty days. Whichever
cluster you are on, someone has to renew the token before it expires (daily on EKS, monthly
elsewhere), which is the tradeoff for never handing CI a long-lived credential.

## Step 5 - Build the kubeconfig

```bash
SERVER=$(kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}')
kubectl config view --minify --raw -o jsonpath='{.clusters[0].cluster.certificate-authority-data}' | base64 -d > ca.crt
kubectl config set-cluster basic-cluster --server="$SERVER" --certificate-authority=ca.crt --embed-certs --kubeconfig=gitlab-ci.kubeconfig
kubectl config set-credentials gitlab-ci --token="$TOKEN" --kubeconfig=gitlab-ci.kubeconfig
kubectl config set-context gitlab-ci --cluster=basic-cluster --user=gitlab-ci --namespace=staging --kubeconfig=gitlab-ci.kubeconfig
kubectl config use-context gitlab-ci --kubeconfig=gitlab-ci.kubeconfig
```

```
Cluster "basic-cluster" set.
User "gitlab-ci" set.
Context "gitlab-ci" created.
Switched to context "gitlab-ci".
```

Every command carries its own `--kubeconfig=gitlab-ci.kubeconfig`, so none of this touches your own
admin config. `ca.crt` and `gitlab-ci.kubeconfig` now sit beside `rbac.yaml`.

::: gotcha
**Never run `cat gitlab-ci.kubeconfig` or `echo $TOKEN`.** The kubeconfig embeds the bearer token in
plain text; anyone who reads it can act as the pipeline until the token expires.
:::

## Step 6 - Prove what the identity can do

```bash
kubectl auth whoami --kubeconfig=gitlab-ci.kubeconfig
```

Returns a table naming `Username  system:serviceaccount:cicd:gitlab-ci`, a UID, and
`Groups  [system:serviceaccounts system:serviceaccounts:cicd system:authenticated]`.

```bash
kubectl get pods --kubeconfig=gitlab-ci.kubeconfig
kubectl get pods --namespace production --kubeconfig=gitlab-ci.kubeconfig
```

Both print `No resources found in <namespace> namespace.`: nothing is deployed yet, but the identity
can at least look.

```bash
kubectl get pods --namespace kube-system --kubeconfig=gitlab-ci.kubeconfig
```

The real failure this identity is supposed to hit:

```
Error from server (Forbidden): pods is forbidden: User "system:serviceaccount:cicd:gitlab-ci" cannot list resource "pods" in API group "" in the namespace "kube-system"
```

That `Forbidden` is the RBAC boundary working exactly as designed: the ServiceAccount has no
RoleBinding into `kube-system`, so it cannot even read there, let alone change anything.

```bash
kubectl auth can-i create deployments --namespace production --kubeconfig=gitlab-ci.kubeconfig
```

→ `yes`. And the one that is worth reading twice:

```bash
kubectl auth can-i create namespaces --kubeconfig=gitlab-ci.kubeconfig
```

```
Warning: resource 'namespaces' is not namespace scoped
no
```

The warning appears because the context's default namespace is `staging`, and `Namespace` is a
cluster-scoped resource: Kubernetes is telling you the question itself doesn't quite make sense
namespaced, then answers it anyway: `no`. This identity cannot create namespaces at all.

## Cleaning up

```bash
rm gitlab-ci.kubeconfig ca.crt
```

Keep `rbac.yaml` and the cluster itself: the next handout in this section builds on both. If you are
not moving straight on, delete the cluster to stop it billing:

```bash
cd ~/devops-projects/s01-l04
eksctl delete cluster -f cluster.yaml --wait
```

## Traps

::: gotcha
**`kubectl create token` fails with `serviceaccounts "gitlab-ci" not found`.** `rbac.yaml` was never
applied, or you ran the command from a different folder than the one `rbac.yaml` lives in. Re-run
`kubectl apply -f rbac.yaml` from `~/devops-projects/s04`, then mint the token again.
:::

::: gotcha
**`kubectl auth whoami` shows an `arn:aws:sts::…` user instead of the ServiceAccount.** A command was
run without `--kubeconfig=gitlab-ci.kubeconfig`, so it used your own admin credentials instead of the
pipeline identity's. Add the flag and retype the command.
:::
