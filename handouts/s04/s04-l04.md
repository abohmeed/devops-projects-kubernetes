The previous handout pushed WeatherApp to GitLab. The AWS role from earlier in this section is already
waiting for this project, but the pipeline still needs things that must never live in the repository
itself: a Docker Hub token, and the app's own passwords. This handout locks the AWS trust
to the exact project, gives GitLab the settings and secrets the pipeline needs, and proves with a first
job that GitLab can reach the cluster without a single stored key.

## Before you start

You need the GitLab project and AWS role from the earlier handouts in this section, and a Docker Hub
personal access token with Read & Write scope (Docker Hub → Account Settings → Security → New Access
Token). Export the same variables you exported when the role was created:

```bash
cd ~/devops-projects/s04
export AWS_PROFILE=<your-aws-profile>
export AWS_REGION=us-east-1
export ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
export GITLAB_PROJECT_PATH=<your-group>/weatherapp
```

## Step 1 - Pin the trust to the project's numeric ID

A project's path is really just a name, and in principle a name can be reused once the project behind
it is deleted. Pin the trust to the project's numeric ID instead, which never changes for the life of
the project. On the project page: **Actions** (⋮) → **Copy project ID**.

```bash
export GITLAB_PROJECT_ID=<the-project-id-you-copied>
```

Open `trust-policy.json` and add one line to the `StringEquals` block, after the `aud` line:

```json
          "gitlab.com:project_id": "${GITLAB_PROJECT_ID}",
```

```bash
aws iam update-assume-role-policy --role-name gitlab-weatherapp-deployer --policy-document "$(envsubst < trust-policy.json)"
```

No output means it worked.

## Step 2 - Protect tags

**Settings** → **Repository** → **Protected tags** → **Add new**. In **Tag**, type `*` and click
**Create wildcard**; **Allowed to create** → **Maintainers**; click **Protect**.

The role's trust policy only trusts protected refs, and GitLab only hands protected variables to
protected branches and tags. `main` is already protected by default, but the version tags created
later in this section need the same protection or the pipeline won't have what it needs when it gets
there.

## Step 3 - Create the seven variables

**Settings** → **CI/CD** → **Variables** → **Add variable** for each row below. Set **Visibility**,
tick **Protect variable** where the table says to, leave **Expand variable reference** unticked, and
leave **Type** as `Variable` and **Environments** as `All (default)`.

| Key | Value | Protect variable | Visibility |
|---|---|---|---|
| `DOCKERHUB_USER` | your Docker Hub username | unticked | Visible |
| `DOCKERHUB_TOKEN` | Docker Hub token, Read & Write | ticked | Masked and hidden |
| `AWS_ROLE_ARN` | `arn:aws:iam::<your-account-id>:role/gitlab-weatherapp-deployer` | ticked | Masked |
| `JWT_SECRET` | `openssl rand -hex 32` | ticked | Masked and hidden |
| `DB_ROOT_PASSWORD` | `openssl rand -hex 16` | ticked | Masked and hidden |
| `DB_PASSWORD` | `openssl rand -hex 16` | ticked | Masked and hidden |
| `WEATHER_CONTACT` | your email address or a link to your project (not a secret; MET Norway asks every app for one) | ticked | Visible |

**Masked** means GitLab replaces the value with `[MASKED]` wherever it would otherwise show up in a
job log. **Hidden** means nobody, including you, can read the value back from this page again once
it's saved. `AWS_ROLE_ARN` is not a secret on its own, but it does contain your account number, so it
is masked too.

::: gotcha
**Keep `JWT_SECRET`, `DB_ROOT_PASSWORD` and `DB_PASSWORD` for the life of the deployment.** MySQL only
reads its passwords the first time it starts. Change either database password after that and the app
is locked out of its own database.
:::

Notice what is **not** on this list: no AWS access keys, and no kubeconfig. And variable names accept
only letters, digits and underscores: a dash isn't allowed (trying a key like `K8S-CONFIG` is refused
with `can contain only letters, digits and '_'.`).

## Step 4 - What the pipeline will do

Before writing it, the plan in one paragraph: on a merge request, it builds the three images just to
prove the change still builds. On `main`, it builds and pushes those images tagged with the short
commit ID, then deploys that exact tag to `staging`. On a version tag such as `1.0.0`, it copies those
already-tested images to the tag `1.0.0` and deploys to `production`, but only when someone presses a
button. That manual step is what makes this **continuous delivery** rather than continuous deployment.

## Step 5 - Write `.gitlab-ci.yml`

At the root of the repository, create `.gitlab-ci.yml`:

```yaml
.deploy:
  image:
    name: amazon/aws-cli:2.37.4
    entrypoint: [""]
  id_tokens:
    GITLAB_OIDC_TOKEN:
      aud: https://gitlab.com
  variables:
    AWS_REGION: us-east-1
    CLUSTER_NAME: basic-cluster
    AWS_WEB_IDENTITY_TOKEN_FILE: /tmp/web-identity-token
    AWS_ROLE_SESSION_NAME: gitlab-$CI_JOB_ID
    HELM_VERSION: v4.3.0
    HELM_SHA256: 86584a54def73570558f66f5111cc53dfed56689637ae32c1201205d494f54fb
  before_script:
    - echo "$GITLAB_OIDC_TOKEN" > "$AWS_WEB_IDENTITY_TOKEN_FILE"
    - dnf install -y -q tar gzip
    - curl -fsSL -o /tmp/helm.tar.gz "https://get.helm.sh/helm-${HELM_VERSION}-linux-amd64.tar.gz"
    - echo "${HELM_SHA256}  /tmp/helm.tar.gz" | sha256sum -c -
    - tar -xzf /tmp/helm.tar.gz -C /tmp
    - mv /tmp/linux-amd64/helm /usr/local/bin/helm
    - aws eks update-kubeconfig --name "$CLUSTER_NAME" --region "$AWS_REGION" --alias "$CLUSTER_NAME"

check-access:
  extends: .deploy
  script:
    - helm version
    - helm list --namespace staging
    - helm list --namespace production
    - |
      if helm list --namespace kube-system; then
        echo "kube-system should be off limits to this pipeline"
        exit 1
      fi
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
```

`.deploy` is a **template**: the leading dot means it isn't a job on its own; later jobs in this
section reuse it with `extends`. It runs on the official AWS CLI image. The `id_tokens` block asks
GitLab for a token with the audience `https://gitlab.com`, the value AWS expects. Two variables tell
the AWS CLI to assume the role in `AWS_ROLE_ARN` (set in Step 3) using the token GitLab just wrote to a
file: no access key involved anywhere. After that, it downloads Helm at a pinned version and checks
it against its published checksum before trusting it, then runs `aws eks update-kubeconfig` so
`kubectl` and Helm both know how to reach the cluster. `check-access` lists Helm releases in `staging`
and `production`, and also tries `kube-system`, where it must be refused.

## Step 6 - Run it for the first time

```bash
cd ~/weatherapp
git add .gitlab-ci.yml
git commit -m "Add a pipeline that checks cluster access"
git push
```

In GitLab: **Build** → **Pipelines** → the newest pipeline → open the `check-access` job. In the log:

```
$ helm version
version.BuildInfo{Version:"v4.3.0", …}
```

Then two empty lists (nothing deployed yet), and the real failure this job is hoping for:

```
Error: list: failed to list: secrets is forbidden: User "gitlab-ci:gitlab-<job id>" cannot list resource "secrets" in API group "" in the namespace "kube-system"
```

...followed by `Job succeeded`. The user name in that error is the access entry's username combined
with this job's own session name (proof the whole chain worked): GitLab proved who it was, AWS handed
it a role for the run, EKS placed it in the `cicd` group, and RBAC fenced it in to exactly the
namespaces it should reach.

## Cleaning up

Nothing to remove: keep the pipeline file, the variables and the protected tag; the rest of this
section builds on all three. If you are stopping here for good, remove the variables and protected tag
from **Settings** and revoke the Docker Hub token from Docker Hub's Security page.

## Traps

::: gotcha
**`An error occurred (AccessDenied) when calling the AssumeRoleWithWebIdentity operation: Not
authorized…`** The trust doesn't match: wrong `project_id`, wrong path, or the job ran on an
unprotected ref. Check `aws iam get-role --role-name gitlab-weatherapp-deployer` and re-run the job.
:::

::: gotcha
**`sha256sum: WARNING: 1 computed checksum did NOT match`** A typo in `HELM_SHA256`. Fix the value in
the file and push again, never skip the checksum check to work around it.
:::
