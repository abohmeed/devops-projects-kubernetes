The previous handout proved GitLab can reach the cluster with no stored key. But there is nothing to
deploy yet: the images on Docker Hub still show the version pushed by hand earlier in this course, and
everything since then lives only in git history. This handout puts the pipeline's first real stage in
place: build on every merge request, and build-and-push on every change that lands on `main`.

## Before you start

You need `.gitlab-ci.yml` from the previous handout, already pushed, with a green `check-access` job.

```bash
cd ~/weatherapp
git log --oneline -1
```

Should show `Add a pipeline that checks cluster access`.

## Step 1 - Remove `check-access`, keep `.deploy`

Open `.gitlab-ci.yml`. Delete the entire `check-access:` job: it already proved the chain works.
Leave `.deploy:` exactly as it is; the delivery stage a later handout adds will put it to work.

## Step 2 - Decide when a pipeline should even run

At the top of the file:

```yaml
workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

stages:
  - build
  - push
```

Anything else (pushing to a feature branch with no merge request open, for instance) runs nothing at
all. Every pipeline that ever runs in this project now has a reason to exist, and no compute minutes
are spent on ones nobody asked for. `stages` orders execution: jobs in the same stage run in parallel,
and the next stage only starts once every job in the previous one has succeeded.

## Step 3 - A shared Docker template

Before `.deploy`, add:

```yaml
.docker:
  image: docker:29.8.1-cli
  services:
    - docker:29.8.1-dind
  variables:
    DOCKER_TLS_CERTDIR: "/certs"
```

The job container gives you the Docker client; the `dind` (Docker-in-Docker) service next to it runs an
actual Docker engine, and the two talk over TLS using certificates GitLab shares between them through
`DOCKER_TLS_CERTDIR`. The version is pinned rather than `latest`, since a moving tag can change under
you without warning.

## Step 4 - The `build` job

At the end of the file:

```yaml
build:
  extends: .docker
  stage: build
  script:
    - docker build --tag weatherapp-auth auth
    - docker build --tag weatherapp-ui UI
    - docker build --tag weatherapp-weather weather
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
```

`build` runs only on merge requests. It doesn't log in anywhere and doesn't push anything. It answers
exactly one question: does this change still build?

## Step 5 - The `push` job

```yaml
push:
  extends: .docker
  stage: push
  script:
    - echo "$DOCKERHUB_TOKEN" | docker login --username "$DOCKERHUB_USER" --password-stdin
    - docker build --tag "$DOCKERHUB_USER/weatherapp-auth:$CI_COMMIT_SHORT_SHA" auth
    - docker push "$DOCKERHUB_USER/weatherapp-auth:$CI_COMMIT_SHORT_SHA"
    - docker build --tag "$DOCKERHUB_USER/weatherapp-ui:$CI_COMMIT_SHORT_SHA" UI
    - docker push "$DOCKERHUB_USER/weatherapp-ui:$CI_COMMIT_SHORT_SHA"
    - docker build --tag "$DOCKERHUB_USER/weatherapp-weather:$CI_COMMIT_SHORT_SHA" weather
    - docker push "$DOCKERHUB_USER/weatherapp-weather:$CI_COMMIT_SHORT_SHA"
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
```

`push` runs only on the default branch. `--password-stdin` pipes the token in through standard input,
so it never touches the command line or a shell history. Every image is tagged
`$DOCKERHUB_USER/weatherapp-<service>:$CI_COMMIT_SHORT_SHA`: the short commit ID ties every image
straight back to the commit that produced it, and the promotion and deploy stages added later in this
section key off this exact same tag. A moving tag like `latest` could never tell you what is actually
deployed.

## Step 6 - Push straight to `main` the first time

```bash
git add .gitlab-ci.yml
git commit -m "Build on merge requests, push on main"
git push
```

This first change goes straight to `main`, since the merge check isn't turned on yet and the pipeline
file itself has to reach `main` somehow. In GitLab, **Build** → **Pipelines**: the newest pipeline runs
a single stage, `push`, and finishes green.

## Step 7 - Turn on the merge check

**Settings** → **Merge requests** → **Merge checks** → tick **Pipelines must succeed** → **Save
changes**. From now on nothing merges into `main` unless its pipeline passes.

## Step 8 - A real change through a merge request

```bash
git switch -c login-heading
```

In `UI/public/login.html`, change:

```html
        <h2 class="form-signin-heading">Sign in to the Weather App</h2>
```

```bash
git add UI/public/login.html
git commit -m "Change the login heading"
git push -u origin login-heading
```

```
remote:
remote: To create a merge request for login-heading, visit:
remote:   https://gitlab.com/<your-group>/weatherapp/-/merge_requests/new?merge_request%5Bsource_branch%5D=login-heading
remote:
```

Open that link, click **Create merge request**. No pipeline runs for the bare branch push: the
`workflow` rules only fire on a merge request event or on `main`. In the merge request, the pipeline
widget shows only **build**, since `push` only ever runs on `main`.

## Step 9 - Merge and watch `push` run

Click **Set to auto-merge**. Once the `build` pipeline passes, GitLab merges the branch on its own and
deletes the source branch. On `main`, the pipeline now runs **push**. Watch it finish green under
**Build** → **Pipelines**.

## Step 10 - Confirm the image landed on Docker Hub

```bash
git switch main
git pull
```

```
Fast-forward
UI/public/login.html | 2 +-
```

```bash
git rev-parse --short=8 HEAD
```

Eight hex characters: the same length GitLab uses (a plain `git log --oneline` can show as few as
seven).

```bash
export DOCKERHUB_USER=<your-dockerhub-username>
docker buildx imagetools inspect $DOCKERHUB_USER/weatherapp-ui:<the-eight-char-sha>
```

```
Name:      docker.io/<your-dockerhub-username>/weatherapp-ui:<sha>
MediaType: application/vnd.docker.distribution.manifest.v2+json
Digest:    sha256:eb772ab0…
```

The `Name` line is the image the pipeline put there, not you.

Nothing to remove: keep `.gitlab-ci.yml`, the merge check, and the images on Docker Hub. This

## Traps

::: gotcha
**`push` fails with `unauthorized: incorrect username or password`.** `DOCKERHUB_TOKEN` is wrong, or
the token is read-only rather than Read & Write. Regenerate the token on Docker Hub with Read & Write
scope, update the CI/CD variable, and retry the job.
:::

::: gotcha
**`toomanyrequests: You have reached your pull rate limit`.** Anonymous Docker Hub pulls on a merge
request job (the `build` job never logs in) can hit Docker Hub's rate limit under heavy use. Wait a
minute and retry the job.
:::
