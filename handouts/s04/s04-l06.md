The previous handout finished the build-and-push stage: every change reaching `main` now ends with
three new images on Docker Hub, each tagged with its commit ID. But images sitting on a registry don't
run anywhere on their own: someone would still have to run three `helm upgrade --install` commands by
hand, typing the tag and five secrets every time. This handout adds the second stage, so every change
that reaches `main` deploys to `staging` automatically.

## Before you start

You need `.gitlab-ci.yml` from the previous handout, with a green `push` job on `main` and the merge
check turned on.

```bash
cd ~/weatherapp
git switch main
git pull
git switch -c deliver-stage
```

## Step 1 - The shared deploy script

Open `.gitlab-ci.yml`. Under `.deploy`, after the last `before_script` line
(`aws eks update-kubeconfig …`), add:

```yaml
  script:
    - >
      helm upgrade --install weatherapp-auth ./weatherapp-auth
      --namespace "$NAMESPACE"
      --set image.repository="$DOCKERHUB_USER/weatherapp-auth"
      --set image.tag="$IMAGE_TAG"
      --set jwtSecret="$JWT_SECRET"
      --set mysql.auth.rootPassword="$DB_ROOT_PASSWORD"
      --set mysql.auth.password="$DB_PASSWORD"
      --wait --rollback-on-failure --timeout 10m
    - >
      helm upgrade --install weatherapp-weather ./weatherapp-weather
      --namespace "$NAMESPACE"
      --set image.repository="$DOCKERHUB_USER/weatherapp-weather"
      --set image.tag="$IMAGE_TAG"
      --set apikey="$WEATHER_API_KEY"
      --wait --rollback-on-failure --timeout 5m
    - >
      helm upgrade --install weatherapp-ui ./weatherapp-ui
      --namespace "$NAMESPACE"
      --set image.repository="$DOCKERHUB_USER/weatherapp-ui"
      --set image.tag="$IMAGE_TAG"
      --set jwtSecret="$JWT_SECRET"
      --wait --rollback-on-failure --timeout 5m
```

These are the same three `helm upgrade --install` commands from earlier in this course, but nothing
here hardcodes a namespace or a tag: each reads `--namespace "$NAMESPACE"` and
`--set image.tag="$IMAGE_TAG"`, so the job using this template decides both. `jwtSecret` is set to the
same value in both the auth chart and the UI chart, since auth signs the login token and the UI checks
it. The leading `>` folds each long command over several lines so it reads without scrolling sideways.

This script lives in the **template** rather than in a job directly, because the production job added
in the next handout runs these exact same commands, only against a different namespace and tag: write
it once here, reuse it twice.

Two flags matter more than the rest: without `--wait`, Helm reports a release as deployed the moment
Kubernetes accepts the objects, even if the pods behind it then crash. With `--wait`, Helm stays and
watches until the pods are actually ready. With `--rollback-on-failure`, if they never become ready
within the timeout, Helm puts the previous working release back and **fails the job**. A red pipeline
here does not mean staging is broken: it means staging is still on the last good version. (If you've
used Helm 3, this used to be one flag, `--atomic`; Helm 4 renamed it to `--rollback-on-failure`.) `auth`
gets a longer `--timeout 10m` since, on a first install, MySQL has to initialize a new volume before
auth can even start.

## Step 2 - The `deliver` job

Add `deliver` to `stages`, after `push`:

```yaml
stages:
  - build
  - push
  - deliver
```

At the end of the file:

```yaml
deliver:
  extends: .deploy
  stage: deliver
  environment:
    name: staging
  resource_group: staging
  variables:
    NAMESPACE: staging
    IMAGE_TAG: $CI_COMMIT_SHORT_SHA
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
```

`environment: name: staging` does **not** create the `staging` namespace: that namespace already
exists from the RBAC handout earlier in this section. What it does is give GitLab its own record of the
deployment: which commit produced it and when it ran. `resource_group: staging` makes sure that if two
merges land close together, their deploys queue up one after another instead of racing inside the same
namespace.

## Step 3 - A visible change, and ship it

In `UI/public/login.html`, change the login button's class:

```html
        <button class="btn btn-lg btn-success btn-block" id="login" type="submit">Sign in</button>
```

```bash
git add .gitlab-ci.yml UI/public/login.html
git commit -m "Deliver every change on main to staging"
git push -u origin deliver-stage
```

Open the merge-request link GitLab prints, click **Create merge request**, then **Set to auto-merge**.
The MR's pipeline shows only **build**, since `deliver` is still restricted to `main`. Once it merges,
`main` runs both **push** and **deliver**.

## Step 4 - Read the `deliver` job's log

Open the `deliver` job. It signs in with the OIDC role, updates the kubeconfig
(`Added new context basic-cluster to /root/.kube/config`), then:

```
$ helm upgrade --install weatherapp-auth …
Release "weatherapp-auth" does not exist. Installing it now.
```

The first install takes a minute or two, since MySQL is initializing its volume. The log ends with all
three releases' `STATUS: deployed` blocks and `Job succeeded`.

## Step 5 - Confirm it as admin

```bash
kubectl get pods --namespace staging
```

Seven pods, all `1/1 Running`: two each of the auth, UI and weather pods, plus
`weatherapp-auth-mysql-0`: every chart in this course runs two replicas.

```bash
helm list --namespace staging
```

Three releases, `REVISION 1`, `STATUS deployed`.

```bash
kubectl get pvc --namespace staging
```

```
data-weatherapp-auth-mysql-0   Bound   pvc-…   8Gi   RWO   ebs-csi-default-sc
```

That's the disk auth's MySQL is actually writing to.

```bash
kubectl get svc weatherapp-ui --namespace staging
```

A `LoadBalancer` Service with an `EXTERNAL-IP` hostname ending `.elb.amazonaws.com`.

## Step 6 - Open the app

Once the hostname resolves (allow a minute or two after the Service first appears), open
`http://<the-hostname>` in a browser. The login heading and green **Sign in** button should be there
from the earlier changes. Sign up with a user name and password, sign in, and look up a city: the
current weather should come back.

## Step 7 - The GitLab environment

In GitLab: **Operate** → **Environments** → `staging`. One deployment is listed, with the commit that
produced it and the job that ran it (`deliver`). This is the same page the next handout in this section
uses to release, and later to roll back, production.

## Cleaning up

Nothing to remove: keep the `staging` deployment running. The final handout in this section tears
everything down as part of finishing the whole pipeline.

## Traps

::: gotcha
**`deliver` fails with `Error: … forbidden: User "gitlab-ci:gitlab-…" cannot create resource …`.** The
RBAC Group subject is missing from a RoleBinding: re-apply `rbac.yaml` from the earlier handouts in
this section, then retry the job.
:::

::: gotcha
**`Error: … context deadline exceeded` from `--rollback-on-failure`.** A pod never became ready inside
the timeout: a missing image tag, or MySQL taking longer than expected. Check
`kubectl get pods --namespace staging` for the real cause before retrying.
:::
