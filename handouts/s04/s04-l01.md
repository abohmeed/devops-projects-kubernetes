## The problem this section solves

Picture a small team that only brings its work together once, at release time, maybe once a
quarter. Each person's changes sat untested against everyone else's for weeks or months. The first
moment the whole codebase actually ran together was the day it shipped, which is also the worst
possible moment to discover it does not work.

That late discovery has a predictable shape:

- Bugs that only show up once several people's changes meet are found late, when they are
  expensive to trace and fix.
- Quality checks often run on infrastructure that does not resemble the real production
  environment, so passing those checks is not the same as being safe to ship.
- A release becomes an event: a scheduled window of downtime long enough to install everything and,
  if it goes wrong, undo it again.

None of this scales against how fast users now expect software to move. A mobile app that pushes a
small update every week can fix problems and add value faster than a competitor still working in
quarterly cycles. Slow, infrequent, all-or-nothing releases stopped being a viable way to compete.

::: keyconcept
The root cause in every symptom above is the same: code from different people is combined and
tested too rarely, and too late. Everything CI/CD does is aimed at shrinking that gap between
"written" and "combined and verified."
:::

## Continuous integration: merge early, verify automatically

**Continuous integration (CI)** is the practice of merging every developer's changes into one
shared codebase frequently, at least once a day, rather than letting them diverge for weeks. Each
time someone merges, an automated process builds the project and runs its test suite against the
result. If the build or a test fails, the person who merged that change gets the feedback and fixes
it before moving on.

A common misunderstanding is worth clearing up directly: the word **integration** in "continuous
integration" does not describe a type of test. It describes the act of bringing each person's code
together into the shared codebase. The build and tests that run afterward are simply how that
integration gets *verified* automatically, whatever kind of tests the project happens to have.

Practiced consistently, CI gives a team two guarantees that a quarterly release cycle cannot:

1. The shared codebase reflects everyone's latest work, not a snapshot from weeks ago.
2. That shared codebase is, at (almost) any point in time, in a state that could be released,
   because it was verified the moment it was assembled.

| Without CI | With CI |
|---|---|
| Changes combine for the first time at release | Changes combine the same day they are written |
| A broken combination is found at release time | A broken combination is found within one build |
| "Does it still work together" is a question asked rarely | "Does it still work together" is answered on every merge |

## Making realistic test environments affordable

A second obstacle to shipping often stood in the way even after CI caught bugs early: a test
environment that behaves like production used to be expensive to build and keep up to date, so
teams tested somewhere that did not quite match reality. Two ideas from earlier lessons in this
course remove that obstacle.

First, a container image is built once, from one Dockerfile, and that exact image is what moves
forward: the same bytes that were tested are the ones that eventually run in production, rather
than an environment being rebuilt by hand for every stage. Second, a Kubernetes cluster can host
several isolated environments as separate namespaces on the same cluster, rather than needing
separate hardware for each one. Together, this makes production-like test environments cheap enough
to have for every change, not just for the occasional big release.

::: gotcha
Sharing one cluster across environments through namespaces is possible, including putting
production on it alongside development and testing, but it is not something to do casually. This
handout only says it is possible; deciding whether to do it is a judgment call this course does not
make for you here.
:::

## Continuous delivery vs. continuous deployment

Once a change has passed continuous integration, it can move on to one or more test-like
environments automatically. From there, two paths are possible, and they are easy to confuse
because they look identical right up until the last step.

| | Continuous delivery | Continuous deployment |
|---|---|---|
| Change passes CI and moves through test-like environments | Automatic | Automatic |
| Final release to production | **Waits for a person to approve it** | Fully automatic, no approval step |

That is the entire difference. If you are ever unsure which term applies to a given setup, ask one
question: **is there a human approval before production?** A yes means continuous delivery. A no
means continuous deployment.

Neither choice is objectively better. Teams that keep a manual approval usually do so for business
or compliance reasons; teams that remove it are betting that their automated checks are trustworthy
enough to skip a human gate. Both are valid engineering decisions, and which one a given team picks
depends on what that team and its business need, not on which term sounds more advanced.

As with continuous integration, a failure at any stage along this path sends the change back to
whoever authored it, rather than letting a broken change continue forward.

## What a pipeline is

A CI/CD tool is the piece of software that coordinates everything above: it talks to your version
control system, triggers builds, pushes images to a registry, deploys to a cluster, and runs your
tests, instead of a person running each of those tools by hand in sequence. The sequence of
automated steps that the tool runs from start to finish is called a **pipeline**. A pipeline is
usually triggered by an event in your source repository, such as a new commit or a merge request,
though it can also be started manually.

Any task you have previously done by hand at a terminal, such as building an image, pushing it to a
registry, or upgrading a release on a cluster, is exactly the kind of task a pipeline step
automates. This course uses **GitLab CI/CD** as its pipeline tool for the rest of this section.
