A volume snapshot protects one disk. It does not protect the Deployments, Services and Secrets
around that disk, its catalog lives inside the cluster it was taken on, and the EBS snapshot itself
never leaves the Region. Velero closes that gap: it is a server that runs inside your cluster plus a
CLI you run from your own terminal, and when you ask for a backup it creates a Kubernetes object
called a `Backup`. The server reads your cluster's objects through the API and writes them out to an
S3 bucket via the AWS plugin. For the data sitting on your volumes, Velero asks the CSI driver for a
snapshot, then its data mover (a tool called Kopia, run by a pod called the node agent on every
node) copies the snapshot's contents into the same bucket and removes the temporary snapshot when it
is done. Copying into S3 (rather than trusting the EBS snapshot alone) gives you both a single
consistent point in time, and data any cluster able to read the bucket can restore.

## Before you start

You need the EKS cluster and the WeatherApp from the previous handouts in this section, with the
`ebs-snapclass` `VolumeSnapshotClass` already in place. You need `sudo` on the machine you are
working from, since installing the Velero CLI uses it.

```bash
export AWS_PROFILE=<your-aws-profile>
cd <your-s05-folder>
```

## Step 1 - Create the backup bucket

Bucket names are global across all of AWS, so generate one with a random suffix:

```bash
export BUCKET=weatherapp-velero-$(openssl rand -hex 4)
aws s3api create-bucket --bucket "$BUCKET" --region us-east-1
```

```json
{
    "Location": "/weatherapp-velero-bbf53e96",
    "BucketArn": "arn:aws:s3:::weatherapp-velero-bbf53e96"
}
```

In `us-east-1` there is no location constraint to pass. A new bucket is private by default, and its
objects are encrypted at rest, so neither has to be configured separately.

```bash
echo "$BUCKET"
```

Keep this name; it is pasted into three files below.

## Step 2 - The bucket policy

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "BackupObjects",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:DeleteObject",
        "s3:PutObject",
        "s3:AbortMultipartUpload",
        "s3:ListMultipartUploadParts"
      ],
      "Resource": "arn:aws:s3:::<BUCKET>/*"
    },
    {
      "Sid": "ListTheBucket",
      "Effect": "Allow",
      "Action": ["s3:ListBucket"],
      "Resource": "arn:aws:s3:::<BUCKET>"
    }
  ]
}
```

Replace `<BUCKET>` with the name from Step 1, in both places. Velero can get, put and delete objects
in the bucket, plus the two actions large uploads need (aborting and listing multipart uploads), and
it can list the bucket itself. There is no EC2 permission anywhere in this file: Velero never
touches EBS directly; the CSI driver takes the snapshots itself, through the Pod Identity role it
already has.

## Step 3 - The trust policy, and the role outside any cluster

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "VeleroPodsOnEKS",
      "Effect": "Allow",
      "Principal": {
        "Service": "pods.eks.amazonaws.com"
      },
      "Action": [
        "sts:AssumeRole",
        "sts:TagSession"
      ],
      "Condition": {
        "StringEquals": {
          "aws:RequestTag/kubernetes-namespace": "velero",
          "aws:RequestTag/kubernetes-service-account": "velero-server"
        }
      }
    }
  ]
}
```

This narrows who can assume the role to one service account, `velero-server`, in one namespace,
`velero`.

```bash
ROLE_ARN=$(aws iam create-role --role-name weatherapp-velero --assume-role-policy-document file://velero-trust-policy.json --query Role.Arn --output text)
aws iam put-role-policy --role-name weatherapp-velero --policy-name velero-s3 --policy-document file://velero-policy.json
```

Create this role deliberately outside of `eksctl`. If `eksctl` created it, it would live inside this
cluster's CloudFormation stack and be deleted the moment the cluster is. The whole point of a backup
is to outlive the cluster it protects, so the permission to read it has to outlive the cluster too.

```bash
aws eks create-pod-identity-association --cluster-name <YOUR_CLUSTER_NAME> --region us-east-1 --namespace velero --service-account velero-server --role-arn "$ROLE_ARN" --query association.associationId --output text
```

```
a-g1cle9jjyxe51cfy8
```

This association can exist before the service account it names actually does.

## Step 4 - Tell Velero which snapshot class to use

Open `volumesnapshotclass.yaml` from the previous handouts and add a label:

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: ebs-snapclass
  labels:
    velero.io/csi-volumesnapshot-class: "true"
driver: ebs.csi.aws.com
deletionPolicy: Delete
```

```bash
kubectl apply -f volumesnapshotclass.yaml
```

Only one class per driver should carry this label.

## Step 5 - Install the Velero CLI

```bash
curl -LO https://github.com/velero-io/velero/releases/download/v1.18.3/velero-v1.18.3-linux-amd64.tar.gz
curl -LO https://github.com/velero-io/velero/releases/download/v1.18.3/CHECKSUM
grep velero-v1.18.3-linux-amd64.tar.gz CHECKSUM | sha256sum -c -
```

```
velero-v1.18.3-linux-amd64.tar.gz: OK
```

A broken download is a far harder problem to chase later than it is to catch right now. Once the
checksum comes back clean:

```bash
tar -xzf velero-v1.18.3-linux-amd64.tar.gz
sudo install velero-v1.18.3-linux-amd64/velero /usr/local/bin/velero
velero version --client-only
```

```
Client:
	Version: v1.18.3
	Git commit: cd3fd10b093dad32ee284e27fcba4e9073c9c94b
```

## Step 6 - The Helm values

```yaml
# values.yaml
image:
  repository: docker.io/velero/velero
  tag: v1.18.3

initContainers:
  - name: velero-plugin-for-aws
    image: velero/velero-plugin-for-aws:v1.14.3
    imagePullPolicy: IfNotPresent
    volumeMounts:
      - mountPath: /target
        name: plugins

configuration:
  backupStorageLocation:
    - name: default
      provider: aws
      bucket: <BUCKET>
      default: true
      accessMode: ReadWrite
      config:
        region: us-east-1
  features: EnableCSI

snapshotsEnabled: false

deployNodeAgent: true
nodeAgent:
  disableHostPath: true

credentials:
  useSecret: false
serviceAccount:
  server:
    name: velero-server
```

Every line here is a decision. The AWS plugin is added as an init container: the piece that lets
Velero talk to S3 at all. `backupStorageLocation` is a **list** with one entry: an older version of
this chart read a single map here instead, and today's chart rejects that older shape with a schema
error (`got object, want array`). `features: EnableCSI` tells Velero to use CSI snapshots for volume
data, and `snapshotsEnabled: false` turns off Velero's own EBS snapshotter, since this handout uses
the data mover instead. `deployNodeAgent: true` installs the data mover with no host paths, since it
copies from a snapshot rather than reading live files off the node. `useSecret: false` means Pod
Identity supplies the credentials: there are no keys to manage. Replace `<BUCKET>` with your bucket
name before installing.

::: gotcha
**Never run `kubectl get secret -o yaml`, `helm get values`, or `aws iam get-role` without
`--query` here.** The role ARN carries your account id; only the association's id is safe to print.
:::

## Step 7 - Install with Helm

```bash
helm repo add vmware-tanzu https://vmware-tanzu.github.io/helm-charts
helm upgrade --install velero vmware-tanzu/velero --version 12.2.0 -n velero --create-namespace -f values.yaml
```

Pin the chart version rather than taking whatever happens to be latest.

```bash
kubectl get pods -n velero
```

```

node-agent-s4w2h          1/1     Running   0          16s
node-agent-w4lb4          1/1     Running   0          16s
```

## Step 8 - Confirm the whole chain

```bash
velero backup-location get
```

```
NAME      PROVIDER   BUCKET/PREFIX                PHASE       LAST VALIDATED                  ACCESS MODE   DEFAULT
default   aws        weatherapp-velero-bbf53e96   Available   2026-09-27 14:12:10 +0000 UTC   ReadWrite     true
```

If it says `Unknown`, wait ten seconds and rerun.

```bash
velero version
```

```
Client:
	Version: v1.18.3
	Git commit: cd3fd10b093dad32ee284e27fcba4e9073c9c94b
Server:
	Version: v1.18.3
```

`Available` means the server reached the bucket using the role you built: the bucket, the trust
policy, the role, and Pod Identity are all doing their job together.

::: keyconcept
**A nightly schedule is one command away.** `velero schedule create weatherapp-nightly --schedule="0 2 * * *" --include-namespaces weatherapp --snapshot-move-data` turns the manual backup in the next handout into a recurring job, with the same flags. Whatever schedule you set becomes your recovery point: a nightly schedule means you could lose up to a day of data.
:::

## Stopping here?

Velero, the bucket and the role are fine to leave in place if you are continuing to the next
handout, which uses them. To remove everything this handout created:

```bash
helm uninstall velero -n velero
kubectl delete namespace velero
aws s3 rb "s3://$BUCKET" --force
aws iam delete-role-policy --role-name weatherapp-velero --policy-name velero-s3
aws iam delete-role --role-name weatherapp-velero
```

## Traps

::: gotcha
**`helm upgrade --install` fails with `values don't meet the specifications of the schema(s) … got
object, want array`.** The `backupStorageLocation` block in `values.yaml` lost its leading `- ` and
became a map instead of a list. Fix the indentation and rerun.
:::

::: gotcha
**The backup location stays `Unavailable`.** Either the bucket name in `values.yaml` is mistyped, or
the Pod Identity association from Step 3 is missing. Run `velero backup-location get -o yaml` to
read the exact message, fix the cause, then rerun the `helm upgrade --install`.
:::

::: gotcha
**`create-pod-identity-association` returns `ResourceInUseException`.** An association for
`velero`/`velero-server` on this cluster already exists. Delete it before creating a new one, or
reuse the existing one.
:::
