Most real-world data loss is not a dead disk. It is a bad change: a migration that drops a table, or
a script that deletes the wrong rows. The application keeps running and the disk stays healthy, but
the data on it is gone. This handout damages the WeatherApp's database on purpose, using the snapshot
taken in the previous handout, then restores the disk in place and proves exactly which data comes
back and which does not.

## Before you start

You need the cluster, the WeatherApp, and the `mysql-snap-1` snapshot from the previous handout,
still in place, with one user (call them `alice`) already registered. Set your profile and move into
the folder holding your snapshot files:

```bash
export AWS_PROFILE=<your-aws-profile>
cd <your-s05-folder>
```

## Step 1 - Register a second user, then damage the database

```bash
kubectl get svc -n weatherapp weatherapp-ui
```

Open the load balancer's hostname and sign up a second user (call them `bob`), then log in as `bob`
to confirm the account works. `bob` did not exist at the moment the snapshot was taken. Keep that
in mind, since it is what the rest of this handout proves.

Now cause the kind of damage a snapshot is meant to protect against:

```bash
kubectl exec -n weatherapp weatherapp-auth-mysql-0 -- sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "DROP TABLE auth.users"'
```

```
mysql: [Warning] Using a password on the command line interface can be insecure.
```

The whole command is wrapped in single quotes, so it is sent into the pod unchanged, and
`$MYSQL_ROOT_PASSWORD` is only read once it is inside the container, from the pod's own environment:
the password never appears on your screen or in your shell's history. `mysql`'s warning is about
the command line *inside the pod*, not the one you typed.

Try logging in as `alice`: the login fails. The application is still up and the disk is still
healthy, but the `users` table is gone.

## Step 2 - The restore plan

Kubernetes has no way to roll a damaged volume back in place. Instead, you create a brand-new volume
from the snapshot and hand it to MySQL as if it had always been there. A StatefulSet does not look
for just any disk: it looks for a claim with one exact name, built from its claim template and the
pod's own name (here, `data-weatherapp-auth-mysql-0`). The plan is four steps: stop MySQL, remove the
damaged claim, create a new claim with that exact same name sourced from the snapshot, then start
MySQL again.

## Step 3 - Stop MySQL

```bash
kubectl scale statefulset weatherapp-auth-mysql -n weatherapp --replicas=0
kubectl get pods -n weatherapp
```

The MySQL pod is gone; the auth and UI pods keep running. Auth will fail its health checks, and
Kubernetes will even restart it, until MySQL is back (that is expected while you work).

## Step 4 - Remove the damaged claim

```bash
kubectl delete pvc data-weatherapp-auth-mysql-0 -n weatherapp
```

```
persistentvolumeclaim "data-weatherapp-auth-mysql-0" deleted from weatherapp namespace
```

This returns right away since the MySQL pod is already gone. If the pod were still running, the
delete would hang on a finalizer that protects a claim still in use. Because the storage class's
reclaim policy is `Delete`, the damaged EBS volume behind this claim is removed along with the
claim. In a real incident you might switch that volume to `Retain` first so it can be kept for
investigation; this handout does not need that, since the snapshot is independent of the volume it
came from.

## Step 5 - Create the new claim from the snapshot

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data-weatherapp-auth-mysql-0
  namespace: weatherapp
spec:
  storageClassName: ebs-csi-default-sc
  dataSource:
    name: mysql-snap-1
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 8Gi
```

```bash
kubectl apply -f pvc-from-snapshot.yaml
kubectl get pvc -n weatherapp
```

```
NAME                           STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS         VOLUMEATTRIBUTESCLASS   AGE
data-weatherapp-auth-mysql-0   Pending                                      ebs-csi-default-sc   <unset>                 2s
```

`Pending` is expected: the storage class waits for the first pod that actually uses the claim, so
the new volume is created in the same availability zone as that pod, not before.

## Step 6 - Start MySQL again

```bash
kubectl scale statefulset weatherapp-auth-mysql -n weatherapp --replicas=1
kubectl get pods -n weatherapp
```

Rerun the `get` until `weatherapp-auth-mysql-0` and both `weatherapp-auth-…` pods are `1/1 Running`:

```
NAME                                READY   STATUS    RESTARTS        AGE
weatherapp-auth-78874ffbf-rjzxk     1/1     Running   1 (4m26s ago)   17m
weatherapp-auth-78874ffbf-rm8jz     1/1     Running   1 (4m26s ago)   17m
weatherapp-auth-mysql-0             1/1     Running   0               29s
weatherapp-ui-5f8dd445c8-74lnk      1/1     Running   0               17m
weatherapp-ui-5f8dd445c8-zfx2q      1/1     Running   0               17m
weatherapp-weather-6df58665-8xqxs   1/1     Running   0               17m
weatherapp-weather-6df58665-q46pd   1/1     Running   0               17m
```

The `RESTARTS 1` on the auth pods is expected: their liveness probe restarted them about 30 seconds
after MySQL stopped, since auth could not reach its database in that window.

```bash
kubectl get pvc -n weatherapp
```

```
data-weatherapp-auth-mysql-0   Bound   pvc-…   8Gi   RWO   ebs-csi-default-sc   <unset>   37s
```

MySQL finds its data folder already there, on the restored disk, so it does not initialize a new
database: it starts on the data exactly as it stood at the moment the snapshot was taken.

## Step 7 - Prove it with two users

Log in as `alice`: it works. Log in as `bob`: you get an invalid-credentials error. `bob` was not
lost by the restore: he never existed at the moment the snapshot was taken.

::: keyconcept
**That gap (everything written after the last snapshot) is a recovery point: the point your data
can actually return to.** This is why snapshots run on a schedule, and how often that schedule runs
is a business decision, not a technical one.
:::

## Step 8 - Clean up the snapshot

```bash
kubectl delete volumesnapshot mysql-snap-1 -n weatherapp
kubectl get volumesnapshotcontent
```

```
No resources found
```

The underlying EBS snapshot is deleted along with the `VolumeSnapshot` object, since the snapshot
class's deletion policy is `Delete`. The restored volume itself stays: it is a volume of its own
now. Keep the `VolumeSnapshotClass`, since later handouts in this section need it again.

::: gotcha
**A snapshot restore is not a full disaster-recovery story.** It saved one disk, and nothing else:
not the Deployments, Services, and Secrets around that disk. The catalog that tracks the snapshot
lives inside this same cluster, and the EBS snapshot itself stays in this Region. If you lost the
cluster, or lost the Region, a snapshot alone would not bring the application back. Later handouts in
this section cover a tool built for that: Velero.
:::

## Stopping here?

The cluster and the WeatherApp (with `alice` only) are fine to leave running if you are continuing to
the next handout. To stop entirely:

```bash
kubectl delete namespace weatherapp
eksctl delete cluster -f cluster.yaml --wait
```

## Traps

::: gotcha
**Typing the `DROP TABLE` command with the outer quoting reversed fails with `Access denied`.** The
whole `sh -c '...'` argument must be in single quotes, with `$MYSQL_ROOT_PASSWORD` in double quotes
*inside* them, so your own shell never expands the variable. If it expands to nothing, MySQL sees an
empty password.
:::

::: gotcha
**`kubectl delete pvc` hangs.** The MySQL pod is still running, and the `kubernetes.io/pvc-protection`
finalizer is blocking the delete until it is gone. Confirm Step 3 actually scaled the StatefulSet to
zero before deleting the claim.
:::

::: gotcha
**The restored claim stays `Pending`, with an event naming the snapshot as not ready or not found.**
`mysql-snap-1` is missing or was never marked `READYTOUSE`. Go back and confirm the previous
handout's snapshot completed before starting this one.
:::
