Losing a namespace is recoverable with the same cluster still standing. The harder question is what
happens when the whole cluster is gone, or the whole Region it lives in is having a very bad day.
Everything you would normally reach for (the running pods, the stored credentials, the cluster
itself) lived inside that one cluster. This handout destroys the primary cluster, builds a new one
in a second Region, and restores the application into it from nothing but what survived outside the
original cluster.

## Before you start

You need the primary cluster, the WeatherApp, and a completed Velero backup named
`weatherapp-golden` (from the previous handout) with its backup storage location `Available`
(`ReadWrite`) in `us-east-1`. You need the `weatherapp-velero` IAM role and its policy, still in
place. You need a second AWS Region with enough vCPU quota for a two-node cluster (`t3.large` × 2 =
4 vCPU); this handout uses `eu-west-1`. Check your quota there before starting:

```bash
aws service-quotas get-service-quota --service-code ec2 --quota-code L-1216C47A --region eu-west-1
```

## Step 1 - The three survivors

A disaster-recovery plan needs three things to survive outside the cluster you are about to delete,
or there is nothing to rebuild from: the backups themselves (in S3 since the previous handout), the
permission to read them (the IAM role, created outside any cluster), and the recipe for a new
cluster, which turns out to be nothing more than a file.

## Step 2 - Write the recovery cluster's recipe

```yaml
# dr-cluster.yaml
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig

metadata:
  name: dr-cluster
  region: eu-west-1
  version: "1.36"

accessConfig:
  authenticationMode: API
  bootstrapClusterCreatorAdminPermissions: true

addons:
  - name: eks-pod-identity-agent
    version: v1.3.10-eksbuild.3
  - name: aws-ebs-csi-driver
    version: v1.66.0-eksbuild.1
    useDefaultPodIdentityAssociations: true
    configurationValues: |-
      defaultStorageClass:
        enabled: true

managedNodeGroups:
  - name: ng-1
    amiFamily: AmazonLinux2023
    instanceType: t3.large
    desiredCapacity: 2
    minSize: 2
    maxSize: 2
```

This file mirrors the cluster file from earlier in the course, in a second Region, and carries the
same two storage add-ons the primary cluster has. Velero recreates each volume claim with its
original storage class name, `ebs-csi-default-sc`, and these add-ons are what create a storage class
with exactly that name on the new cluster. The snapshot controller is not needed here, since
restoring the app moves its data from S3, not from a volume snapshot.

## Step 3 - Destroy the primary

```bash
export AWS_PROFILE=<your-aws-profile>
cd <path-to>/cluster.yaml-folder
kubectl delete namespace weatherapp
eksctl delete cluster -f cluster.yaml --wait
```

Delete the namespace **before** the cluster: this removes the load balancer and the MySQL volume
properly. Deleting the cluster underneath them instead leaves both orphaned and still billing. From
the moment the delete starts, the application is down, and everything between here and the login at
the end of Step 9 is the recovery time.

## Step 4 - Build the replacement

```bash
cd <your-s05-folder>
eksctl create cluster -f dr-cluster.yaml
kubectl get nodes
kubectl get storageclass
```

## Step 5 - The second survivor: the role

```bash
ROLE_ARN=$(aws iam get-role --role-name weatherapp-velero --query Role.Arn --output text)
aws eks create-pod-identity-association --cluster-name dr-cluster --region eu-west-1 --namespace velero --service-account velero-server --role-arn "$ROLE_ARN" --query association.associationId --output text
```

```
a-lhmth15pahl8juq0i
```

The role comes back untouched, since no cluster ever owned it. Its trust policy names a service, not
a cluster, so the same role can be associated with as many clusters as you like.

## Step 6 - A read-only view of the backups

```bash
cp values.yaml values-dr.yaml
```

Open `values-dr.yaml` and change one line, `accessMode: ReadWrite` to `accessMode: ReadOnly`:

```yaml
# values-dr.yaml
image:
  repository: docker.io/velero/velero
  tag: v1.18.3

initContainers:
  - name: velero-plugin-for-aws
    image: velero/velero-plugin-for-aws:v1.14.3
    imagePullPolicy: IfNotPresent
    volumeMounts:
      - mountPath: /target
        name: plugins

configuration:
  backupStorageLocation:
    - name: default
      provider: aws
      bucket: <BUCKET>
      default: true
      accessMode: ReadOnly
      config:
        region: us-east-1

  features: EnableCSI

snapshotsEnabled: false

deployNodeAgent: true
nodeAgent:
  disableHostPath: true

credentials:
  useSecret: false
serviceAccount:
  server:
    name: velero-server
```

The Region inside this file stays `us-east-1`, since that is the bucket's Region, not the recovery
cluster's Region: the cluster runs in `eu-west-1`, but the backups it reads still live where they
were originally written. This means the recovery cluster can restore from those backups, but it can
never overwrite or delete the backups the whole recovery depends on.

## Step 7 - Velero on the recovery cluster

```bash
helm upgrade --install velero vmware-tanzu/velero --version 12.2.0 -n velero --create-namespace -f values-dr.yaml
kubectl get pods -n velero
```

## Step 8 - The backup is already there

Velero reads the bucket's backup list about once a minute. Wait roughly 60 seconds after the
location turns `Available` before checking:

```bash
velero backup get
```

```

weatherapp-golden   Completed   0        0          2026-09-27 14:41:02 +0000 UTC   29d       default                             <none>
```

`weatherapp-golden` appears without you ever creating a backup on this cluster: Velero simply read
the list of backups from the bucket itself.

## Step 9 - Restore across Regions

```bash
velero restore create dr-restore-1 --from-backup weatherapp-golden --wait
```


```bash
kubectl get datadownloads -n velero
```

```

dr-restore-1-5kdqn   Completed   46s       218438819    218438819     default            56s   ip-192-168-56-244.eu-west-1.compute.internal
```

The actual bytes crossed from a bucket in one Region into a brand-new volume in another: this is
the part an EBS snapshot alone could never do.

```bash
kubectl get pods -n weatherapp
kubectl get pvc -n weatherapp
helm list -n weatherapp
```

Rerun `kubectl get pods -n weatherapp` until all seven pods are `1/1 Running`; the claim comes back
`Bound`, and `helm list` shows the same three releases as before.

## Step 10 - Prove it in eu-west-1

```bash
kubectl get svc -n weatherapp weatherapp-ui
```

```
NAME            TYPE           CLUSTER-IP      EXTERNAL-IP                                                               PORT(S)        AGE
weatherapp-ui   LoadBalancer   10.100.128.99   a87ee2b76ff4c4ea3a1556322fdca310-1391211664.eu-west-1.elb.amazonaws.com   80:30656/TCP   63s
```

Open the new hostname (it ends in `.eu-west-1.elb.amazonaws.com`, since the recovery cluster runs
there) and log in as `alice`: it works, in a Region that has never seen her before this moment. This
is the recovery point (the instant `weatherapp-golden` was taken) and the recovery time is
everything between the delete in Step 3 and this login.

::: keyconcept
**Measured back to back, with no investigation pauses, this whole recovery (namespace delete,
cluster delete, cluster create, role association, Velero install, the first backup sync, and the
restore through to a working login) takes about 33 minutes of wall clock.** Most of that is the two
`eksctl` operations (delete and create); the restore itself finishes in under a minute once the
backup location has synced.
:::

## The real-world caveat

The backup bucket itself still sits in `us-east-1` (the very Region this handout pretended to lose),
so on its own, this setup is not safe from a true Region-wide outage. In production, you would
also replicate that bucket into the recovery Region, run backups on a schedule instead of by hand,
and practice this exact restore regularly: a restore you have never tested is only a hope.

## Cleaning up (both Regions)

This section left resources in **two** Regions. Clean up in this order, so nothing is orphaned and
nothing keeps billing:

**1. The recovery cluster's application (eu-west-1):**

```bash
kubectl delete namespace weatherapp
```

**2. The recovery cluster itself (eu-west-1):**

```bash
eksctl delete cluster -f dr-cluster.yaml --wait
```

**3. The primary cluster, if you have not already removed it in Step 3 above (us-east-1):** already
gone at this point in this handout's own flow, but if you are cleaning up from a different starting
state:

```bash
kubectl delete namespace weatherapp
eksctl delete cluster -f cluster.yaml --wait
```

Delete any leftover `VolumeSnapshot` **before** its cluster: an EBS snapshot left behind after its
cluster is gone still bills, and there is no cluster left to delete it through.

**4. The backup bucket.** The recovery cluster's backup storage location is `ReadOnly`, so Velero on
that cluster cannot delete the bucket's contents. Remove it directly:

```bash
export BUCKET=$(aws s3api list-buckets --query "Buckets[?starts_with(Name, 'weatherapp-velero-')].Name" --output text)
aws s3 rb "s3://$BUCKET" --force
```

**5. The IAM role:**

```bash
aws iam delete-role-policy --role-name weatherapp-velero --policy-name velero-s3
aws iam delete-role --role-name weatherapp-velero
```

With that, nothing from this section is left billing in either Region. Before you stop, it is worth
confirming by hand in both `us-east-1` and `eu-west-1`: no `basic-cluster` or `dr-cluster`, no
`eksctl-*` CloudFormation stack for either, no EC2 instance, NAT gateway, Elastic IP, load balancer,
EBS volume or EBS snapshot tagged for either cluster, and no `weatherapp-velero-*` bucket or
`weatherapp-velero` role remaining.

## Traps

::: gotcha
**`eksctl delete cluster` or `eksctl create cluster` fails with `checking AWS STS access – cannot get
role ARN for current session`.** `AWS_PROFILE` was not exported in this terminal. Export it and
retry. This is easy to miss the moment you open a fresh shell in Step 3.
:::

::: gotcha
**`eksctl create cluster -f dr-cluster.yaml` fails on capacity, or `VcpuLimitExceeded`.** The second
Region's default vCPU quota may be lower than the primary Region's. Check it with the
`get-service-quota` command in "Before you start" before you begin, and request an increase if
needed. This can take time to process, so do it well before you plan to run this handout.
:::

::: gotcha
**`velero backup get` on the recovery cluster prints only the header row, with no backups listed.**
The first sync has not run yet. Wait about 30 seconds after the backup location turns `Available` and
rerun.
:::

::: gotcha
**The recovery cluster's backup location stays `Unavailable`.** The Pod Identity association from
Step 5 is missing, or the bucket name in `values-dr.yaml` is wrong. Confirm the association exists,
fix the values file if needed, and rerun the `helm upgrade --install`.
:::

::: gotcha
**`aws s3 rb` fails with `BucketNotEmpty`.** The `--force` flag was left off: it is required to
empty and remove the bucket in one step.
:::
