An EBS snapshot is a point-in-time copy of a volume, and after the first one, every later snapshot
only stores the blocks that changed since the last. Kubernetes has no native idea of a snapshot, so
it borrows the same class / request / real-thing shape you already know from storage: a
VolumeSnapshotClass plays the role of a StorageClass, a VolumeSnapshot plays the role of a
PersistentVolumeClaim, and a VolumeSnapshotContent plays the role of a PersistentVolume. Two
programs make it work: the snapshot controller (an add-on EKS does not install for you) watches
those three objects, and the EBS CSI driver's snapshotter sidecar is the piece that actually calls
EBS to take the copy. This handout rebuilds the EKS cluster, adds the snapshot controller, brings
the WeatherApp back into its own namespace, and takes the first snapshot of its database.

## Before you start

You need an AWS account with an EKS-capable IAM identity, `eksctl`, `kubectl`, `helm`, the AWS CLI,
and the WeatherApp Helm charts (`weatherapp-auth`, `weatherapp-weather`, `weatherapp-ui`) from
earlier in this course. You also need a free WeatherAPI.com key. Everything below assumes a
`cluster.yaml` for a cluster named `<YOUR_CLUSTER_NAME>` and an `addons.yaml` with the EKS Pod
Identity agent and the EBS CSI driver, both from an earlier section.

```bash
export AWS_PROFILE=<your-aws-profile>
cd <path-to>/cluster.yaml-folder
eksctl create cluster -f cluster.yaml
```

## Step 1 - Install the snapshot controller, before the storage add-ons

Next to `cluster.yaml`, create `snapshot-addon.yaml`:

```yaml
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig

metadata:
  name: <YOUR_CLUSTER_NAME>
  region: <YOUR_CLUSTER_REGION>

addons:
  - name: snapshot-controller
    version: v8.6.0-eksbuild.2
```

```bash
eksctl create addon -f snapshot-addon.yaml
```

Install this **before** the storage add-ons, as the EBS CSI driver's documentation asks: the
driver's snapshotter sidecar is the piece that talks to the snapshot API, and it needs that API
present to do any work. On the EKS-managed add-on, the sidecar always ships regardless of order —
installing the snapshot API first simply keeps the order the docs describe.

```bash
kubectl get crd | grep volumesnapshot
```

```
volumesnapshotclasses.snapshot.storage.k8s.io              2026-09-27T13:42:32Z
volumesnapshotcontents.snapshot.storage.k8s.io             2026-09-27T13:42:32Z
volumesnapshots.snapshot.storage.k8s.io                    2026-09-27T13:42:32Z
```

Now install the storage add-ons (the EKS Pod Identity agent and the EBS CSI driver) from
`addons.yaml`:

```bash
eksctl create addon -f addons.yaml
kubectl get storageclass
```

```
NAME                           PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION   AGE
ebs-csi-default-sc (default)   ebs.csi.aws.com         Delete          WaitForFirstConsumer   true                   14s
gp2                            kubernetes.io/aws-ebs   Delete          WaitForFirstConsumer   false                  9m58s
```

The default StorageClass can take a few seconds to appear after the command returns; if you only
see `gp2`, wait ten seconds and rerun. Confirm the sidecar is really there:

```bash
kubectl -n kube-system get deploy ebs-csi-controller -o jsonpath='{.spec.template.spec.containers[*].name}'
```

```
ebs-plugin csi-provisioner csi-attacher csi-snapshotter csi-resizer liveness-probe
```

`csi-snapshotter` is the container that talks to the snapshot API.

## Step 2 - Bring the WeatherApp back into its own namespace

```bash
export DOCKERHUB_USER=<your-dockerhub-user>
export JWT_SECRET=$(openssl rand -hex 32)
export DB_ROOT_PASSWORD=$(openssl rand -hex 16)
export DB_PASSWORD=$(openssl rand -hex 16)
read -rs WEATHER_API_KEY && export WEATHER_API_KEY
helm upgrade --install weatherapp-auth ./weatherapp-auth -n weatherapp --create-namespace \
  --set image.repository=$DOCKERHUB_USER/weatherapp-auth \
  --set jwtSecret="$JWT_SECRET" \
  --set mysql.auth.rootPassword="$DB_ROOT_PASSWORD" --set mysql.auth.password="$DB_PASSWORD"
helm upgrade --install weatherapp-weather ./weatherapp-weather -n weatherapp \
  --set image.repository=$DOCKERHUB_USER/weatherapp-weather \
  --set apikey="$WEATHER_API_KEY"
helm upgrade --install weatherapp-ui ./weatherapp-ui -n weatherapp \
  --set image.repository=$DOCKERHUB_USER/weatherapp-ui \
  --set jwtSecret="$JWT_SECRET"
```

From here on, this section backs up, deletes, and restores the WeatherApp as a single unit, and a
namespace is exactly that unit — the services still find each other by name, since they all share
it.

```bash
kubectl get pods -n weatherapp
kubectl get svc -n weatherapp weatherapp-ui
```

Once every pod is `1/1 Running`, open the `EXTERNAL-IP` hostname from the second command in a
browser, sign up a user, and log in. This handout tracks one user, `alice`, through the rest of the
section.

## Step 3 - Take the snapshot

Create a new folder and, in it, `volumesnapshotclass.yaml`:

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: ebs-snapclass
driver: ebs.csi.aws.com
deletionPolicy: Delete
```

`deletionPolicy: Delete` means that deleting this object later deletes the real EBS snapshot behind
it too, so nothing is left billing once you are done with it.

```bash
kubectl apply -f volumesnapshotclass.yaml
kubectl get volumesnapshotclass
```

```
volumesnapshotclass.snapshot.storage.k8s.io/ebs-snapclass created
NAME            DRIVER            DELETIONPOLICY   AGE
ebs-snapclass   ebs.csi.aws.com   Delete           2s
```

Now `volumesnapshot.yaml`, pointed at the MySQL claim the WeatherApp's StatefulSet created:

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: mysql-snap-1
  namespace: weatherapp
spec:
  volumeSnapshotClassName: ebs-snapclass
  source:
    persistentVolumeClaimName: data-weatherapp-auth-mysql-0
```

```bash
kubectl apply -f volumesnapshot.yaml
kubectl get volumesnapshot -n weatherapp
```

Rerun the `get` until `READYTOUSE` reads `true` (about 40 seconds):

```
NAME           READYTOUSE   SOURCEPVC                      SOURCESNAPSHOTCONTENT   RESTORESIZE   SNAPSHOTCLASS   SNAPSHOTCONTENT                                    CREATIONTIME   AGE
mysql-snap-1   true         data-weatherapp-auth-mysql-0                           8Gi           ebs-snapclass   snapcontent-555d17cb-47b8-43e9-8628-9a31f4ec888f   39s            40s
```

## Step 4 - Prove it against a real EBS snapshot

`kubectl get volumesnapshotcontent` alone has no column for the underlying EBS snapshot id — ask
for it explicitly:

```bash
kubectl get volumesnapshotcontent -o custom-columns=NAME:.metadata.name,SNAPSHOTHANDLE:.status.snapshotHandle
```

```
NAME                                               SNAPSHOTHANDLE
snapcontent-555d17cb-47b8-43e9-8628-9a31f4ec888f   snap-061c86daefb2c9cbe
```

Copy the `snap-…` id and ask EBS directly, never retyping it:

```bash
aws ec2 describe-snapshots --snapshot-ids <SNAPSHOT_ID> --query 'Snapshots[0].[State,VolumeSize]' --output table
```

```
-------------------
|DescribeSnapshots|
+-----------------+
|  completed      |
|  8              |
+-----------------+
```

`State` is `completed` and `VolumeSize` is `8`, the volume's exact size in GiB.

::: keyconcept
**This is a crash-consistent copy, not an application-consistent one.** The snapshot was taken
while MySQL was still running, so it captures the same state MySQL would be in after a sudden power
cut. MySQL's InnoDB storage engine is built to recover cleanly from exactly that. The snapshot also
lives in the Region it was taken in, and it is incremental: the next snapshot you take of this
volume only stores the blocks that changed since this one.
:::

## Stopping here?

Leaving the cluster running is fine if you are continuing straight to a point-in-time restore. If
you are stopping for longer, delete the snapshot, then the namespace, then the cluster, in that
order, so nothing is orphaned:

```bash
kubectl delete volumesnapshot mysql-snap-1 -n weatherapp
kubectl delete namespace weatherapp
eksctl delete cluster -f cluster.yaml --wait
```

To pick this back up later, rerun `eksctl create cluster -f cluster.yaml`, `eksctl create addon -f
snapshot-addon.yaml`, `eksctl create addon -f addons.yaml`, then Step 2 and Step 3 above.

## Traps

::: gotcha
**`kubectl get storageclass` only shows `gp2` right after `eksctl create addon -f addons.yaml`
returns.** The default StorageClass takes a few seconds to appear. Wait ten seconds and rerun; do
not assume the add-on failed.
:::

::: gotcha
**A plain `kubectl get volumesnapshotcontent` never shows the EBS snapshot id.** The handle lives at
`.status.snapshotHandle`, which is not a default printer column on any Kubernetes version. Use the
`-o custom-columns=...` form in Step 4, not `-o wide`.
:::

::: gotcha
**`READYTOUSE` stays `false` for minutes.** This usually means the snapshot controller or the CSI
driver is unhealthy. Run `kubectl describe volumesnapshot -n weatherapp mysql-snap-1` and read its
Events for the cause before retrying.
:::
